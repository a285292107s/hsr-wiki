# 0038. 终局排期按分组表指针解析，忘却之庭单边排期参与目录排序

## 状态

`accepted`（**已实现**：`endgame.py` 的 `_load_schedules` 重构为按分组表 `ScheduleDataID` 指针解析，三模式统一；忘却之庭排期记录回退 `ScheduleDataGlobal.json` 且允许单边日期，原「ScheduleID − 200000 = GroupID」编号推断废弃；前端 `bySeasonDesc` 排序键改为首个已知端点（`live_begin` 优先、回退 `live_end`），`mazeDateRange` 补单边渲染，`tools/gen-ai-endpoints.mjs` 的排序与日期区间镜像同步；`_load_test_periods` 并入 `_load_schedules` 的测试期分类）

## 背景

用户报告：/endgame 忘却之庭列表的排序有问题——当前游戏内正在进行的混沌回忆赛季排在列表最底部。取证后五条事实定了性：

1. **受影响的是两个内容完整的正式赛季**：`maze.json` 里 1034 扫除风暴 / 1035 来生泅渡各 12 层 + 星启，均非占位行。外部佐证：4.6 版本混沌回忆当期即「来生泅渡」（多篇 4.6 攻略），扫除风暴为 4.5 期。
2. **排期指针已脱离编号约定**：`ChallengeGroupConfig` 中 1034 → `291015`、1035 → `291016`，不再是 `201034`/`201035`；这两条排期记录也不在 `ScheduleDataChallengeMaze.json`，而在 `ScheduleDataGlobal.json`。`ScheduleID − 200000 = GroupID` 的推断对它们失效。
3. **排期是单边的**：`291015` 仅 `BeginTime`（2026-08-17）、`291016` 仅 `EndTime`（2026-11-02）——两期共享 2026-08-17 → 2026-11-02 的窗口，交替分界不在静态数据里（对应 4.5 起版本时长调整）。
4. **旧解析三重不适配**：只读迷宫排期表、按编号硬映射、要求 Begin/End 双全 → 两季 `live_begin/live_end` 落空串，目录卡无日期、状态「未知」。
5. **前端沉底放大成排序错误**：`bySeasonDesc` 把无 `liveBegin` 的条目整体排到所有有日期条目之后——当期赛季落在 57 条中的第 44/45 位，排在 2023 年 4 月的「琥珀恩赐」之后。

另有一条回归安全网：story/boss 的分组配置表（`ChallengeStoryGroupConfig` / `ChallengeBossGroupConfig`）同样带 100% 的 `ScheduleDataID`，且按指针解析出的排期与编号推断**逐条相等**（story 27 条 / boss 22 条，实测零差异）。

## 决策

**排期解析统一按分组表指针；单边日期原样保留；排序与展示取首个已知端点**：

1. **解析判据（三模式统一）**：`{GroupID → ScheduleDataID}` 指针直查排期记录，多张排期表按序查找、先登记者胜（忘却之庭 = `ScheduleDataChallengeMaze` 优先、`ScheduleDataGlobal` 回退；虚构/末日只查各自排期表）。编号推断废弃——它已经被证伪一次，story/boss 未来迁移时同一判据继续成立。无指针的常驻组（100 / 900）不进入结果，与 `_load_permanent_groups` 的「`ScheduleDataID` 为空 = 常驻」判据同源。
2. **单边日期不合成**：`live_begin` / `live_end` 允许其一为空，**禁止**用邻接赛季补全缺失端点（1034 的结束日期 = 1035 的开始日期，这个分界在数据里不存在，补了就是编造）。
3. **占位过滤适配单边**：任一已知端点年份 ≥2030 丢弃（未来占位，如组 108/109 的 2033 排期）；`End` 早于公测（2023-04-26）为 beta 测试期——打 `test` 标、不落日期（沿用原 `_load_test_periods` 语义，并入本函数）；仅 `Begin` 且早于公测视同 beta 残留丢弃；**Begin 早于公测但 End 晚于公测的跨公测排期保留**（组 117 形态，2023-04-17 → 05-15）。原「双全才收」对占位的甄别在这些边界上逐条等价。
4. **前端排序键 = 首个已知端点**：`live_begin` 优先、回退 `live_end`；**同日平局开始端在前**——1036（开始于 2026-11-02）与 1035（结束于 2026-11-02）同日，开始端是未来赛季、结束端是当期，未来者新；两端皆无者按编号降序沉底（常驻关 / 测试期的相对位置与改动前一致）。排序后忘却之庭列首为 1036（未开始）→ **1035（当期）→ 1034（上期）** → 1033，与游戏内「当期置顶、往期倒序」一致；站点把已排期的未来赛季继续置顶（虚构 2027 / 末日 3022 的既有惯例）。
5. **展示**：`mazeDateRange` 补「仅结束端 → `– YYYY.MM.DD`」分支（与既有「仅开始端 → `YYYY.MM.DD –`」对称）；`mazeStatus` 无需改动——单边日期下 1034/1035 均按已知端点判为「进行中」。AI 快照生成器的排序与日期区间是人工镜像副本，同批同步，契约（快照判据 = 应用判据）不破。
6. **已知不准确的诚实呈现**：扫除风暴实际已被来生泅渡接替，但交替分界不在静态数据里，其「进行中」徽标按数据判定保留，不为可读性编造结束日期；后续快照若补全排期自然修正。

## 后果

**正面**

- 当期赛季回到列表头部，读者打开 /endgame 即见游戏内正在进行的期数；日期与状态徽标随之恢复。
- 排期判据从「编号推断」升级为「官方指针」，三模式单一口径；排期记录迁移表、指针编号变化都不再破坏排序。
- 指针化对 story/boss 是**逐条零差异**的纯等价替换（27/22 条实测全等），虚构/末日目录无任何漂移。

**负面**

- 扫除风暴的「进行中」在两期交替后与游戏实际不符（数据无法判定），直到后续快照补全排期。
- 同日平局的「开始端在前」规则依赖读者理解「一条排期只有结束端」的数据形态；列表上两张卡一个显示 `– 2026.11.02`、一个显示 `2026.11.02 –`，需要一点解释成本。

**中性**

- `docs/data/转换器字段映射.md` 的排期段同步重写；`CONTEXT.md` 术语层不受影响（排期指针不属术语）。
- 测试期（101-107/116）与常驻关（100/900）仍按原样渲染在列尾——是否过滤/加徽标是独立的展示决策，本轮不动。

## 替代方案

| 方案 | 为何未采用 |
|---|---|
| 只给迷宫加 `ScheduleDataGlobal` 回退、保留编号推断 | 改动最小，但编号推断已被证伪一次；story/boss 未来迁移时同一问题复发。指针化实测对二者零回归 |
| 缺失端点用邻接赛季补全（1034 的结束 = 1035 的开始） | 分界不在静态数据里，补全 = 编造数据，违反文本/数据来源硬约束 |
| 只改前端排序键（`live_begin || live_end` 兜底）、转换器不动 | 排序能修，但日期区间与状态仍是「未知」，且源头判据继续失真，AI 快照镜像无从对齐 |
| 无日期条目按 ID 降序置顶 | 测试期与常驻关会压过全部正式赛季，与游戏顺序相反 |
| 排序键取 begin 与 end 的较晚者 | 双端齐全的赛季会以结束日参与排序，相邻赛季（前一个的结束 = 后一个的开始）大量同日，平局规则反而成为主路径 |
