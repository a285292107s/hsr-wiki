# 0045. 怪物数值合成链补上实例修正值（含默认等级取组上限）

## 状态

`accepted`（**已实现**：`monster_common.load_monsters` 透出 `stance_modify` / `speed_modify`（非空才落键、实例不继承模板值）；`monster_detail` 原值随 payload 给前端；`endgame._monster_out` **在转换期并入** stance/speed；前端 `monster-stats.ts` 增 `modify` 入参与 `monsterStanceValue`，详情页默认等级改为「该难度组曲线的最高档」；`EnemyCard` 撤掉「另有修正」标注；AI 快照四维标签改为「（模板基准）」。修订 [0040](0040-怪物详情页战斗数值口径.md) 决策 1 / 4 / 6。**被 [0049](0049-怪物数值合成链补上怪物侧精英组倍率.md) 修订**——算式插入精英组段后，修正值的乘法位置随该 ADR 的链条定义刷新；[0050](0050-出没样本带关卡语境与实战面板.md) 在其上叠关卡侧精英组）

## 1. 背景与问题

[ADR 0040](0040-怪物详情页战斗数值口径.md) 建立的合成链只有三段：`基准 × 维度修饰比 × 等级曲线`，
并把 `MonsterConfig` 的 `*ModifyValue` 当作「场景系数（社群术语修饰值 2）」**排除在合成之外**。
0040 当时给出的理由是「该系数在 Stage 相关配置区间采样离散，不在本仓逐怪合成范围内」。

但 `*ModifyValue` 就在 `MonsterConfig`（逐怪、逐实例）里，不是 Stage 级配置：

- `StanceModifyValue`：**472 个实例**非空（值全是 30 的整数倍，如 +30 / −120，2250 条为空）；
- `SpeedModifyValue`：**369 个实例**非空（如 −44 / +56 / +37）；
- `{Stance,Speed}ModifyRatio`：**2722/2722 条恒为 1** ⇒ 唯一旋钮就是那个 Value。

而站点已经在展示这些数值：终局敌方卡（`EnemyCard.vue`）显示「韧性 / 速度」标签，用的是模板基准值——
实测已分发数据里有 **127 个敌方实例带韧性修正、32 个带速度修正**，这些卡上的数字因此是偏的
（例：`100401401` 模板韧性 300、实例修正 −120，卡上原显示 300）。

## 2. 判定

**是本站的口径缺陷，不是官方数据错误**（与 0040 同判）：修正值确有作用，且**加法位置可验证**——
上一轮「加法位置无据可验」的结论被推翻，验证方式见决策 2。

## Considered Options

- **维持 [0040](0040-怪物详情页战斗数值口径.md) 的「`*ModifyValue` 是 Stage 级场景系数、排除在合成之外」**：放弃——该值就在逐怪的 `MonsterConfig` 里（`StanceModifyValue` 472 个实例非空、`SpeedModifyValue` 369 个），且 `{Stance,Speed}ModifyRatio` 2722/2722 恒为 1，唯一旋钮就是那个 Value；加法位置已可验证（见决策 2）。
- **让终局敌方卡继续显示模板基准韧性 / 速度**：放弃——实测已分发数据里 127 个敌方实例带韧性修正、32 个带速度修正，卡上数字是偏的（例 `100401401` 实际 −120，原显示 300）。
- **转换期把修正值并入 `stats` 写死**：放弃——会掩盖「基准 vs 修正」两层来源，前端滑条与口径注记都需要分开的两层。

## 3. 决策

1. **算式（修正值加在曲线之后、不再被缩放）**：
   `值(等级) = 基准 × 维度修饰比 × 等级曲线[难度组][等级] + 修正值`；
   **韧性不入等级曲线链**（曲线表没有韧性维度）：`韧性 = 韧性基准 + 修正值`。
2. **验证依据（社群实现逐项反推，非官方公式）**：参考站 `hsr.nanoka.cc`（与本仓同源解包数据的社区站）
   的怪物页面已实现该合成，同族同模板对照可判定加法位置——`144 × 1.32 = 190`，带 −44 修正的那一档
   显示 **146**（`190 − 44`；若先加后乘会得到 132）；韧性 `90 + 30 = 120`、`360 − 120 = 240`、
   `190 + 56 = 246` 全部吻合。**这是社群实现证据，不是官方文档**；若日后拿到官方口径，以官方为准。
3. **落点分工（与 0040 一致的理由：滑条要实时合成）**：
   - **详情页**：`monster_common` 透出原值 → `monster_detail` 落进 payload → 前端按上式在
     1..组上限 上实时合成（等级滑条拖动即重算）；
   - **终局敌方卡**：没有等级语境，转换期直接并入（`_monster_out`，口径 = 基准 + 修正值），
     payload 里不再出现这两个键、前端零合成逻辑。
4. **默认等级 = 该怪难度组曲线的最高档**（不再写死 100）。写死 100 在曲线组上限不是 100 时会
   静默出错：滑条 max 与值不一致（组 1401 只到 40）时合成取不到曲线行 → 整页回退基准值却仍标「等级 100」。
   实测：`HardLevelGroup.json` 有 9 个难度组（组 1/3 分别到 100/120，组 1401 只到 40），
   但 **2722/2722 个怪都在组 1（上限 100）**，且 632 个目录条目的组上限全为 100
   ⇒ **本决策对现有页面零数值变化**，只是消掉潜在错误。数据里 `StageConfig.Level` 最高到 120
   （93 种等级），但没有任何怪引用到 120 的那条曲线，故不把滑条上限抬到 120。
5. **口径注记必须与数字同屏**（承接 0040 决策 4）：注记写「模板基准 × 维度修饰比 × 等级曲线（难度组 N）
   ＋ 实例修正值；基准值 …，未含关卡级剧情与场景系数」，并在该实例带修正时把修正值写进注记。
6. **透明度不写进 UI**：既然修正值已并入数字，就不再单独标「另有修正」——同屏出现两套口径
   （一个含修正、一个提示未含）必被误读。原始值仍在数据里（详情 payload）可回溯。

## 4. 影响面

- `tools/converter/converters/monster_common.py`：新增 `_modify_value()`；两者非空才落键，
  **实例以自己的 config 记录为准且不继承模板的**。
- `tools/converter/converters/monster_detail.py`：payload 增 `stance_modify` / `speed_modify`（原值）。
- `tools/converter/converters/endgame.py`：`_monster_out` 并入 stance/speed 并跳过原始键；`_lean_monster` 无需再剥。
- 前端：`src/lib/monster-stats.ts`（`modify` 入参 + `monsterStanceValue`）、`MonsterDetailView.vue`
  （默认等级 = 组上限、速度含修正、韧性走 `monsterStanceValue`、注记）、`EnemyCard.vue`（撤标注）、
  `src/services/types/{monster,endgame}.ts`。
- AI 快照：怪物详情的四维数值**不做合成**（不在生成器里实现第二份算式），标签逐字改为
  「生命（模板基准）」等；口径写在 `docs/agents/ai-discoverability.md`。
- 测试：`pytest`（`_modify_value` 透明度与实例不继承、`_monster_out` 并入）；`vitest`
  （`modify` 加在曲线之后 + `monsterStanceValue`）；`e2e/layout-monster.spec.ts`（用实例页
  `100201502` 独立算一遍期望值对照）、`e2e/layout-endgame.spec.ts`（卡的数值必须能在数据里找到）。

## 5. 后果

- 0040 决策 1 的算式**扩展**为四段；决策 4「未含场景系数」收窄为「未含**关卡级**剧情与场景系数」；
  决策 6 的「默认等级 100」被本决策 4 取代。
- 0040 决策 3 关于「实例别名必须用自己那条 config 记录」的原则同样适用于修正值：**不得继承模板的**。
- 详情页与终局卡对同一实例的数字保持一致（终局卡=基准+修正；详情页在滑条任意档=基准×比×曲线+修正，
  两者在曲线=1 的档位才重合）——这是**刻意的**：终局卡不承载等级，故不做曲线。
