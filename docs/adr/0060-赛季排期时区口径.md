# 赛季排期的时区口径：裸本地串按固定 +08:00 解释

**Status**: Accepted（已实现：前端判据 + 预渲染生成器镜像 + 单测）

> 本 ADR 只裁一件事：**终局赛季排期字段（`live_begin` / `live_end` / `begin` / `end`）的时间解释口径**。
> 它不改字段结构、不改数据源、不改路由与快照份数，也不动 `mazeStatus` 的状态枚举与展示文案。

## Context

上游给的排期是**无时区的裸本地时间串**（`2026-11-02 04:00:00`）。实测四份终局全量表共 **186 条排期串，带时区 / `Z` 标记的 0 条**。

`new Date('2026-11-02 04:00:00')` 的语义是「按运行环境的本地时区解释」——它不是**一个**绝对时刻，而是**每个环境各自一个**。实测同一串的绝对时刻：

| 运行环境 | `new Date(裸串).getTime()` | 与排期时区（+08:00）之差 |
| --- | --- | --- |
| UTC | `2026-11-02T04:00:00Z` | +8h |
| Asia/Shanghai | `2026-11-01T20:00:00Z` | 0 |
| America/New_York | `2026-11-02T09:00:00Z` | +13h |
| Pacific/Kiritimati | `2026-11-01T14:00:00Z` | −6h |

三条后果，前两条是**同一 URL 两套事实**：

1. **访客之间分叉**：`mazeStatus` 拿这个时刻与 `Date.now()` 比大小，于是「当期赛季」（以及目录卡状态徽章、玩法页「当期/最新赛季」判据）在赛季边界附近对**不同时区的访客**给出不同答案，窗口最宽 ±14h。
2. **快照与页面分叉**：预渲染快照在**构建机**上算这个判据（`tools/gen-ai-endpoints.mjs` 的 `seasonStatus` 镜像），页面在**访客浏览器**里算。构建落在边界附近时，两者给出不同赛季——而快照是爬虫与 AI 唯一可见的那一份。
3. **带时区串的日期文案会漂移**（当前数据未命中，机制已实测）：`dateRange` 旧实现用 `getFullYear()/getMonth()/getDate()` 本地读取，`new Date('2023-06-12T04:00:00+08:00')` 在 UTC 构建机上读作 `2023.06.11`。现有裸串因为「同环境解析 + 同环境格式化」自洽而不显形，一旦数据换成 ISO 形态即整片差一天。

## Decision

1. **裸串（`YYYY-MM-DD`、`YYYY-MM-DD HH:mm[:ss]`、`YYYY-MM-DDTHH:mm[:ss]`）一律按固定 `+08:00` 解释**——排期是游戏官方服务器时间，`04:00` 指服务器墙钟的 04:00，与访客所在地无关。常量 `SEASON_TZ_OFFSET` 单点声明。
2. **已带时区偏移或 `Z` 的串按原语义解释**，不被改写（唯一入口 `seasonTimeMs`）。
3. **展示日期取排期时区的墙钟日期**，不取访客本地日期（`seasonDateParts`）；格式仍为 `YYYY.MM.DD`，一年一个赛季的既有文案形态不变。
4. **前端与预渲染生成器同源同判据**：两端各有一份实现（生成器不能 import TS），注释互为指针，任何一侧改动必须同批改另一侧——与仓库既有的「镜像副本」纪律一致（如 `bySeasonDesc` / `mazeDateRange`）。
5. **判据落点不变**：`mazeStatus` 的枚举（`live`/`ended`/`upcoming`/`unknown`）与其展示文案、`bySeasonDesc` 排序键、目录卡与 Hero 的渲染分支全部不动；只换「字符串 → 绝对时刻」这一步。
6. **不新增字段、不改转换器**：本轮不要求上游写 ISO+offset（见替代方案 a）。

## 替代方案（被否 / 留账）

- **(a) 让转换器把排期写成带偏移的 ISO 串（如 `2026-11-02T04:00:00+08:00`）**：更彻底——口径写进数据，前端与生成器都不必再解释。**本轮不做**：需重跑四份终局全量表并把 `maze*.catalog.json` 一并改写（排期字段同时进目录卡与 sitemap 派生），数据版本与增量缓存都要重新对齐，收益与「前端两处 30 行判据」不成比例。记为后续项：若将来出现第三种消费方（如 API 对外），优先做这条。
- **(b) 引入时区库（如 `luxon` / `date-fns-tz`）**：违反运行时依赖准入（五件套之外不引库）。**禁止**。
- **(c) 跟随访客本地时区（即维持现状）**：等于承认「同一 URL 对不同用户是不同事实」，与「单事实源」「快照 ↔ 页面逐字一致」两条既有判据正面冲突。**否决**。
- **(d) 服务端按构建时区统一（例如强制构建机 TZ=Asia/Shanghai）**：只治快照侧，访客侧仍分叉（判据在浏览器里跑），且把正确性挂在构建环境变量上。**否决为唯一手段**。

## 后果

### 正面

- 「当期赛季」在任意访客、任意构建机上是**同一个绝对时刻的同一个答案**；赛季切换不再有 ±14h 的模糊带。
- 快照与页面的赛季选取判据可逐字对齐（本轮已用「生成器读全量表 + 同一 +08:00 判据」一并收口）。
- 带时区串若将来进入数据，日期文案不再随构建机差一天。

### 负面 / 留账

- **隐含假设入库**：`+08:00` 是常量，官方若改赛事时区必须改这两处（单点常量 + ADR 记录，可检索）。
- **peak 仍无排期**：异相仲裁 10/10 期四个排期字段全空 ⇒ 状态恒 `unknown`、永无「当期赛季」，这是**数据缺失**而非本口径能修的问题（展示侧已按「最新赛季」如实标注，Hero 不再挂无信息的「未知」徽章）。
- **镜像面 +1**：`seasonTimeMs` / `seasonDateParts` 两份实现（TS + 生成器），任何一端口径改动都要同批改另一侧；单测只能锁前端那一份，生成器那一份靠 TZ 无关性实测（见验收）。

## 验收

- 单测（`src/app/catalog/__tests__/pages.test.ts`）：裸串 = 显式 `+08:00` 的 ISO 串；日期串补零点；带 `Z` 串原样；空/非法 ⇒ `null`；展示日期取排期墙钟（`2026-11-02T21:30:00Z` ⇒ `2026.11.03`）；`mazeStatus` 在边界前后 1 小时翻转（fake timers 钉系统时间）。
- 生成器镜像实测：同一份产物在 `TZ=UTC` 与 `TZ=Asia/Shanghai` 下生成的排期串逐字相同。
- 既有 e2e：`e2e/layout-endgame-season.spec.ts` 的 Hero 状态文案用例（期望值由 `mazeStatus` 派生）保持不变、必须全绿。
