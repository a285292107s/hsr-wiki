# 0058. 终局敌方卡逐战斗阶段血量（`phase_hp` 数组 + 首处消费客户端实体配置）

## 状态

`accepted`（**已实现**：`monster_common.load_phase_hp_ratios` / `monster_hp_phases` + `endgame._monster_out`
落 `phase_hp` + `EnemyCard` 逐阶段行）。**扩充 [0055](0055-终局敌方卡显示关卡内血量.md)**：
`hp` 单值保持不动（= 阶段 1 的值），多阶段敌方另落一组逐阶段值。

**2026-10-27 补记**：§2 决策 6 的展示形态（「一阶段一行」逐阶段列血量 + 技能按阶段分组平铺）已被推翻——
多阶段敌方卡改为**卡内阶段切换**：名称行右侧分段控件，切换同时把左列血量与技能面板换到该阶段；单阶段卡不变。
数据键 `hp` / `phase_hp` / `phase_list` 与转换器零改动；`boss_guides` 的「阶段机制」文案**不并入**同一套切换
（结构 ≠ 文案，条目数与战斗阶段数不一定相等，见 [0044](0044-首领机制随敌方卡呈现.md) 的 2026-10-16 补记）。

## 1. 背景与问题

用户提问：「boss 每个阶段，是否都有各自的生命值？」核完数据后要求**补上**，
并把「/endgame/peak/9 的怪物卡片，左侧生命值显示」改成「阶段 1 / 血量 / 阶段 2 / 血量 / ……」。
用户进一步裁决**范围**：**全模式生效，凡 >1 阶段一律逐阶段列**。

### 1.1 事实（`query.py` / 实体配置直读，2026-10-16）

- `Config/ConfigCharacter/Monster/*_Config.json`（**客户端实体配置**层，由
  `MonsterTemplateConfig.JsonConfig` 指针落地）带 `MaxMonsterPhase` + `PhaseList[].PhaseNum /
  PhaseMaxHPRatio`。**该字段在 `ExcelOutput` 的 2,253 份表里零命中**——数值与文案层没有它，
  只有这一层有。
- 语义：`PhaseMaxHPRatio` = **该阶段最大生命 = 基准 × 比例**，**不是**「占总量份额」。
  两条判据：① 实测取值 > 1（解析后 159 个多阶段模板的比例里最高到 9 / 6 / 2.5 / 2；
  也有 0.5 / 0.6 / 0.7 / 0.75 这类小于 1 的）；② 同一模板里阶段 1 未声明、
  阶段 2 显式 `1`（模板 `2004021` / `2004022`）⇒ **未声明 ≡ 1**。
- 分布（**按转换器实际读的口径**：`MonsterTemplateConfig` 632 行，逐行按 `JsonConfig` 指针读到的
  实体配置；其中 5 条指针是死链、跳过）：带 `PhaseList` 的模板 **185** 个，跨 ≥2 阶段的 **159** 个、
  共 **402** 条阶段条目（未声明 331 / 动态表达式 70 / 静态字面量 1）；含该字段的实体配置文件 **44** 份。
  （旁证口径：整个 `ConfigCharacter/Monster` 目录 572 份非 layout 配置里 133 份多阶段、327 条条目——
  目录里的配置并非都被 `MonsterTemplateConfig` 引用，两个数不要混用。）
- 脚本层零消费（`Config/ConfigAbility/**` 里该字段 0 命中），引擎在切阶段时读取
  （`GlobalTaskListTemplate.Monster_ChangePhase` = `SetDynamicValueByProperty(ChangePhase_MaxHPValue ← MaxHP)`
  → `SetHP ModifyRatio=1` → `ResetStance` → `RefreshChangePhaseUI`）⇒ 站内**只做展示**，
  不推导战斗时序。
- 实测样本 904 王棋（`403501001` → 模板 `4035010` → `Monster_W4_IronTombCore_00_Config.json`）：
  **3 阶段，比例 1 / 1.25 / 1**。普关 `StageID 30509021`（Lv100 / 难度组 3）=
  12,395,969.9 / 15,494,962.3 / 12,395,969.9；绝境 `30509022`（Lv120）=
  49,583,878.5 / 61,979,848.1 / 49,583,878.5。站上现有单值恰是阶段 1。
- 阶段号连续性：185/185 个带 `PhaseList` 的模板 `PhaseNum` 恰为 `1..n`（159 个多阶段里
  101 个是 `(1,2)`、58 个是 `(1,2,3)`）⇒ 数组下标 +1 即阶段号。

## 2. 决策

1. **首处消费客户端实体配置层**：`PhaseMaxHPRatio` 只存在于 `Config/ConfigCharacter`。
   新增 `config.CHARACTER_CONFIG_DIR` 常量与 `monster_common.load_phase_hp_ratios()`，
   后者按 `MonsterTemplateConfig.JsonConfig` 指针逐模板读实体配置、取 `PhaseList` 的比例。
   这是本仓**第一处消费该层**的产物字段，故增量依赖按**目录级**登记
   （`incremental.MODULE_SOURCES["monster_common"]`）——单文件指针跑不出 AST 静态依赖
   （`test_incremental.py` 的守卫只认字面量路径的 `load_json` 调用）。
2. **取整只做一次、且在最外层**：合成链的未取整结果单点在新拆出的
   `_monster_hp_raw`（`monster_hp_at` 与 `monster_hp_phases` 共用）。阶段值 =
   `未取整基准 × 比例` 后**逐项**取一位小数；若在中间先取整再乘比例，末位会与直算值差 0.1
   （`0.25 × 1.5 = 0.375 → 0.4`，而 `round1(0.25) = 0.3 → 0.45 → 0.5`）。用例钉住这条。
3. **只落跨 ≥2 阶段的模板**：单阶段（473/632 个模板）与无该字段的模板**不落 `phase_hp`**——
   这 473 个模板覆盖了 10,006 处带 `hp` 的敌方条目，给它们各挂一个「只有一项、值与 `hp` 相同」
   的数组是纯冗余（实际落 `phase_hp` 的只有 499 处）。
4. **两条宁缺不假**（比例解析不出即**整条不落** + warning 留痕，绝不填半真数据）：
   - 动态表达式解析不出：`PostfixExpr.DynamicHashes[h]` → `DynamicValues.Floats[h].ReadInfo`
     （`Type: SkillParam`）→ 同模板 `MonsterConfig.SkillList` 里 `SkillTriggerKey` 匹配的技能的
     `ParamList[Index].Value`；`Type` 为 `ClientOnly` / `None`、或链上任一环缺位 ⇒ 该模板整条丢。
   - `PhaseNum` 不是 `1..n` 连续（有洞）⇒ 该模板整条丢：前端按下标 +1 出阶段号，有洞即错位。
5. **`hp` 与 `phase_hp` 并存**，语义各自成立：`hp` = 阶段 1 的值，`phase_hp` = 逐阶段。
   不删 `hp` 的理由：① 它是 0055 的既定契约，目录卡 / AI 快照 / 既有 e2e 都按它断言；
   ② 159 个多阶段模板里**只有 5 个**阶段 1 比例 ≠ 1（`4013016 [0.7,1]` / `4023011 [0.5,1]` /
   `4033011 [0.5,1]` / `4033021 [0.7,1]` / `4053011 [0.7,1]`），这 5 个在终局四份产物里
   都**不带 `hp`** ⇒ 现有 `hp` 值与阶段 1 值全量一致，删它只会制造无谓的契约变更。
   （若日后有模板被用到且阶段 1 比例 ≠ 1，前端的逐阶段优先规则仍保证显示正确——
   `hp` 只作退出码，不作展示值。）
6. **展示形态（用户裁决）**：`EnemyCard` 立绘下方的 HP 块改为**一阶段一行**「阶段 N + 数值」，
   行序即阶段序；标签复用 `mob.stage`（「阶段 {n}」，与技能分组的阶段号同键——读者不必学两套说法），
   不新开词典键（13 语言包零改动）。单值形态仍用 `catalog.sig.hp`（「HP」）。
   前端的取值判据收敛在一个 computed `hpRows`：**两键并存时逐阶段优先**，
   无 `phase_hp` 才退回 `hp` 单行；两键皆缺即整块不渲染（不显示 0）。
7. **不做数值二次加工**：比例是引擎内部量，站上只展示**结果值**——
   不上屏倍率、不显示「阶段 2 ×1.25」这类标注（官方界面也没有），也不把比例写进 payload。

## 3. 影响面

- `tools/converter/config.py`：新增 `CHARACTER_CONFIG_DIR`（实体配置层，目录级依赖）。
- `tools/converter/converters/monster_common.py`：`_monster_hp_raw`（未取整单点）、
  `monster_hp_phases`、`_phase_ratio_expr`、`load_phase_hp_ratios`（进程内缓存）+
  `_PHASE_HP_RATIOS`；模块 docstring 补该层的读法。
- `tools/converter/converters/endgame.py`：`_phase_ratios()` 入口；`_monster_out` 在
  `hp_ctx` 成立时另落 `phase_hp`（比例表按**模板 ID** 取，故用 `info["_tpl"] or mid`）。
- `tools/converter/incremental.py`：`monster_common` 登记 `CHARACTER_CONFIG_DIR`。
- 数据：`public/data/cn/maze{,_extra,_boss,_peak}.json` 的敌方条目按模板增 `phase_hp` 键；
  既有字段逐字不变（`hp` 不动、13 语言包不动）。
- 前端：`services/types/endgame.ts`（`MazeMonsterInfo.phase_hp`）、`components/EnemyCard.vue`
  （`hpRows` + 逐阶段行）、`styles/endgame-monsters.css`（HP 块改竖向列 + `--phases` 行内竖排）、
  `styles/endgame-type-scale.css`（新行沿用既有两档字号）。
- 测试：`pytest`（比例表解析 / `PhaseNum` 连续性 / 缓存 / 动态哈希链 / 取整只做一次 /
  `_monster_out` 按模板 ID 命中）、`e2e/layout-endgame-season.spec.ts`（peak/9 王棋 3 阶段逐行断言）。

## 替代方案（被否）

- **把 `hp` 换成数组（去掉单值）**：否——0055 的 `hp` 已进目录卡代表阵容、AI 快照与既有 e2e 契约；
  且轻形态（期级合并列表）没有等级语境、根本不落这两个键，替换只会让「有值 / 无值」两种形态
  各自多一次数组解包。
- **只落比例（`phase_hp_ratio`），逐阶段值由前端乘**：否——前端要拿到未取整的基准才能复算，
  而终局轻形态**不带**合成链输入（0055 决策 1）；透出链输入就是 0055 已否掉的方案。
- **单阶段敌方也落单元素数组**：否——单阶段敌方各挂一个与 `hp` 同值的数组是纯冗余
  （10,006 处带 `hp` 的条目里只有 499 处真的跨多阶段），
  且会让既有 e2e 的 `.nk-egd-mon__hp-label` 断言全部要改。
- **上屏倍率（「阶段 2 ×1.25」）**：否——官方界面只给绝对值；倍率是引擎内部量，
  展示它等于把「同一只怪的血量随阶段变化」解释成乘法题。
- **`PhaseNum` 有洞时按下标硬排**：否——阶段号会错位（第 3 段显示成「阶段 2」），
  而实测 185/185 都连续 ⇒ 这是零成本的保险，不是真实约束。
- **阶段 1 比例 ≠ 1 的 5 个模板也照落 `hp`**：否——那是 0055 的既有键，改它的值等于静默改口径；
  这 5 个模板在终局产物里都不带 `hp`，无需处理。

## 4. 后果

- 「终局敌方卡一个数就够」不再成立：**凡跨 ≥2 战斗阶段的敌方**，卡片左侧是逐阶段的数值列。
- **`Config/ConfigCharacter` 成为产物可消费层**：凡「`ExcelOutput` 里查不到的战斗/引擎态字段」
  都要先在这一层找一遍（此前只有「数值与文案在 `ExcelOutput`」这一条边界）。
  这类字段的增量依赖按目录登记，且**禁止**因此把整目录读进产物。
- `monster_hp_at` 与 `monster_hp_phases` 共用一个未取整函数：日后改合成链只需改 `_monster_hp_raw`，
  两个出口不会漂移（取整位置由用例钉住）。
- AI 快照沿用 0026 / 0050 / 0055 的「不同步」取舍（快照取期级合并列表，无等级语境）。
