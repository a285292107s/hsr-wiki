# 0057. 图片资源自持与 WebP 入库口径

## 状态

`accepted`（2026-10-16 完成）：口径决策 1–6 已定，并**已按 11 个批次执行完毕**——
`CDN_CATEGORIES` 的全部 **24 个分类**均声明 `local`，入库 **4,364 文件 / 245.48 MB**。
第 9–11 批（`avatarcutinfigures` 105 文件 / 17.18 MB、`lightconemaxfigures` 171 文件 / 32.03 MB、
`bgpic` 3 文件 / 0.38 MB）为**首页重构新增**：前两者是首页单条目分区的主图（需要比卡片图源
大一档的原图），后者是首页的**地面材料**（游戏自己的 Wiki 背景图）。第 9 批同时带来一条新的
入库形态：**裁剪式入库**（决策 3 附注）。本 ADR 同时是后续「新增分类 / 新版本补图」的**操作契约**。

## 1. 背景与问题

站点图片走「nanoka 主源 → jsDelivr 回退」双源（[0013](0013-cdn资源兜底架构.md)），回退源是自建 fork
`a285292107s/StarRailTextures`。该 fork **冻结在游戏 4.4**，而站点数据已是 4.6，于是：

- **4.5+ 新增图片两侧都取不到**，只能吃占位（`/voracity` 实测 17 处引用 / 9 个文件全部 404）。
- **nanoka 缺整个分类**（`bufficon`：扁平与各子路径全 404）、`trace` 分类是 **146 字节占位图**
  （不是真图标），`statusimmune` 同理。
- **jsDelivr 在大陆直连慢且会 burst 限流**（实测 1219 ms；限流下返回 503/429，会被误判成「真 404」）
  → 图片密集页破图。

同时本地有一份**比 fork 完整**的解包数据（含 fork 缺的 1512 / 1513），构成「资源自持」的动因。

**执行期新增的两条认知**（详见 §7）：

- 站点自己的死链自查枚举器 `collectUrls`（`src/app/debug/dead-links.ts`）存在**覆盖盲区**：
  它只枚举自己渲染的视图，`achievement` / `bufficon` / `avatarroundicon` / `tutorialpic` 不经它出现，
  且对**已本地化**分类只记录 nanoka 形态的 fallback（主源变本地后该文件的 nanoka URL 不再出现）。
  ⇒ 它不能单独充当「待入库清单」。
- 站点引用集里混有一批**在上游 CDN 上同样 404 的既有死链**，它们不是「待自持的资源」。

## 2. 决策（已定）

1. **目录**：本地图标入库到 `public/data/assets/icons/<分类>/…`。语言中立媒体**不在结构层内**
   ——`public/data/cn/` 是缺省语言的结构层（全令牌化数据），图标既不是令牌化数据、消费也不经取数层
   （走 `services/cdn/`）。见 [0052](0052-多语言站点架构-路径前缀与语言包.md) 修订注记。
2. **转码工具**：统一用 **PicList 的转码工具**转 WebP，且**必须显式设 `quality=82`**。
   PicList 缺省 `quality` 是 **100**（`getOutputQuality()` 在 `quality` 缺失/非法时返回 100）——
   不显式设置只能省 32%，而不是 83%。**这是本项目最容易踩的一步。**
   命令行等价物收口在 `tools/ingest-icons.py`（Pillow，逐字节等价），入库照该脚本执行。
3. **入库范围 = 站点实际引用的文件集**（**2026-10-16 修正**）。
   原表述为「一律 `localFiles` 白名单限定到具体文件、不整分类入库」；执行中发现：
   - 站点引用集由**站点自己的解析层**决定，逐条手写白名单既不可能穷尽、也会随上游漂移；
   - 分类级 `local`（不带 `localFiles`）天然就是「本地缺文件 → 回退远端」，白名单的唯一作用是
     **省掉本地 404 的往返**，而非安全边界。

   故修正为：**凡站点引用的文件一律入库**，`local` 不带白名单；仅两种情形保留 `localFiles`：
   ① 分类体量极大而站点只用极少数（`tutorialpic`：全量 1504 张 / 960 MB）；
   ② 分类内部分引用在解包/上游本就缺失，只能入库子集（`relicfigures`）。
    **附注 · 裁剪式入库**（第 9 批新增形态）：当原图的**画面主体只占画布一部分**时，直接转码会得到
    「一张大画布中间一个小人」——上版后，同一分区的各条板裁切比各不相同。此时允许在转码前**按 alpha
    包围盒裁掉透明边并补齐到指定比例**（`tools/ingest-icons.py --crop-alpha 4:5`）。判据：同一分区的
    各条板必须是**同一裁切比**；裁剪窗口中心 = 包围盒中心，越界平移回画布内，无随机量。实测取舍：
    `avatarcutinfigures` 包围盒只占画布 50%~100% 宽 / 47%~100% 高（比例 0.68~1.34），故裁 4:5；
    `lightconemaxfigures` 包围盒**等于整张画布**（100%×100%），故**不裁**（`--crop-alpha none`，
    与决策 4 的原始式子逐字节一致）。裁剪类分类的产物校验式相应前置一步 `crop`。

4. **转码参数的可复现校验**：产物等价于 **libwebp `quality=82` + 最高压缩努力档（`method=6`）**。
   机械校验法：Pillow `Image.open(src).convert('RGBA').save(dst, 'WEBP', quality=82, method=6)`
   可**逐字节复现**已入库文件（试点批 9/9）。
   注意：字节只锁 **libwebp 参数**、不锁 wrapper——同一组参数下 PicList 与 Pillow 产物一致，
   故该式用作「参数没走样」的回归哨兵，不作为「用的是哪个工具」的判据。
   全量执行时单进程约 **8 文件/分**（348×408 图约 7 s），故转码器须**多进程**（本机 12 逻辑核，
   开 10 路即可把 8 小时压到约 50 分钟）。
5. **入库必须配人眼核对**：图标字形是**纯白 + 透明底**，白底预览看不出内容，`naturalWidth > 0`
   也证明不了有内容 ⇒ 同批生成**深底大字联系表**核对后再入库（口径同 `docs/memory/spine.md`）。
6. **入库后必须跑「存在性校验」**（**执行期新增，源于一次真实事故**）：
   站点的 e2e 只断言 img 的 `src` **属性形态**，而回退切换发生在 error 事件之后 ⇒
   **文件落在错路径也能全绿通过**。故每批必须用真实注册表 + 真实解析层反推「站点会请求的本地路径」
   并逐一核对磁盘，另跑一次「驱动真实站点抓本地请求 HTTP 状态」的探针。

## 3. 实测约束（决策依据与执行结果）

| 事实 | 数值 | 口径 |
| --- | --- | --- |
| 本地解包规模 | **51,845 文件 / 11,835.8 MB**，全部 `.png`，最大单文件 7.6 MB，>20 MB 者 0 个 | 目录度量 |
| 站点引用集（可映射部分） | **约 4,000 文件 / 1,352 MB** | 批次转码实测累加 |
| WebP 体积**投影**（迁移前） | q82 ≈ **419 MB**（16.8%） | 按分类抽样外推 |
| WebP 体积**实测** | **195.90 MB**（PNG 1,352 MB 的 **14.5%**）——投影高估约 2 倍 | 入库目录度量 |
| 分类压缩率实测 | `rank` **9.1%**、`monsterfigure` **15.3%**、`avatardrawcard` **15.6%**、`lightconemediumicon` **20.5%**、`avatarroundicon` **21.5%**、`itemfigures` **22.0%**、`gridfight-asset` **48.1%**、`skillicons` **48.4%**、`bufficon` **48.9%** | 逐批实测 |
| 产物体积 | `dist` **156.94 MB → 352.32 MB** / 9,109 文件（`data/assets/` 195.90 MB）；`.git` 270 MB | 目录度量 |
| Vercel Hobby 限制 | CLI 静态上传 100 MB / 15,000 文件；**构建产物无硬上限**；本站走 **Git 集成部署，故上述 CLI 限制不适用** | 平台文档 |
| 仓库 `.vercelignore` 记录的更严限制 | `Request body too large. Limit: 10mb` | 仓库内既有记录 |
| 访问量 | 日均 ≤10 | 用户给出 |
| 外部源延迟（本机实测） | jsDelivr **1219 ms** > `raw.githubusercontent` 842 ms > nanoka **669 ms** | 探针 |

**注**：投影一行保留以记录偏差——原投影把「站点所需资源子集」估为 8,323 文件 / 2,488.3 MB，
实测可映射并入库的只有 1,352 MB，差额来自①早期按 nanoka **首段**归类把同一批文件重复计数、
②上游同样 404 的既有死链不构成可入库资源。**结论：涉及目录归类的估算不能按 URL 首段归类。**

## 4. 替代方案（被否）

| 被否方案 | 否决理由 |
| --- | --- |
| 用 Playwright 自带 Chromium 的 `canvas.toDataURL('image/webp')` 转码（`docs/memory/spine.md` 原记载） | **实测无法复现已入库产物**：同一组输入下 64×64 图标产物约大 1 倍（572 B → 1190 B）、教程图也不等；且质量参数 0.8–1.0 全网格无逐字节命中。该口径不再作为入库转码法（原记载已校正） |
| 用 PicList 的缺省质量（不显式设 `quality`） | 缺省是 100，只省 32% 而非 83% |
| 整分类入库（含上游根本不存在于站点引用集里的文件） | 无收益且制造全站本地 404；见决策 3——入库范围是**站点引用集**，不是分类目录全集 |
| 以 GitHub 图床作为**唯一**源、撤掉 nanoka | 大陆直连 1219 ms 且 burst 限流，比现状更差；现状已有双源回退，撤掉只会让单点故障面变大 |
| 按语言复制图片（随语言包一起切分） | 图片是**语言中立**资源，复制 13 份纯属浪费 |
| 只用 jsDelivr 的固定 commit 快照而不重建**自建** fork | 快照会冻结在更早的版本，解决不了「4.5+ 两侧都缺」的根因（[终局内容图标数据源审计](../audit/终局内容图标数据源审计.md)） |

## 5. 全量迁移范围（已裁决）

| | 路径 | 体积后果 | 主要风险 |
| --- | --- | --- | --- |
| **A** | GitHub 图床（新仓库 + PicList 转 WebP，经 jsDelivr / raw 引用） | 本站 0，图床仓库 +~419 MB | 大陆延迟最差且 burst 限流 → 破图（已记录在案） |
| **B** ✅ | 站点所需图片**全量本地化**（随站部署到 `public/data/assets/`） | `dist` 157 → **约 520 MB（实测 352 MB）** | 仓库膨胀、构建变慢、资源更新需重新入库；但**零外部依赖、无大陆问题** |
| **C** | 维持现状 + **按需补缺**（= `/voracity` 试点与既有小图标入库的路子） | 近乎 0 | fork 冻结在 4.4 → 4.5+ 资源持续缺；nanoka 无 `bufficon` 分类 |

**用户裁决：B（全量本地化）**，2026-10-16 起按 8 批执行完毕。判据是 B 严格覆盖 A 的收益并去掉
A 的全部风险，代价只是仓库体积；B 的原阻塞点（Vercel 带宽）因**日均 ≤10 访问**已作废。

## 6. 后果

- **已实现**：`dist/data/` 104.75 → 300.13 MB；本地优先成为**主路径**，双源回退退化为兜底，
  大陆破图问题从根上消失。`bufficon` 从「无任何源、只能落通用星形 SVG 占位」变为本地真图供给
  ——这是本次迁移**用户可见收益最大**的一处。
- **仓库与构建**：`.git` 涨到 270 MB；构建产物 352 MB。规模仍在 Hobby 的 Git 集成部署口径内。
- **更新时效**：入库是**构建期快照**，上游改图不会自动跟进；新版本新增图标由「本地缺失 → 回退远端」
  兜住，但上游**修正**既有图标（如 1503 占位贴图被修）需重新入库该文件。
- **converter 不参与**：`public/data/assets/**` 在「重跑产物 vs 已提交产物」对比里会恒定表现为
  「已提交有、本次未产出」，属已知伪差异。
- 无论选哪条，**决策 2、4、5、6 都要遵守**。

## 7. 落地清单与操作契约

**目录与解析**：`public/data/assets/icons/**`；`src/services/cdn/base.ts` 的 `LOCAL_ICONS_BASE` +
分类 `local` / `localFiles` 声明；**零 converter 改动**。

**入库三步**（后续补图照此执行）：

0. **工具**：`python tools/ingest-icons.py --category <分类> [--crop-alpha 4:5] [--jobs 10]`；
   人眼核对的深底联系表同批产出（`--sheet`），已入库目录可用 `--sheet-only` 重建。
1. **定清单**：用站点自己的解析层反推站点会请求的 `(分类, file)`，不要按 URL 首段归类
   ——`rank` 的 nanoka 路径是 `rank/_dependencies/textures`（**两段**）、`gridfight-*` 各分类也都是两段。
   本地目录 `spec.local` 与文件形态按**站点 URL**（`LOCAL_ICONS_BASE/<spec.local>/<file>`）组织，
   **不复制** nanoka 侧多出的目录段。
2. **转码**：PicList 显式 `quality=82`（等价 Pillow `q82/method=6`，多进程并行）；入库前跑
   深底联系表人眼核对。
3. **验证**（三件套，缺一不可）：
   - 存在性校验：按真实注册表 + 真实解析层反推本地路径并核对磁盘（**未匹配 0、缺失 0**）；
   - 站点探针：驱动真实站点抓 `/data/assets/icons/**` 的全部请求状态（**非 2xx 必须为 0**），
     且**路由覆盖度直接决定结论强度**——目录页不走访时只看得到个位数文件；
   - `pnpm build`（七守卫）+ `pnpm test` + 受影响 e2e。

**已登记的既有死链**（上游 CDN 上同样 404，**非本迁移引入、也无可入库内容**，本站行为与本迁移前
一致：本地 404 → 回退 nanoka → 仍 404 → 降级占位）。**待用户裁决是否单独处理**：

| 分类 | 数量 | 样例 | 疑似成因 |
| --- | --- | --- | --- |
| `itemfigures` | 356 | `01.webp` | 源数据 icon 尾号为 1–2 位数字，解包无对应文件 |
| `relicfigures` | 123 | `IconRelic_101_5.webp`、`_6` | 疑似 `SLOT_INDEX` 越界（解包只有 `_1`–`_4`） |
| `gridfight-equipment` | 33 | `23000.webp` | 光锥 id 落进了货币战争装备目录 |
| `skillicons` | 1 | `UltraItem_1506_00.webp` | 解包同名文件在 3 个不同子目录，无法唯一确定 |

**文档**：本 ADR；`docs/memory/spine.md` 的入库转码口径；[0052](0052-多语言站点架构-路径前缀与语言包.md)
修订注记（目录归属）；[../audit/终局内容图标数据源审计.md](../audit/终局内容图标数据源审计.md)（缺口盘点）。
