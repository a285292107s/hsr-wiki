# 0039. 角色拉丁转写名由转换器写入（TextMapEN × AvatarName）

## 状态

`accepted`（**已实现**：`converters/character_detail.py` 输出 `name_en`，解析器 `textmap.resolve_text_en` + 按需加载 `ensure_textmap_en`（`config.TEXTMAP_EN_FILE`）；`incremental.MODULE_SOURCES.character_detail` 补登该文本表；`public/data/cn/characters/*.json` 全量重跑（98 个文件，10 个开拓者形态留空）；前端 `CharacterData.name_en` + `CharHero.vue` 名称族消费，`src/app/views/CharacterView.vue` 骨架同步；e2e 三条新契约见「相关」）

## 背景

角色详情页 hero 排版迭代（用户给定标准：awwwards / Webby / FWA 级品质）选定「档案馆」语言下的**卷宗封面**结构：抬头（编号 · 阵营）→ 规格行（星级 / 属性 / 命途 / 强化）→ **名称族（中文主字 + 拉丁转写注音）** → 摘要。第三段要求一个此前站内不存在的展示事实——角色的拉丁转写名。取证结论：

1. **本地已转换数据没有角色英文名**：`characters.json`（`LocalCharList`）只有 `name` / `full_name`（中文），`full_name` 在实测中为空串；`CharListEntry`（含 `en`/`zh`/`ja`/`ko`）是**未被任何代码消费的类型预留**，其数据端点也不在 `public/data/cn/`。
2. **上游有权威来源**：`ExcelOutput/AvatarConfig.json` 的 `AvatarName` 是 TextMap Hash 引用，`TextMap/TextMapEN.json` 直查命中——`AvatarConfig` 94 条 + `AvatarConfigLD` 4 条已实装角色**全量零 miss**（1001 → `March 7th`、1204 → `Jing Yuan`、1503 → `Pearl`）。
3. **占位符形态**：开拓者 10 个形态（8001–8010）的 `AvatarName` 在**中英两张 TextMap 里都是 `{NICKNAME}`**（玩家命名），CN 侧现由 `clean_text` 替换为「开拓者」再拼命途名，EN 侧没有任何可用的等价物；`AvatarFullName` 的 Hash 在 TextMapEN 中不存在。
4. **排版需要的是「档位」而非「信息」**：注音是次级字阶（hud 字体 + 宽字距），用于把中文主字托起来，因此**空值必须不渲染**（渲染出「UNDEFINED」或退回中文都会破坏这一档）。

## 决策

**拉丁转写名作为数据字段由转换器写入，前端只读**：

1. **字段归属**：`name_en` 写在 `characters/{id}.json`（converter 侧 `converters/character_detail.py`）。前端**禁止**用 id→译名映射表、本地常量表或运行时拼造补齐——「所有展示文本必须来自现有数据源」的既有硬约束在此的直接推论。字符详情以外的消费面（目录卡、AI 快照）本轮不开。
2. **解析判据**：`AvatarName.Hash` → TextMapEN **直查**（`resolve_text_en`）——不做 `xxhash` 字面量回退、不走 `clean_text`（后者是中文标签清洗：`{NICKNAME}`→开拓者、`{SPACE}`→空格等，对译名只会造成污染）。
3. **加载与增量**：TextMapEN 55.9MB，**按需加载**（`ensure_textmap_en()` 由该模块调用，不随 `load_textmap()` 常驻）；同时登记进 `incremental.MODULE_SOURCES.character_detail`——否则英文文本表更新时模块不重跑、字段静默过期。
4. **占位符判据**：解析值以 `{` 开头 → 输出**空串**（上游未本地化，不是译名）。空串是合法值：`CharacterData.name_en` 可缺省，消费方按 `v-if` 不渲染；**禁止**回退成中文、禁止拼「Trailblazer · Destruction」这类自造译名。
5. **排版契约**：中文主字与注音构成**一个排版单元**——名称族内距（6px）必须小于 head 各行行距（手机/平板 12、桌面 16）；主字字号两侧大于注音（`<1024` 2rem / `≥1024` `clamp(2.4rem, 5.2vw, 4rem)`），注音为 hud 0.6875rem / 0.3em 字距 / `--text3`。

## 后果

**正面**

- 全量 94 个非开拓者角色一次拿到权威译名，零人工维护、零硬编码；新增角色随下次转换自动获得。
- 排版多出一条可断言的档位轴（主字 / 注音），且注音可数据派生化断言；拓荒者形态的「不渲染」也成为可断言契约（缺字段不给假值）。
- 字段归属清晰：转换器是唯一写入方，前端与 AI 快照只读，后续若列表端点也要用，直接复用同一解析器。

**负面**

- 10 个开拓者形态在 hero 上没有注音行，与其余角色视觉不一致（属上游缺口，非本决策引入；补它需要新数据来源，见替代方案）。
- 98 个详情 JSON 各增一个字段，随站数据体积略增（实测可忽略）。

**中性**

- `CharListEntry`（含 `en`）仍是未消费的类型预留——本轮不动，避免把一个未被使用的端点纳入范围；若日后启用，应与 `name_en` 口径统一。
- AI 预渲染快照不需要新契约：快照正文取自页面文本，注音行随 DOM 自然进入快照。

## 替代方案

| 方案 | 为何未采用 |
|---|---|
| 前端硬编码 id → 英文名映射表 | 违反「禁止在代码中写死或自建数据源」；98 条人工维护，新增角色必漏 |
| 从 `vendor/TurnBasedGameData` 手工导出英文名清单入库 | 绕过 `convert.py` 数据边界（AGENTS.md 数据边界），且清单会与源数据版本脱钩 |
| 开拓者用 EN 命途名拼出译名 | `{NICKNAME}` 不是译名；EN 命途名的来源也要另找，拼出来即编造 |
| 引入官方 wiki 的 `characters.json`（`en`/`ja`/`ko` 字段） | 该端点未入库、属新增外部数据源与新的数据同步面，收益（10 个形态的注音）不抵成本 |
| 只做字号势能、不做双语 | 「编号 + 中文 + 拉丁」的卷宗语言不成立，少一条排版轴，hero 仍是单行大字 |
| 由前端在运行时读取 `TextMapEN` 并解析 | 55.9MB 文本表进运行期，直接冲击首屏与部署体积；且违反「本地优先、构建期转换」架构 |
