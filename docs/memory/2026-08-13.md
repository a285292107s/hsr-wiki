## playwright 包导入坑位（pnpm 严格结构 + 重复踩坑）
- 触发：多次（含本会话）写一次性探针脚本时 `import { chromium } from 'playwright'` 报 ERR_MODULE_NOT_FOUND；曾误判为脚本放置路径问题（temp/ → 项目根都失败）。
- 根因：package.json 仅直接依赖 `@playwright/test`（无 playwright）；pnpm 严格 node_modules 只符号链接直接依赖到根，`playwright@1.62.1` 作为传递依赖仅存在于 `node_modules/.pnpm/playwright@1.62.1/` 隔离存储，根 node_modules 解析不到——与脚本位置无关。
- 解法（已验证）：脚本/探针统一 `import { chromium } from '@playwright/test'`——其入口 `export * from 'playwright/test'` 全量 re-export playwright API（chromium/firefox/request 实测可取）；与 e2e/helpers.ts、*.spec.ts 既有写法一致。禁止再写 `from 'playwright'`。
- 验证：node -e "require('@playwright/test')" 输出 chromium: object；dom-probe.mjs 改导入后一次运行成功。


## Vite 8 (rolldown-vite) dev 下 transform 缓存永久陈旧坑位（Windows 实证）
- 现象：改 CSS/TS 后 dev server 永远返回旧内容，重启 dev server 才恢复；「时有发生」非必现。
- 根因链（2026-08-13 探针实证）：
  ① rolldown-vite 8.1.5 无 chokidar 依赖（内联自研 watcher），Windows 下「文件被整写（O_TRUNC 重写，如工具保存/脚本写回）之后的紧邻变更事件」会被 watcher 吞掉（实测 writeFileSync→append 序列 0/3 丢失；append→append 全捕获）；
  ② Vite transform 缓存无 mtime 兜底——事件丢失 = 该文件 transform 结果永久陈旧，且不受后续无关请求影响；
  ③ 「.vue 新鲜 .css 陈旧」是假象：陈旧与否取决于该文件最后一次成功事件与磁盘修改的先后，与扩展名无关。
- 尝试过的自动方案（全部废弃，勿再尝试）：
  ① JS 周期失效 invalidateAll() —— 打不通 rolldown rust 内核缓存（响应仍旧），无效；
  ② watcher.emit('change') —— 绕开 rust watcher，无效；
  ③ utimes（仅改 mtime）—— rust 只认内容/size 变化，无效且自激（Windows 元数据精度导致写入后
     立即采样读旧值，基线漂移）；
  ④ 分轮「内容触碰」（append 换行→冷却→remove→刷新基线）—— 单实例验证有效（G1 3/3、快路径 3/3、
     自激归零），但多实例/多进程并发时 append+覆盖写竞争会破坏源文件（实测 compare.ts 被写成 787B
     空白壳，git checkout 恢复）——自动改源文件 = 不可接受的破坏风险，最终废弃。
- 最终防线（2026-08-14 定稿，均已落地）：
  ① vite.config.ts server.watch.usePolling(300ms) + ignored 追加 public/data（2953 文件不走
     transform 缓存，防轮询开销）——唯一官方配置答案，降低事件丢失率（注意：不根除，事件被
     软失效吸收型 usePolling 无效，实测）；
  ② 手动自愈工具 tools/refresh-vite-cache.mjs —— 「读回→写回×2」触发必达事件（手动按需、先保存
     再运行；人工可控，远低于自动方案风险）；
  ③ 排查顺序：curl 对比磁盘特征串 → 自愈工具 → 重启 dev server。
- vite 8.1.5 的 configureServer 返回值会被立即调用（close 钩子语义失效），dev 插件清理必须挂
  server.httpServer.on('close')——实测记录，供未来 dev 插件参考。
- 上游动态（2026-08-14 检索）：无官方成熟方案直接命中本问题；vite 8 bundled-dev 架构的
  reload/HMR 链路仍在活跃修复（vitejs/vite #23194 refresh-after-edit、#23097 settle harness、
  #22883 client-side HMR 已入 8.2）。升级 vite 8.2+ 后重测问题是否减少；若官方修复彻底，
  自愈工具可退役。
- build 不受影响（2026-08-15 结论）：vite build 是独立进程、同步全量读磁盘，无 watcher 事件链路，
  也无跨进程源码级增量缓存（node_modules/.vite 持久化缓存仅服务 dev 依赖预构建），产物必然反映
  磁盘内容——可反当「磁盘内容是否已更新」的诊断手段：dev 显示旧内容时跑 build，产物新 = 磁盘
  已更新（走 ② 自愈），产物也旧 = 文件未落盘/未保存。未来若 rolldown 引入构建增量缓存，其失效
  机制为内容 hash 寻址（内容变 hash 必变），与 dev 事件驱动失效本质不同，同样无此风险。注意 build
  只能当诊断/验收手段，不能替代 ② 自愈——它验证「磁盘→产物」链路，dev 进程 transform 缓存依旧陈旧。
- 教训：dev 工具链自动修改 src 源文件是不可接受的（并发写竞争损坏文件）；任何「触碰」类方案
  必须设计成手动、按需、单实例执行（tools/refresh-vite-cache.mjs 已是此形态）。
- 行为约束：dev 下怀疑「改了不生效」时禁止直接重启分析——先跑 ② 自愈，仍不生效再重启；排查顺序 ③→②→重启。
  build 进行中禁止运行 ②（refresh-vite-cache.mjs 会写回源文件，与 build 读取并发时写竞争破坏文件）。
