# 终局玩法详情页与赛季增益体系名

**Status**: Accepted（已实现）

## Context

四个终局玩法（忘却之庭 / 虚构叙事 / 末日幻影 / 异相仲裁）此前在站内只有**赛季级**页面，玩法本身的官方规则正文无处安放，且站点长期把每期增益统称「**赛季增益**」——而该词**不是游戏内词**（TextMap 命中 0）。

- 官方规则正文在 `IntroData.json`（231 条，字段 `ID/Title/Desc/Desc_Os`），但**未登记在 `tools/converter/incremental.py` 的 `MODULE_SOURCES`**，站点零消费。
- 游戏内每套增益体系各有其名，出处是官方正文的**分节标题**：忘却之庭 = 记忆紊流（IntroData 2；同文副本 44）、虚构叙事 = 荒腔走板（115）、末日幻影 = 终焉公理（93）、异相仲裁 = 裁决象限（167）。四个名字都能在对应 `Desc` 的 `◆…◆` 分节里逐字命中。
- 选择语义也不同：忘却之庭 1 条固定；虚构叙事每支队伍选 1；末日幻影每场战斗选 1；异相仲裁王棋挑战前选 1。
- `/endgame/{mode}` 四条路由此前 302 到目录页，玩法级路由被占。

数据事实（实测）：maze 57 组（55 有增益 / 2 常驻组无）；story 27 季各 3 条（10 季无 `sub_buffs`）；boss 22 季 stage1/stage2 恒各 3 条（5 季另有 tierce），扁平 `buffs` 是 1∪2 并集（20 季 6 条、2 季 5 条）；peak 10 季各 3 条（源字段在王棋扩展表 `ChallengePeakBossConfig.BuffList`，不在 `ChallengePeakConfig`）。

## Decision

1. **新增第四种页面形态「单页数据页」**：`/endgame/{mode}`（正则白名单 `(maze|story|boss|peak)`，`meta.depth = 3`；赛季页 `depth` 3 → 4）。含 h1 + 面包屑 + 规则分节 + 结构口径 + 增益体系 + 赛季列表 + 其它玩法内链；**不使用 `nk-snapshot__entry`**、**无条目级覆盖率断言**。
2. **新产物 `endgame_guide.json`**：`{ modes: { <key>: { key, label, en, intro_id, sections[{title,text}], system{name,count,choice} } } }`。正文**逐字**来自 `IntroData`（不改写、不润色）；`sections` 按 `◆…◆` 标记切分。
3. **体系名数据派生、不写死展示文本**：转换器只登记「哪个 `IntroData` / 哪一节是增益体系」这类判据常量（`INTRO_ID` / `_BUFF_SYSTEM` / `_CHOICE`），取值必须在该模式 `sections` 的标题里命中，未命中则告警且不落 `system`（宁可缺，不自造）；`label` 由首个分节标题派生；`en` 无数据源，取常量并由测试与前端 `ENDGAME_MODES` 对齐。
4. **`count` 口径**：各模式判据字段长度的众数（只统计非空项）——maze 单值计 1、story `BuffList`、boss `BuffList1`、peak 王棋表 `BuffList`。**禁止**用 boss 扁平 `buffs` 表达「3 选 1」。
5. **体系名上屏**：赛季页的区块/看板标签改用体系名（`FALLBACK_SYSTEM_NAME = '赛季增益'` 只在产物缺省时回退，一处开关即可全站退回）；玩法页的「当期增益」只出**名称与图标**（不出 `desc`，避免 AI 快照出现未展开的 `#N[i]` 占位符）。
6. **AI 快照三件套同步**：生成器 + `check-ai-endpoints` 的 `singleFamilies` + `vercel.json` 四条 rewrite + 契约文档；少一处 `pnpm build` 末步即红。

## Alternatives considered

- **只正名、不加玩法页**：改动最小，但官方规则正文仍然无处安放（P3 未解决），且结构口径没有承载位。
- **只做增益图鉴（按体系名聚合四个体系的全部增益）**：与「玩法说明」是两件事，且 216 个 ID 去重后仍要按玩法分组，信息架构更绕。
- **玩法页并入赛季页锚点**：赛季页已有 6 个区块，再塞规则正文会让「当期赛季」与「玩法常青规则」两种时钟混在一屏。
- **把体系名写死在前端常量表**：最省事，但违反「展示文本必须来自数据源」，且上游改名时站点不会自己发现。

## Consequences

- **好处**：玩法级内容有了稳定归属；四个体系名与选法上屏；单页数据页形态可被后续「玩法/专题」类页面复用。
- **负面清单**：
  1. 4 条新可索引路由的长期维护成本（快照 / sitemap / rewrite 三处同步，由守卫兜底）；
  2. 规则正文随版本漂移，需重跑转换器（`python convert.py --only endgame_guide --force`）；
  3. 玩法页的「结构口径」取**当期赛季**，是时钟性数据（层数历史上变过），页面上显式标注「以当期赛季为准」，**禁止**改用多季众数；
  4. `en` 常量与前端 `ENDGAME_MODES` 存在同源同写的两份（测试锁相等），改名需同时改两处。

## 验收

- `cd tools/converter && python -m pytest tests -q` 全绿（`test_endgame_guide.py` 锁判据常量与产物结构）。
- `pnpm build` 末步 AI 端点守卫 7/7（快照含 4 个玩法页；`/endgame/xyz` 仍 404）。
- `e2e/layout-endgame.spec.ts` 含 4 条玩法页用例（h1 = 玩法名、规则分节数 = 产物、体系名上屏、当期增益无 `#N` 占位、赛季内链 ≥3、无 `nk-snapshot__entry`）与 `/endgame/xyz` 404 用例。
