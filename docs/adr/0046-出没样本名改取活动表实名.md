# 0046. 出没样本名改取活动表实名（`StageConfig.StageName` 的活动级常量不可作关卡名）

## 状态

`accepted`（**已实现**：`tools/converter/converters/monster_extra.py` 新增
`load_activity_stage_names()`（6 条实名链）与 `load_appearances()` 的两级名称来源；
`public/data/cn/monsters/*.json` 全量重生成（821 个文件变化）；`pytest` 新增
`TestActivityStageNames` 5 例；`e2e/layout-monster.spec.ts` 增「样本名逐项等于数据」与
`1004015` 回归哨。**决策 1 / 2 / 3 被 [0047](0047-出没样本只展示玩家可见关卡名.md) 修订**：
活动 6 链仍是①档实名源，但样本名不再退回 `StageConfig.StageName`——只有玩家可见关卡名才上屏，
无名的关卡只进 `total`；决策 4 / 5 继续有效）

## 1. 背景与问题

用户问：「`/monster/1004015`（托帕幻象）为什么在『出没关卡』里有一个『承露天人』的徽章？」

溯源：徽章 = `appearances.samples[].name`，该值取自 `StageConfig.StageName`。

- 托帕幻象确实出现于 **14 关**，全在 `StageType = FightFest`（星天演武仪典）：
  `4190010~4190016`（擂台赛•其一，等级 20–85）与 `4192010~4192016`（梦境训练•托帕），
  两族都在波次里**直接**列了 `1004015` / `100401501`（与召唤链无关）；
- 但 **FightFest 的 134 个关卡共用同一个 `StageName` 文本**「承露天人」（同一个 hash
  `7086853316639384589`），而「承露天人」是**同一活动里的另一只敌人**（模板 `2023030`，
  出现在 `4191050~4191056`）。样本按「同一 `StageType` 只取一条」去重后，14 关就塌缩成这
  一个与关内名单无关的徽章。

**这不是孤例，是整类形态**：`StageConfig` 33 种 `StageType` 里有 10 种的非空 `StageName`
**在整个类型内只有一个取值**（FightFest 134 关 / TelevisionActivity 70 / ElationActivity 49 /
SummonActivity 70 / GridFightActivity 84 / FightActivity 308 / TreasureDungeon 427 / FateRin 43 /
FateActivity 8 / BattleCollege 35），其中逐关核对关卡名单后**9/10 的标签与该关名单 0 命中**
（「裂界造物」「反物质军团」是阵营名；FightFest 只是 7/134 巧合命中）。另有 StarFightActivity
（210 关，`StageName` 只有「承露天人」与空串两个取值）与 BoxingClub（847 关，只有 2 个取值、
826 关与名单无关）这两种「非严格常量但同样是占位名」的形态。

## 2. 判定

**是本站的口径缺陷**：`StageConfig.StageName` 在这些类型里不是「关卡名」，而是活动级占位/阵营名，
把它当关卡名展示必然误导——用户看到的是「托帕幻象出现在一个叫承露天人的关卡里」。

## 3. 决策

1. **有实名源的活动类型：只用实名源，不回退**。真实关卡名在这些活动表里，各链均按
   `EventID = StageID // 10` 折算，并退回原值再查一次（覆盖 FightFest `419000` 这类
   「关卡号 = 活动号」的单关特例）：
   | StageType | 实名链 | 覆盖（实测） |
   | --- | --- | --- |
   | FightFest | `FightFestStageInfo.ChallengeName` | 134/134 |
   | ElationActivity | `ElationBattleLevel.StageName` | 49/49 |
   | TelevisionActivity | `ActivityTelevisionLevel.EventID → TelevisionID` → `ActivityTelevisionStage.StageName` | 70/70 |
   | SummonActivity | `ActivitySummonLevel.EventID → GroupID` → `ActivitySummonGroup.StageName` | 70/70 |
   | BoxingClub | `BoxingClubStage.Name` | 679/847（97/121 个活动号有行） |
   | StarFightActivity | `StarFightStageConfig.EventID → GroupID` → `ActivityStarFightGroup.GroupTitle` | 210/210 |
   **查不到就是不落样本**（`named.get(...)` 为空即不收）；缺表同理（字典恒含这 6 个键，避免退回常量名）。
2. **无实名源、且 `StageName` 在整个 `StageType` 内只有一个取值（关卡数 > 1）→ 不落样本**。
   `total` 照计，页面只显示「共出现在 N 个关卡」+ 活动出处备注。单关卡类型（>1 的守卫之外）
   保留其名称：只有一个关卡时该字段不构成误导。
3. **其余类型照旧用 `StageConfig.StageName`**（源字段保真）：那些类型的 `StageName` 逐关变化
   （Mainline 20075 关 / 71 个取值，Challenge 1695 / 95，Trial 169 / 56 …），是关卡显示名。
4. **刻意不做的三件事**：① 不设「标签覆盖率/占比阈值」——阈值即自造判据（与 2026-10 第 57 轮
   否掉高抗性阈值的同一条纪律）；② 不用「标签必须 ∈ 本关波次名单的敌方名」这条看似更准的判据——
   它会误杀官方式名号（实测 Challenge 的「蛮神，疯王，纷争的化身」、Cocoon 的「「灯塔」」都不等于
   任何敌方名）；③ 不落 `StageType` 的中文枚举（全仓无该枚举文本源，承第 57 轮裁决）。
5. `total` 口径不变（关卡波次 + 召唤链、不含无限波次随机编组池）；AI 快照仍逐字读该块。

## 4. 影响面

- `tools/converter/converters/monster_extra.py`：`_load_table` / `_join_names` /
  `load_activity_stage_names` 新增；`load_appearances` 增名称两级来源与整类常量判定。
- 数据：`public/data/cn/monsters/*.json` 重生成，**821 个文件变化**（626 个换成实名、
  192 个样本整组消失、3 个换了来源关卡但同名）。
- 测试：`pytest tools/converter/tests/test_monster_extra.py`（六条链索引、实名优先于常量名、
  无实名不回退、整类常量不落样本、缺表只掉一条链）；`e2e/layout-monster.spec.ts`
  （样本 chip 数与名字逐项等于数据；`1004015` 的样本名不得再是「承露天人」）。
- 文档：`docs/data/转换器字段映射.md` 的 monster_extra「出没」条目。

## 5. 后果

- 活动关卡的徽章从「活动级常量/阵营名」变成真实关卡名（如「擂台赛•其一」「与银袋山同行」
  「「很多鸽子」」「破敌先锋」），`1004015` 的样本名由「承露天人」变为「擂台赛•其一」。
- 样本数**只会减少或换名**，不会新增：`load_appearances` 的「同一 `StageType` 只取一条」去重未变
  ——因此 `1004015` 只显示 1 个徽章（`4190010`），它的另一族「梦境训练•托帕」不上屏。要同类型多族
  并列需另开一条决策（改去重口径），本轮不动。
- **已知边界（记录备查）**：无实名源的活动类型（FightActivity / TreasureDungeon / GridFightActivity /
  FateRin / FateActivity / BattleCollege / Heliobus / AetherDivide）不再出样本；而 Mainline / Trial /
  VerseSimulation 等逐关变化的类型里，**仍会有阵营/敌群名上屏**（如「反物质军团」「裂界造物」），
  判据上无法与官方式名号区分（见决策 4），保持源字段保真。
