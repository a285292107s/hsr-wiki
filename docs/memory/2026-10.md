## 「贪饕」污染色：机制语境色进令牌体系（ADR 0027）——**取证推翻了口述色相**

- **用户原话**：「讨论一下颜色的问题。贪饕污染，游戏内有专门的主题颜色，是代表不详的猩红色」。
- **事实核查（决定了整轮边界）**：① 站内**没有任何机制专属色**——`/voracity` 全页（吸顶进度条、secnav 激活项、卡底纹与边框、数值强调位）加怪物详情「受『贪饕』侵蚀」标记、终局污染徽标、目录卡「含污染」标记**全部消费 `--primary`**，即读感等于用户当前强调色（缺省赤陶）；② 数据里**没有权威色值**——教程富文本强调色是全局琥珀 `<color=#f29e38ff>`（且与 `--elem-fire #FF6B35` 几乎同色相），侵蚀 buff 图标是通用 `IconBuffShield`，颜色是这套机制唯一能承载身份的表达；③ 素材取证（子代理，HSV 过滤 `V<0.15/V>0.9/S<0.25` + k-means + WCAG 对比度）得到**红徽记 + 洋红能量并存**：徽记 `#DF3D3D`/`#FF4242`、洋红能量 `#C40C6A`（官方 4.6 公告 KV 内 top1 簇 22.2%）、受污染敌人血条 `#FC48AC`、徽记暗部 `#66030C`。
- **最重要的教训**：**「游戏内有专门的主题颜色」这类需求，用户口述的色相不能照抄**——它可能是记忆里最抓眼的一小块（红色徽记），而画面主体与官方宣发的主体其实是另一支（洋红能量）。取证与口述不一致时必须**当场指出**并把选择交回用户（Q8 卡片），照抄会让页面读成「另一个模式色」的近亲。第二条同源教训：**污染标记恰恰渲染在按模式着色的终局页里**，所以选色的第一道验收是「与 `--eg-boss` 玫瑰红 `#FB7185` 分不分得开」，而不是只看单页观感——纯红族正是因此落选（同色相族、红上加红）。
- **9 项决策走卡片收敛**（Q1–Q9）：新领域语义族 + 页面语境色（一份色值两处身份）/ 从游戏素材取样推导 / 覆盖四个面（`/voracity` 数据元素、怪物详情标记、终局徽标与赛季级区块、目录卡标记）/ 分两档（基准位 + 文字亮端 ≥4.5:1）/ `/voracity` 只染数据面 + 结构强调位（不动 hero 与页面底色）/ 登记为「语境色」类别并补登既有 `--eg-*` / 新增 ADR / 本轮文档 + 实现。
- **交付**：`tokens.css` 领域层新增污染族 `--vor-500: #C40C6A`（基准位，仅非文字）+ `--vor-300: #FC48AC`（文字亮端，进 `check-contrast.mjs` 正文类清单）；`voracity.css` 全页 22 处强调位改走污染族（含新增 secnav 激活项与章节序号覆盖）；`endgame.css` 目录卡「含污染」标记、`endgame-detail.css` 污染徽标与赛季区块回链、`monster-detail.css` 侵蚀标记同批从 `--eg-color` / `--primary` / `--metric-val` 摘下。落盘 [ADR 0027](../adr/0027-机制语境色与贪饕污染色.md) + [ADR 索引](../adr/README.md) + `ui-design.md` §2/§3/§5/§9 + `CONTEXT.md` 两条术语（语境色 / 污染色）。

## 末日幻影详情页：赛季增益分场 + 首领特性（ADR 0029）

- **用户原话**：「末日幻影详情页修正，赛季增益6个，是上半场3个，下半场3个。关卡效果没有展示，例如：坚防守备 首领幻影受到的伤害降低50%。弱点击破后，行动额外延后，受到的伤害提高100%。」（附对照站 `hsr.nanoka.cc/boss/3020`）
- **取证先行**：用 kimi-webbridge 打开对照站读**渲染后文本**取得逐条真值（难度 01/04 的节点 1/2 + 星启模式各带「赛季效果 3 条 + 关卡效果 4 条」），据此确认两件事：① 赛季增益按场次下发（`ChallengeBossGroupExtra.BuffList1/2/3` = 上半场/下半场/星启模式，各 3 条，扁平 6 条口径不变）；② 对照站的「关卡效果」= `MonsterGuideConfig × MonsterGuideTag`（`TagList` → 名称 + 简述 + `ParameterList`），站点完全没有消费这两张表。
- **join 判据（易错点）**：机制按**敌方模板**登记（`MonsterID // 100`），但**配置表的敌方 ID 未必等于战斗敌方**——业火焚心的影将军战斗模板 `2035012`，配置表登记的是蚀心兽 `2033022`（同图标 `Monster_2033020`、同机制组 1012xx），直接按模板 join 会让天狼系赛季下半场整场漏机制。补法是 `MonsterGuideTag.SkillID // 100` **唯一**反查（技能 ID = 模板 ×100 + 技能序号），并加唯一性闸门——技能 ID 会被多个首领共享（`100401410`），不唯一即放弃。21 个已发布赛季 × 上下半场覆盖率全绿（「杰帕德」一类未登记机制的护卫不产出条目，正确）。
- **术语同名不同指（用户当场改判）**：游戏内教程（TextMap `7039255158974959772`）把每期的「末法余烬」称**关卡效果**、把随难度追加的首领机制称**首领特性**（`12677071358133122013` 同义）；对照站把后者也标成「关卡效果」。先按用户原话与对照站口径落地，用户随后裁决「采用官方术语，就叫首领特性吧」→ 区块名、数据字段（`level_effects → boss_traits`）、类型（`MazeLevelEffect → MazeBossTrait`）、渲染函数与 CSS 类（`.nk-egd-effect* → .nk-egd-trait*`）、section id（`effects → traits`）同批改名，`CONTEXT.md` 词条与 ADR 标题一并换；站点内**不再**用「关卡效果」指本词条。楼层内的「可用增益」（末法余烬）仍未改名，留在 ADR 替代方案表里记账。教训：**代码/字段/CSS 名跟着术语走，别只改标题**——否则下一轮读代码的人会以为是两套东西。同批用教程文本校正了 `CONTEXT.md` 的末日幻影词条：两场战斗游戏内文案作「节点一/节点二」，源表 `EventIDList1/2` + `BuffList1/2` 与忘却之庭/虚构叙事同构；`ChallengeBossMazeExtra` 逐项对应节点（与 `tierce.nodes` 同源），不是「首领形态」。
- **坑位（自检截图时发现，属通用教训）**：**新增一层 flex 包装 = 改变了子元素的尺寸解析**。`display:flex; flex-direction:column` 里，子项若带 `margin-left/right:auto` 就**不满足 stretch 条件**，`max-width` 直接退化成 shrink-to-fit——`赛季增益` 卡片瞬间从 952px 变成按内容收缩且**各组宽度不一**（实测 692/684/692 与 839/549/839）。修法是给列表显式 `width:100%`（块级父容器下原本靠 stretch 生效，加 wrapper 后失效）。教训：**加包装层后必须量一次几何（left/width 各分组对比），别只看「有没有内容」**。
- **取证陷阱复现**：kimi-webbridge 的**元素截图在后台标签页全黑**（同页实测 `visibilityState=hidden`、`getAnimations().length=0`、卡片 `opacity=1`），不是页面缺陷；改用 Playwright（前台）元素截图才拿到有效画面。

- **降级/未做**：① **AI 快照本轮不同步**（沿 ADR 0026 取舍：要进 catalog + 生成器 + 守卫三处），记账在 ADR 0029 中性条；② `visual.spec` 未跑（无基线变更需求，AGENTS 禁全量）；③ 未跑全量 `layout.spec`（只跑受影响用例：endgame 组 + a11y）；④ 视觉观感（效果卡左侧模式色竖条与分组胶囊）交用户 RunPreview；⑤ 场次标签用用户口径「上半场/下半场」，与游戏内「节点一/节点二」并存，如需改为官方文案是一处常量 + 一处 e2e 断言。

## 星启头部推荐属性是什么 → 节点 3 补上自己的推荐属性（ADR 0032 修订）

### 追加一轮：节点子切换改「三张并列卡片」（ADR 0033 决策 10）

### 再追加一轮：手机断点卡内上下排版（ADR 0033 决策 10 修订）

- **用户原话**：「手机断点下，单个卡片内容改成上下排版，图在上方，其他信息在下方，尽量一行能够显示。」——上一轮我把手机端做成「78% 卡宽 + 横向滚动」，用户看完直接改成「卡内上下排版 + 一行全见」。**「保一行」有两种解法（横滚 / 压缩排版），在卡片这种信息块上用户要的是后者**；横滚适合放到表格与长卡列表（既有 `.nk-hub-release__band` 那种），不适合「三选一」的切换控件——切换控件必须全部可见，否则失去「一眼对比」的意义。
- **压缩的算法先算再写**：手机 375px 内容宽 343、三卡两 gap(8) → 卡 109、内宽 97px。再算最密的一张卡：4 枚 14px 元素图标 + 3×3px gap = 65px ✓；「推荐属性」4 字标签在 0.68rem ≈ 43px ✓——**但「标签 + 4 图标同行」= 43+4+65 = 112px > 97px，放不下**，所以手机端这条 row 必须改列方向（标签一行、图标居中下移）。桌面端内宽 277px 则完全放得下，无需改动。**先算 min-content 再决定哪几行要换轴，比写完再试省一轮**。
- **验收写成可判定式**：`rowScroll ≤ 1`（行不横滚）+ `cardsSpill ≤ 1`（卡内不溢出）+ `lastRight ≤ 1`（末卡不出行右边界）+ 卡内 `flex-direction: column` 且 `fig.bottom ≤ body.top`；再用 `el.children` 的 `y` 去重证明三卡同一行。320 / 375 / 412px 三档实测均为 0 溢出，320px 卡宽 91px 是硬边界（已写进 ADR 负面条）。
- **新增专门用例而不是塞进既有用例**：`/endgame/boss/3020：节点卡片窄屏（375px）一行三卡 + 卡内上下排版`（`@viewport-pinned`，只跑 chromium；3020 节点一是全站最密的卡——4 枚元素图标）。原本想塞进 `/endgame/maze/1036` 手机用例，但那里只覆盖 2 图标，且与该用例「父子层级刻度」的主题无关——**窄屏密度验收要挑数据最密的那一页**。
- **验证**：`e2e/layout.spec.ts --grep endgame` **17 passed**（16 + 新增窄屏用例）；`vue-tsc -b --force` 0；colors/contrast 双绿；`e2e/accessibility.spec.ts` 8 passed；`pnpm test` 349 passed；`pnpm build` exit 0（AI 端点守卫 7/7）；`check-doc-links` PASS。几何：桌面卡 309×98；手机 375 卡 109×144、320 卡 91px、412 卡 121px，三档 `rowScroll/spill/lastRight` 全 0。

> **本节第 3 条（横向滚动）已作废**：最终形态是「卡内上下排版 + 三卡等分一屏宽、不横滚」（用户在下一轮明确要求，见下节）。上一条实测数据仍有效，只是 `.nk-egd-nodecards` 的 `overflow-x: auto` / `scroll-snap` / 78% 卡宽已从代码里删除。

## 终局节点详情面板：字阶 / 区块节奏 / 去胶囊（ADR 0034）

- **用户原话**：「迭代末日幻影，星启模式，每个节点的详情面板，要求反 AI 味，信息层级清晰，字体大小和元素间距合理。」——三条要求里两条半（层级 / 字号 / 间距）是**能量化的**，所以先取证再动手：一次 `page.evaluate` 把面板内 18 个元素的计算字号 / 字重 / 颜色 / 圆角 / 内距 / 盒高全量取回，问题就自己浮出来了。

## UI 重构期降本四包（文档分级 / e2e 三层 / 漂移工具 / 并行实测）

- **提速类配置的验收线是「零新增失败」，不是「更快」**：本地 4 worker 全量比串行快约两成，但三次全量里出现一次并发竞态 flake（同一用例串行复跑与单独复跑均绿）→ `fullyParallel` 保持 `false`。用 `--retries` 把 flake 抹平等于把风险转移到未来某一轮，属禁止手法。
- **守卫噪声本身就是 churn 来源**：e2e 裸 px 扫描器首版把注释 / 用例标题 / 视口里的 px 一起计数（报 63 处，断言位真值 17），等于逼人「改注释或加豁免去凑绿」。判据：可机检守卫**先划断言位，再谈阈值**；基线是兜底，行内豁免才是收口。
- **同一事实的第二处副本就是下一轮返工**：字号绝对值断言改「档位相对序」，首领名 / 污染等级 / 目标分数改从 `public/data/cn/**.json` 派生（沿用 `charFamilyIds` 模式）——UI 迭代时断言不再随之改。

## 光锥 hero 的「圆角矩形环 + 竖条纹」= 8bit 等值线（无 ADR，可逆展示迭代）

- **用户原话**：「光锥图片背景有很浅的，一圈一圈的圆角矩形印记，右侧的信息栏有一条条很浅的竖立的条纹……将它们移除。」
- **先排除颗粒层**：`#app::after` 的 feTurbulence 颗粒（`--grain-opacity: 0.08`）是第一嫌疑人，实测**排除**——面板列向噪声 SD 在开/关颗粒下几乎不变（1.98 vs 1.97），视觉区环在关颗粒后反而更清楚。延续 2026-09 的同一判据：**颗粒是高频噪声，掩不住低频等值线**，不能指望它去抖色带。
- **两个独立成因，都是「整幅色差 < ~8/255 的浅渐变/暗角」**：① **环** = `.nk-hero--lc .nk-hero__visual` 的两层 inset 暗角（实测中心 16.7 → 边缘 13.0，3.7/255 摊在 ~200px）+ `::before` 稀有度椭圆晕染（22.7 → 18.7，4/255 铺满全幅）；② **竖条纹** = 基线 `.nk-hero__panel` 的 `linear-gradient(90deg, transparent → blk-900 60% → 92%)`，整幅只跨 8/255 却铺 660px，塌成 7~8 条竖直色带（无文字区列向 SD 1.97 / 行向 0.12，**列行比 ≈ 16** 是「竖条纹」的定量指纹）。
- **通用判据**：**深底上「整幅色差 < ~8/255」的渐变/暗角必然产生 8bit 色带**——出路只有三条：把对比拉到 10 级以上、删掉、或换成纯色。
- **易错点（本轮踩到）**：**「删掉页面级覆写」≠「取消」**——光锥的暗角是**覆写**基线两层更重的 inset（85% / 50%），删整条规则会回落到更重的暗角；必须显式 `box-shadow: none` / `background: none`（`::before` 同理：删掉会回落基线的左右渐隐）。
- **度量手法（比肉眼可靠，可复用）**：① DPR2 截图后把 `[lo,hi]` 拉到 `[0,255]` 拉伸才看得见结构；② **列/行噪声相干性**：面板取无文字区算列均值 SD 与行均值 SD，竖条纹必然 colSD ≫ rowSD；③ 竖向剖面打印看是否 flat（改前 12.3→14.0 缓坡，改后恒 18.7）；④ 真改动后与注入实验态截图 **sha256 逐字节相同**（本轮 `D6FBF3A5…`）——沿用 2026-09 的标准证据法。
- **落法**：`lightcone.css` 三处收口——视觉区 `box-shadow: none`、`::before { background: none }`、`.nk-hero--lc .nk-hero__panel { background: color-mix(in srgb, var(--blk-900) 70%, transparent) }`（70% 由原渐变**面积均值 13.0** 反解的等深纯色，改后实测 12.67，Δ0.35/255 不可见）。稀有度晕染退场后 `--lc-r` 仍被 ASCENSION 卡消费，未成死变量。
- **取舍与边界**：hero 视觉区不再有稀有度色晕（星级仍是稀有度信号）；要加回来只能用**纯色/硬边**元素承载，不能再用浅渐变。共享原语 `.nk-hero__panel` 的同款浅渐变仍留在角色 / 遗器 hero 上——本轮只改光锥作用域，未动共享原语（那两页的渐变叠在立绘/图标上方，内容起伏大，未见同类色带）。
- **验证**：见交付记录。
- **降级/未做**：`visual.spec` / 像素基线未跑；未跑全量 e2e；**像素级观感交用户 RunPreview**（AI 只给可断言度量，不判「好看」）。

## e2e 墙钟：拆 `layout.spec.ts` 换文件级并行（`fullyParallel: false` 并不禁文件级）

- **起因**：全量 `pnpm test:e2e:ci` 墙钟 327s / 84 用例。JSON reporter 实测**测试时间合计 554s** 装进 327s 墙钟——Playwright 一直在多 worker 跑，瓶颈是 **layout 单文件 469s 被 `fullyParallel: false` 串成一个调度单元**；a11y 仅 85s 跑完后另两个 worker 空转约 5.5 分钟。
- **关键区分（此前文档没说清）**：`fullyParallel: false` 只禁**文件内**并行，**文件级并行始终生效**。故 docs/agents/commands.md 记的「全局并行换 flake，故保持串行」与「按 describe 拆文件」**不是同一件事**——后者不新增任何用例级并发面（文件内本就串行），是零妥协的提速。实测 327s → 约 5.3 分钟（workers=2）。
- **坑位一：Playwright 的文件参数不是 glob**。`e2e/layout-*.spec.ts` **匹配 0 个文件且不报错**——`test:e2e:ci` 只跑 accessibility 的 10 条仍 exit 0，是**静默的 CI 覆盖率归零**陷阱，正是 testing.md「CI 覆盖率不得下降」要防的事。正解是**路径前缀** `e2e/layout-`（匹配全部 `layout-*.spec.ts`，新增文件自动纳入）。凡用文件名当过滤器的脚本，拆分后必须用 `--list` 核对条数。
- **坑位二：拆分会暴露既有 flake，且会被误判为「拆分引入的」**。不限 workers（12 核取半数 → 6）时必现 4 条 30s 超时，单独复跑全绿；3 worker 仍偶发 1 条。追查该条（`/character/1212` 强化技能图标）时，**在未拆分的 `git show HEAD:e2e/layout.spec.ts` 原文件上 4 跑挂 3** → 属既有 CDN 竞态、与拆分无关。**教训：新并行配置下冒出的红，先用「改动前的文件 + 同样并发」复跑定性归属，再决定是回滚并行还是修用例**；否则会去改一条本来正确的断言。
- **坑位三：`--list` 不执行用例体**，缺 import 只在实跑时炸成 `ReferenceError`。拆分时机械搬运 import 易漏（本次漏 `readJson` / `readFileSync` / `computedNumber` / `readTokenPx` / `resolveTokenColor` / `fontPx`，一次跑出 28 条红），且 6 worker 会同时暴露多个文件、看起来像 flake。`pnpm exec playwright test <files> --list` 能查条数，查不了符号，须靠类型检查或静态比对补。
- **`tools/e2e-literal-baseline.json` 随拆分重分布**：原 `layout.spec.ts: 17` 是**过期值**（HEAD 实际 19，光锥系列两轮提交后未重生成）。拆分后为 character 13 + currency 1 + endgame 5 = 19，纯重分布、零新增。**教训：这类按文件计数的基线在文件改名/拆分后必须 `--write-baseline` 重生成，但重生成前后都要核对总数**，否则会顺手把真实新增一起豁免掉。
- **验证**：`pnpm exec playwright test e2e/layout- e2e/accessibility.spec.ts --list` = **84 tests in 10 files**，与拆分前 84 条**逐字一致**（标题 + project 分布双比对）；`node tools/check-e2e-literals.mjs --strict` 绿；`pnpm test` / `pnpm build` 全绿；workers=2 连续 3 轮全量全绿。
- **降级/未做**：`visual.spec` 全量未跑（像素基线回本机，拆分不动视觉）；**未修那条既有 CDN flake**（`/character/1212` 强化图标）——它在 workers=2 下 3 轮全量均绿，属独立议题，修它需改断言语义（见坑位二的教训），不夹带进本轮提速任务。

## Agent 并发上限随模型而定：GLM-5.3-Flash 下超出 2 个子代理的部分静默不运行（用户纠正流程）

- **起因（用户纠正，两次）**：本轮单测审计开了 6 个子代理（3 个只读审计 + 3 个执行 teammate）。用户先指出「主线程运作时只能再开 2 个子代理」，随后补充**该限制为 GLM-5.3-Flash 专属，并非所有模型都有**——3 个只读审计从未运行，Lead 误归因为「被 teammate 实测取代」。
- **坑位**：超并发上限的部分**既不运行也不报错**——spawn 照常返回 running 态，事后不会有任何通知。「没收到报告」是调度信号还是「职责被别人覆盖」，不核对就归因是无据推断；应当 `list_agents` 看成员运行态，或对迟迟不返的成员直接 `send_message` 追问。
- **判据**：并发上限**随模型/provider 而定，不是通用规则**——实测仅 GLM-5.3-Flash 为 3（主线程占 1 槽，子代理只剩 2），其他模型的额度未测。fan-out 前先按当前会话模型确认可用额度：多代理任务分波下发（每波 ≤ 剩余额度，上一波交付后再发下一波）或改串行；spawn 后先 `list_agents` 确认运行态再继续推进，不把「通知未到」当调度依据。
- **本轮影响评估与处理**：交付质量未受损——3 个 teammate 本身都做了首手审计（对照生产模块）+ 逐文件实测跑绿，Lead 全量复验 + build 门禁兜底；被丢弃的 3 个只读审计只是交叉验证层，**不补跑**（teammate 已覆盖同一范围，重跑即重复劳动）。

## 角色详情页「档案馆」方向样张（hero + 00 属性）：底衬优先于描边、底板几何由文字占位定义，以及像素取证自身的三类假结论

- **判据一（压在媒体上的文字由版面给底衬，不由阴影堆叠自证可读）**：hero 铭牌在 ≥1024 压在立绘 / Spine 上。原实现是 8 层黑色 `text-shadow`，而本页 2026-09 已自登记「只加阴影不加底板 ⇒ 文字填充与白底仍是 2.56:1，不等于 AA；要 AA 必须底板 / 暗角」。改成真实底衬后**实测 14 只角色**（单位：最坏单像素对比度；name=标题 / desc=正文 / meta=元素行 / archive=铭牌）：name 17.39、desc 6.36、meta 12.28、archive 5.22，全部达标且噪声地板为 0。**判据：可读性由版面遮罩承担、阴影只做余量；且结论必须取「全部样本的最坏像素」而不是单只角色的均值**——2026-09 的反例（景元 1204 立绘左下是白云）证明单角色实测会给出乐观偏差。
- **判据二（底板的几何边界由文字占位定义，不由视口定义）**：第一版底衬是贯穿全幅的两轴渐变洗色，实测把 14 只角色媒体的**下三分之一压低 77%~88%、中三分之一 53%、上三分之一 31%**，而对比度余量还剩 4~13 倍——预算完全用反了。改为 `.nk-hero__panel::before` 的「铭牌底板」：`--blk-950 88%`、横向 84% 之后才羽化（羽化区整段落在面板右缘之外 ⇒ 文字占位内恒为满浓度）、纵向只羽化顶边 22px（面板内容距底板顶 26px ⇒ 羽化吃不到任何一行字）。改后**上/中三分之一压暗 0%**，代价只落在文字自身的下三分之一里。**判据：局部可解释的代价优于全局无差别的代价；以及「对比度余量」是应当被花掉的预算，不是越高越好。**
- **判据三（渐变的陡度由既有教训定，不由手感定）**：`layout-character.spec.ts` 的光锥用例记着「大面积浅渐变会塌成 8bit 等值线色带」。新底板只在顶边 22px 与右侧尾段羽化，媒体大面不再铺浅渐变。
- **判据四（假刻度条一律删，不做「数据可视化」的样子）**：`00 属性` 原有的等级条是 `width: 100%` 恒定填充，零信息量且是「带填充轨道的评分条」形态。改为 `Lv. 80/80` 铭文 + 一条发丝引导线；属性表用「索引 + 图标 + 名称 + 引导线 + 取值」的卷宗规格表表达，不伪造归一化刻度（每项归一化都要一个自造量纲，属自建数据源）。
- **坑位一（`.nk-title` 是跨页共享原语，页面级改造必须作用域化）**：`tokens.css` 的 `.nk-title` 同时被角色详情、endgame（Buffs / Peak / Pollution）、voracity、settings、lightcone、relic 六个页面消费。本轮「标题族·区头」只写 `.nk-char-page .nk-title*`，**改 tokens.css 等于同时改六个页面的版面**。同理 `.nk-hero__toggle` / `.nk-hero__visual` 是 `.nk-hero` 族共享原语，玻璃胶囊改直角只能在本页作用域内覆写。
- **坑位二（作用域证成的最低成本手段是先数根类名的写入方）**：`.nk-char-page` 全仓**只有 `CharacterView.vue` 一处**写入，故本轮全部页面级选择器天然不外溢，不需要逐页回归。凡「改了某页 CSS 会不会波及别页」的问题，第一步都该是这条检查，而不是先跑全量 e2e。
- **坑位三（领域色令牌的消费情况与直觉相反）**：`--elem-*` 七个令牌（fire / ice / thunder / …）**全仓零消费者**，只有 `tokens.css` 里的定义；`--prop-*` 此前只被怪物详情页消费，角色页属性区完全没消费。故「让角色页用上属性身份色」是零新颜色、零四步评审的改动（落在 §3 领域色豁免内）；而「元素色扩展到 hero 整块」会撞 §3 的双色约束，需要单独裁决是否登记为机制语境色。
- **坑位四（骨架屏与就绪态的逐行高度差要跨三个断点核）**：属性表从两列改单列后，骨架 `.nk-sk--stat` 的高度必须跟着 35 / 41 / 43 三档走（≤767 / 768–1023 / ≥1024 的就绪行高各不相同，取决于 padding 与 `--val` 字号）。只对一档会把 CLS 留在另外两档，且 e2e 不覆盖骨架态——只能靠探针。
- **坑位五（hero 像素取证的三个前置，缺一个就出假结论）**：① Spine 与 parallax 必须冻结（`display:none` + `opacity:1` 覆盖 `nk-dim`），否则动画帧 + lerp 让同一 CSS 相隔 1.2s 的两张截图差到 0.02+ 亮度；**②`color: transparent` 去字形必须作用到后代**——`.nk-char-page .nk-hero__name` 有直接 `color` 声明，只写父级 `.nk-hero__panel` 会被它压过，于是把白色字形本身当成底衬，直接量出 `vsWorst = 1.0` 的假失败；③立绘 2048² webp 必须等 `Image.decode()` 完成再取样，**渐进解码本身就是噪声源**（实测未等时噪声地板 0.02~0.03，足以淹没 0.002 量级的结论）。去字形用 `visibility: hidden` 也不可行——它会把铭牌自己的底衬一起隐藏，量不到真实底衬。
- **坑位六（`.nk-hero__desc` 有 `v-if`，探针必须判空）**：源 `desc` 为空时该元素整个不渲染（开拓者 8003–8010、1224；2026-09 已登记）。多点采样脚本里任何 `querySelector('.nk-hero__desc')` 未判空都会在跑到那只角色时整轮崩掉。
- **坑位七（触控热区按命中区量，不按视觉盒；半径 ≠ 宽度）**：`.nk-hero__toggle` 视觉 59×26，靠 `::before { inset: -9px }` 扩热区，只有用 `elementFromPoint` 从中心向外扫才量得真实命中区 **76×42**（高度差 2px 不达 44）。扩到 `-12px` 后为 82×48。**注意扫描得到的是「自中心的半径」，命中宽高必须是 `left + right + 1`，直接把视觉盒与半径相加会得出 134×67 这类假值**（本轮踩过）。
- **降级/未做**：T1b —— 未跑像素基线（`visual.spec` 4 张本就不含角色详情页）；未跑全量 e2e；仅 Chromium 单引擎；多角色取证取 14 只（按索引等距抽 + 景元），不是全 98 只。交付待确认项：底板浓度是否再降（**下限与实测见下节「底衬取证的三个洞」，88% 并非下限**）；Hero 艺术资产是否从 `contain` 改 `cover`（会裁切 2048×2048 方图上下各约 90px，本轮只把该映射收口成 `--nk-hero-art-scale / --nk-hero-art-pos`、未改取值）；底板右缘的硬边与铭牌体量交用户 RunPreview。

## 角色详情页 hero 骨架态 ↔ 就绪态：骨架只代理「盒子」，不代理「结构」

- **判据一（骨架代理盒子，不代理结构）**：底板绝对定位在信息面板上 ⇒ 面板一变高、底板顶边就跳。骨架面板此前按内容自然堆高，实测比就绪面板中位数大 19~39px（平板最大）。**反直觉之处：写一个「结构忠实」的小骨架会更糟**——就绪面板在窄断点因元素行换行 + 简介折行会显著变高，忠实小骨架反而变成欠预留。正解 = 固定盒高（取实测中位数）+ 内距逐档对齐就绪面板 + 间距全交给 `space-between`。
- **数据（21 只角色等距抽样）**：就绪 hero 面板高 桌面 137.3（p25 = p75 = 137.3）/ 平板 174.5（p25 = p75，极稳）/ 手机 181.7（p25 = 157）；min~max 桌面 92.8~186.3。简介行数：桌面 1 行 15/21、平板 1 行 17/21、手机 2 行 11/21；无简介 2 只（`v-if` 整段不渲染）。
- **判据二（底板只声明一次，两个宿主共用）**：底板是「加载期与就绪态共同的版面事实」，选择器组写成 `.nk-hero__panel::before, .nk-skeleton__hero-panel::before`。分成两处声明必然漂移——本轮之前骨架态没有底板，≥1024 会在数据到位时凭空弹出一块暗板。
- **坑位一（面板盒高对齐前必须先对齐内距）**：骨架面板的竖向 padding 三段各不相同（tokens 基座 24/28、`≥768` 覆盖 36/40、角色页 `≥1024` 归零），而就绪面板是 32/16/20 → 32/32 → 0，两套此前各走各的。直接比总高会把内距差算成盒差。
- **坑位二（`scrollHeight − clientHeight` 会把伪元素的绝对定位出血算进去）**：底板 `inset-bottom: -30px` 让骨架面板恒报「溢出 30px」，而那不是内容溢出（条块总高 78px 恒小于最小盒内容高 111px）。用这个指标判溢出前先排除伪元素出血。
- **坑位三（`space-between` 在负剩余时静默退化）**：`gap` 与 `space-between` 并用时，`space-between` 只在剩余空间为正时生效；负剩余会退回 `flex-start` 并把内容挤进 padding 区（此档因此把 gap 归零、间距全交给 `space-between`）。「固定盒高 + 均分」必须同时保证 内容总高 ≤ 盒内容高，这条不等式已写进 CSS 注释随新增条块一并复核。
- **降级/未做**：长简介角色（如 1204，就绪面板 186.3）仍欠预留约 47px，属中位数代理的固有代价，不追求逐角色对齐；末行无分隔线 ⇒ 骨架块比就绪块高 1px（344px 的 0.3%），**有意不修**（三档各加一条「末行矮 1px」的规则，收益不值这份噪声）。

## 「档案馆」样张的契约钉法（e2e 侧，R1 铺开前的前置）

- **判据（样张必须先钉成契约再往上铺）**：样张的版面事实（单列规格表、属性身份色、底衬令牌、骨架同框、热区尺寸）此前只活在一次性探针里，R1 一铺开就会被静默改掉。故在 `e2e/layout-character.spec.ts` 补 4 条：00 属性规格表 / hero 底衬 / 骨架与就绪同框 / 「动画」开关命中区。
- **判据（期望值一律派生，不写死）**：行首色从 `--prop-<data-prop>` 令牌经 `resolveTokenColor` 解析；行索引从页面标题索引（`00`）派生为 `00-1..00-8`；骨架与就绪面板比的是**两者相等**而不是某个绝对高度；热区用契约常量 `44`（WCAG 2.2 AA 目标尺寸，跨会话不得漂移）。全仓 `check-e2e-literals --strict` 计数保持 19 处不变 ⇒ 新用例零新增裸 px 字面量。
- **坑位（底板浓度必须收口成令牌才可断言）**：底板浓度原先直接写在渐变里（`color-mix(--blk-950 88%)`），断言只能绑魔法值；收口为 `--nk-hero-bed` 后可用「计算出的 `background-image` 须包含该令牌解析色」判定，且顺带成为单一事实源。**注意计算出的渐变里颜色序列化与 `color` 属性同源**（实测 `resolveTokenColor` 的返回值可直接 `toContain` 命中）。**该令牌已在下节「底衬整体退场」中删除**（教训仍成立：浓度只要还要断言就必须是令牌；但令牌本身不该活得比方案久）。

## hero 底衬取证的三个洞：真实后景、浓度下限、去字形顺序

- **判据一（后景必须取用户真正看到的那一态）**：≥1024 且 Spine 就绪时 `CharHero.vue` 给立绘加 `nk-dim`（opacity 0）⇒ **真实运行态后景是 Spine 动画帧，不是立绘卡**。此前全部底衬取证都把立绘卡当后景，等于「测了一个用户看不到的状态」。补测（Spine 活帧、5 帧最坏包络）与立绘卡后景给出同一组数字：name 17.93 / desc 6.29 / meta 11.96 / archive 5.21（立绘卡为 17.39 / 6.36 / 12.28 / 5.22，差 ≤0.4）⇒ **底板确实与素材无关**，这正是「底板几何由文字占位定义」这条判据想要的结果。
- **坑位一（「动画在跑」不能用被底板覆盖的区域判，也不能靠区域选点）**：面板区在底板之下（88% 不透明），动画帧的帧间差被压掉 88% ⇒ 用它判运动会得出「没动」的假结论；换成「底板之外的一块自由区」又会被「那块正好在角色剪影之外」骗到（实测帧差 0）。正解 = **整幅视觉区逐像素帧差**（实测 maxDelta 218~236、38%~46% 像素变化 ⇒ 动画确实在推进）。同时必须记录 `visibilityState`（后台标签页 rAF 挂起会让 canvas 静止，得出「稳定但假」的结论）。
- **坑位二（Spine 就绪率要显式记录）**：headless 下 6 只抽样有 2 只 15s 内没就绪（走立绘卡），故「活帧」结论的样本量必须写明，不能笼统写成「全部角色」。
- **判据二（浓度下限要算清，不能把「当前取值」当「下限」）**：`--text2` / `--text3`（L≈0.321）在**纯白素材**下的 α 下限是 **0.802**，不是 88%；88% 是留了余量的取值。实测 6 只角色：88% → desc 6.36:1，78% → 5.02:1（仍达标）。**教训：把「取值」写成「下限」会让后续决策失去真实的余量信息**——用户据此以为没有下调空间（本轮就发生过，三处复述被一并订正）。
- **坑位三（去字形必须在读取文字颜色之后）**：顺序反了会把「文字色」读成 `rgba(0,0,0,0)`，等于拿黑色去比暗底衬，稳定得出 ~1.07 的假结论（本轮踩过；同一手法在别的脚本里顺序正确，所以只在那一个脚本里错，且数字看起来「很像一个结论」）。**凡「先扰动 DOM 再测量」的探针，一律先取真值再扰动。**

## hero 底衬整体退场：判据从「最坏单像素」换成「逐字形像素的 AA 分布」（无 ADR，可逆展示迭代）

- **用户口径（本轮起点）**：文字与立绘重叠本就不多，为保 WCAG 而破坏观感得不偿失。故底衬（`--nk-hero-bed` 逐文字块底板）与 `nk-hero__scrim` 整片收口一起删除，媒体上不再有任何压暗层；可读性改由**字形自身**承担：`--nk-hero-glyph-ink`（`--blk-950` 82%）+ `--nk-hero-glyph-shadow`（`0 1px 3px` 紧贴 + `0 0 14px` 软散两层）。
- **判据一（重叠要按「字形像素」量，不按「文字盒」量）**：文字盒宽 520 而名称是 `align-items:flex-start` 的收缩盒，盒级重叠会同时高估名称、低估元素行。逐字形像素（覆盖率 α ≥ 0.6）实测 3 视口 × 3 角色：**名称压在可见立绘上 0%、阵营/星级 0%、简介 0~17%、元素徽标文字 10~100%、铭牌 80~85%、动画开关 75~88%**。⇒ 底衬的真实服务对象只有**简介 + 元素徽标**两处；铭牌/开关压在立绘上 80% 却零失败，是因为它们自带小底板。
- **判据二（AA 必须按逐字形像素的分布判，不能只报最坏单像素）**：同一批数据里「最坏单像素」口径给出 1.02:1（活帧包络甚至 1.01），听起来是「全页崩了」；分布口径才给出真实形状——名称 0% 失败（min 17.0，43~54px 属大字号档 3:1）、简介 0~14.8% 失败（min 1.01、median 6.98）、元素徽标 0~100% 失败（min 1.05）、铭牌/开关/阵营/星级 0% 失败（min 6.02~7.04）。**最坏单像素是包络不是判据**：它能把「4% 的像素」讲成「整体不达标」，也能把「零遮挡」讲成「必须垫板」。
- **判据三（软影买得到观感、买不到证书）**：保留软影、只去填充色再测紧邻像素，简介的「影环」对比度是 **7.76:1**，而同一条简介的严格口径是 1.01~1.36:1。⇒ 「AA 由硬保证降为记录值」是**明示的降级**，不是通过：本页现在的口径是「重叠少 ⇒ 接受少量字形像素不达 AA」，而不是「软影等效底板」。任何后续「本页 AA 达标」的说法都必须先说明用的是哪个口径。
- **坑位一（`nk-dim`：Spine 活帧时静态立绘被淡出 ⇒ 重叠掩码必须先冻结 Spine）**：第一版探针在 Spine 活帧下隐藏面板取「纯素材」背景，结果掩码**全空**，每行都得出「横向重叠 0%」——一个方向正确、理由完全错误的结论（真因是立绘 `opacity: 0`）。正解：先点「动画」开关关掉 Spine（用户真实存在的一态），静态立绘常显，两次取样共用同一背景，逐像素映射才成立。**凡「两态相减」的探针，先确认两态之间除被测量对象外没有任何别的差异。**
- **坑位二（`--bg` 是令牌表达式，不能直接 `parseRgba`）**：`getPropertyValue('--bg')` 返回的是 `color-mix(...)` 原文，正则取数会把表达式里的 `950` / `96` 当成 RGB ⇒ 掩码饱和到整幅 clip（area 100%、每个叶节点 onMedia 100%，连名称都是 100%）。正解：读宿主元素**已解析**的 `backgroundColor`（`.nk-hero` 的 `background: var(--bg)`）。
- **坑位三（对比度必须用元素自己的 `color`，且带 alpha 时先与紧邻像素合成）**：`--text3` 一类令牌可能带 alpha，直接用 rgb 三元组会把文字算亮；大字号档（≥24px，或 ≥18.66px 粗体）判 3:1 而非 4.5:1——本页名称 43~54px 属此档，若按 4.5:1 判会得出「名称也不达标」的假结论。
- **降级/未做**：T1b —— 未跑像素基线（4 张本就不含角色详情页）、未跑全量 e2e；仅 Chromium 单引擎；逐字形取证 3 视口 × 3 角色（1001 / 1505 / 白云底 1204），活帧最坏包络为 3 帧 × 4 角色 × 3 视口。**待用户 RunPreview 确认**：媒体无底板后的整体观感、软影强度（`--nk-hero-glyph-ink` 82%）、徽标小件底板的观感。
- **追加（用户两轮改判后的收口）**：①徽标小件底板被用户判为「比页面更黑（#000@92% vs 页面 #121214），压亮绘读作洞」⇒ 退回裸文字，压绘处的可读性交还字形软影；②「ARCHIVE · №」铭牌从媒体右下角（absolute）迁入**信息面板 head 首行**（档案文号在抬头），媒体右下彻底让给立绘 / Spine，两断点各自受益。连带重测 21 只就绪面板中位数：桌面 164.3 / 平板 197.5 / 手机 204.7（简介行数为最长驱动）。
- **坑位（盒高必须对中位数「上取整」）**：桌面盒高写 164（164.3 下取整）后，同框契约在全量并发下反复报差 1.25px（另一条测量路径量到 165.25）——次像素差在单跑时看不出来。正解 = 盒高对中位数上取整（164→165 / 197.5→198 / 204.7→205→206 依次上取），而不是放宽契约容差。
- **坑位（hud 字体未就位会让量高抖 ±2px）**：编号行用 `--font-hud`，worker 并发下 `document.fonts.ready` 前量面板高度会与字体就位后差 ~1px，正好击穿 1px 容差。凡量面板 / 行高并被字体影响的断言，先 `document.fonts.ready` 再量。

## 角色详情 hero「卷宗封面」迭代：双语名对偶 / 抬头行重排 / 入场编排（数据字段见 ADR 0039，展示层无 ADR）

- **用户口径（本轮起点）**：以 awwwards / Webby / FWA 为品质标准迭代 hero 排版；四条一起上——双语名对偶、字号势能、meta 分层、出场编排；「无底板」主张与前几轮的可读性取舍不变（不因本轮重新引入底板 / 暗角）。
- **判据一（不可折行的短标必须 `flex: none + nowrap`，不能依赖容器富余）**：抬头行首版被渲染成两行（「ARCHIVE · №」/「1001」）。根因不是宽度不够（面板 520、内容 ~262），而是**flex row 里的文本 item 默认 `flex-shrink: 1`**，父级 `align-items: flex-start` 给的是 fit-content 之外的收缩机会 ⇒ 编号被挤到换行。正解 = 编号 / 阵营两端 `flex: none; white-space: nowrap`。**判据：编号、币值、状态戳一类「不可折行短标」一律显式锁死，审查时看的是 `flex-shrink` 而不是剩余空间。**
- **判据二（跨「文字列 / 媒体」边界的横向装饰线一律不用）**：首版抬头行用 `flex: 1` 的横向引导线与属性规格表对齐语法，但面板左对齐、立绘居中 ⇒ 线长由面板宽度决定，桌面档实测正好压在立绘左缘（线 x = 459.6，立绘左缘 452）读作杂线。正解 = 纵向发丝分隔（1×12px）。**属性规格表的引导线之所以成立，是因为它两端都在文字列内；同一条语法一旦跨到媒体边界就不再是「引导」而是「杂线」。**
- **判据三（拉丁注音是与主字同一排版单元，不是独立信息）**：注音与主字的族内间距（6px）必须**小于** head 各行行距（手机/平板 12、桌面 16），否则读作两条并列小字。同理注音字号必须是次级档（0.6875rem hud / 0.3em 字距 / `--text3`），主字两侧放大。
- **判据四（占位符不是译名：缺字段不渲染 > 回退中文）**：开拓者 10 个形态（8001–8010）的 `AvatarName` 在中英两张 TextMap 里都是 `{NICKNAME}`。解析器按「以 `{` 开头 → 空串」收口，前端 `v-if` 不渲染，e2e 锁住「8001 无注音行」。**回退成中文会让主字与注音重复同一字符串，比缺一行更糟；这类上游缺口的正确形态是「少一行」并留可断言契约。**
- **坑位一（骨架盒高必须重新实测，不能按新增行线性外推）**：名称 54.4→64px + 新增 0.6875rem 注音行后，就绪面板中位数从 **桌面 165 / 平板 199 / 手机 206** 升到 **桌面 200.3 / 平板 224.5 / 手机 211.5**（14 只等距样本 × 3 断点）；次轮抬头行拆两行后桌面再升到 218.3、手机 212.5。线性外推（+22）会低估十余像素——主字升档、注音行、抬头行形态是叠加项。改版后一律重测中位数再写骨架盒高，并复核「条块总高 ≤ 盒内容高」的不等式（新增注音条块后总高 78→98）。
- **坑位二（入场动画的 reduced-motion 断言不能用 `animation-duration`）**：`tokens.css` 的全局降级把 `animation-duration` 压到 0.01ms，**任何动画在 reduced-motion 下看起来都「已关闭」** ⇒ 用 duration 断言是假证明。正解 = `page.emulateMedia({ reducedMotion: 'reduce' })` 后断言页面级 `animation-name === 'none'`（并断言四行共用同一关键帧、延迟严格递增、`iteration-count = 1`）。
- **坑位三（入场动画与既有几何断言不冲突，但要知道为什么）**：`translateY(10px)` 只进 `getBoundingClientRect`，不进布局高度 ⇒ 骨架/就绪「同高」契约与溢出扫描都不受影响；面板 `bottom: 24px` 的下移余量 10px < 24px，故「面板须整体在 hero 内」也不会在动画中段翻红。
- **降级/未做**：T1b —— 未跑像素基线（4 张本就不含角色详情页）、未跑全量 e2e；仅 Chromium 单引擎；多角色取证 14 只等距抽样（含 1001 / 1204 / 8001，不是全 98 只）；未做逐字形重叠重测（本轮不动软影令牌与面板横向几何，重叠口径沿用上一轮记录值）。
- **待用户 RunPreview 确认**：主字 64px（桌面）/ 32px（<1024）是否到位；抬头行纵向发丝分隔的观感；注音 0.3em 字距；入场编排节奏（0.55s + 70ms 错峰）。**素材右移方案本轮主动放弃**：立绘 `background-position` 右移会与 Spine 画布（居中 + scale 1.15）产生切换跳变，需先解决两者对齐，另立一轮。

## 同轮第二轮自检：抬头行断点形态、正文基准复核与「零重叠带」回归

- **坑位一（新增文字元素必须复核它是否落在已记录的「零重叠带」内）**：第一轮把阵营从规格行搬进抬头行后，桌面档它在 x≈483 起、而立绘左缘在 452（1440 实测）⇒ 灰字整段压在花瓣亮部上。**这是本轮自己引入的回归，靠高 DPI 裁剪（dsf 2、裁面板框）看出来，不是靠全页截图**——全页缩略下那行小字「看起来还行」。判据：任何新搬进 hero 文字列的元素，都要问「它的 x 区间是否越过了立绘左缘」，越过了就必须换形态（拆行 / 换位 / 删）。
- **判据（同一元素的断点形态可以不同，但方向必须在 e2e 里锁死）**：≥1024 抬头行拆两行（两项都退回文字列左缘）、纵向分隔退场；<1024 面板在媒体下方、重叠为零，保持单行省高度。这条「桌面拆行 / 移动端单行」已写成 e2e 契约（用 `top()` 差 > 2px 判拆行、分隔 `display` 判形态），否则下一轮排版调整会把修复静默改回去。
- **判据（hero 正文字号必须跟页面正文基准，不能单看 hero 定）**：hero 简介一度升到 15px（桌面）/ 14px（手机），实测**短简介掉尾行孤字**（1001 由 1 行变 2 行，第二行只有「照相。」）、**手机面板中位数 211.5→239.6**。查证角色页正文基准统一为 `0.8125rem / 1.9`（`nk-story__text` 与 hero 简介同配方）⇒ 撤回升档。**大标题可以独走一套尺度，正文不行：改正文前先 grep 同类正文的既有配方。**
- **判据（次级信息的强化要有节制）**：星级 `0.8rem/0.14em` → `0.85rem/0.1em`（稀有度是角色第一属性，值得比 11.52px 的徽标文字重一档），其余规格行文案字号不动——本轮只承认这一处层级不足。
- **降级/未做（第二轮）**：T1b —— 未跑像素基线、未跑全量 e2e；仅 Chromium 单引擎；盒高中位数复测 14 只等距样本 × 3 断点；**未重测逐字形重叠**（本轮两处改动分别是抬头行换形态与星级字号，面板横向几何与软影令牌未动）。

## 同轮第三轮：hero 媒体滚动视差（CSS 滚动驱动动画）+ 内容切换编排的既有事实

- **判据一（视差落在「媒体容器」而不是素材定位上）**：实现选 `animation-timeline: scroll(nearest)` + `animation-range: 0 420px` 驱动 `.nk-hero__visual` 的 `translateY(0→36px)`。**关键不是用了 timeline，而是作用对象**——位移整个媒体容器 ⇒ 立绘与 Spine 画布同步移动，两者对齐关系不变；上一轮放弃的「素材右移」正是逐元素改 `background-position`（改一侧就会与 Spine 错位）。**凡要让「媒体 + Spine」一起动的动效，位移必须落在共同祖先上。**
- **坑位一（全局 reduced-motion 降级盖不住 timeline 动画）**：`tokens.css` 的全局降级只写 `animation-duration: 0.01ms`，而滚动驱动动画的进度由 timeline 决定、**完全不看 duration** ⇒ 新增 timeline 动画时全局降级形同不存在，必须自己写 `@media (prefers-reduced-motion: reduce) { animation: none }`。实测：`reduce` 下 `animation-name: none`、位移恒 0；`no-preference` 下 0→13.5（滚 158）→30.8（359）→36（436 封顶）。断言口径同入场编排：`emulateMedia({ reducedMotion: 'reduce' })` + `animation-name === 'none'`。
- **判据二（视差必须断言「封顶」而不是只看「会动」）**：`animation-range` 决定位移上界，越界后应保持不变。e2e 用「滚到远超区间（4000）后位移与区间末端值相等（±0.5px）」判定——只断言「滚了会变大」的话，把 range 写丢（无界增长）也会绿。
- **坑位二（换角色后不能断言整页无溢出）**：client-side 跳转到另一角色后 Spine 画布已在场，`findHorizontalOverflow` 必判红 3 个元素（既有未登记缺陷，2026-09 已定性：canvas scale 1.15 越界、被祖先裁掉、用户看不到）。新写的「换角色重挂」用例因此**只断言 JS 无异常**，不调 `noUnknownOverflow`——与既有结论一致：要断言角色详情页整页溢出，必须先由 Hero/spine 域裁决。
- **修正上一轮的推断（换角色重播入场编排：本来就成立，不需要 `:key`）**：`detail-core.load()` 在 fetch 前先 `id.value = newId; data.value = null` ⇒ 父级 `v-if="d"` 立即卸载 CharHero，数据到位后新挂载 ⇒ 入场编排天然重播。**教训：动「内容切换编排」之前先读 store 的加载生命周期（是否重置 data），不要先给组件加 `:key`**——加 key 只会在「data 不重置」的假设下才有意义，而本仓是重置的。已补契约（用 DOM 节点实例身份判重挂，不依赖动画时序，慢机也不 flake）。
- **降级/未做（第三轮）**：T3 —— 视差仅 Chromium 单引擎取证（滚动驱动动画在 Firefox/Safari 的支持面较窄，本仓口径是「不支持即静态」的渐进增强，未跨引擎取证）；未跑像素基线、未跑全量 e2e；未跑真机触屏（触屏无「精确指针」判定，但视差按滚动而非指针驱动，触屏同样生效）。

## 同轮第四轮：平板档改并排版式（文字在左 · 媒体在右），以及一次被实测推翻的级联推断

- **用户口径（本页逐档的构图意图）**：手机竖排（媒体在上）／平板与桌面同一意图（文字在左、媒体在右），区别只是平板没有叠压空间。
- **判据（平板档的真问题是「空洞」而不是「不一致」）**：768 档实测文字块右侧约 **350×160 全空**、媒体带居中后左右各留 113px ⇒ 读作「手机版式被拉宽」。改为并排：媒体 `flex: 0 0 46%` + `aspect-ratio: 4/5`（flex-basis 给出确定宽度 ⇒ aspect-ratio 才拿得到确定高度）、`align-items: flex-start` 保住媒体的竖幅比例、文字面板 `align-self: center` 纵向居中。**收益不只是好看**：hero 带高 768 档从 ~700 降到 436，首屏（768×1024）从「只见头图」变成「头图 + 8 行属性表全显」。
- **坑位（媒体侧向渐隐必须按档重写）**：`.nk-hero__visual::before` 的左右双向渐隐是给「通栏媒体带」用的；并排后媒体右缘紧邻文字列，右侧渐隐会让媒体糊进文字区 ⇒ 平板档只保留左侧单向渐隐（`linear-gradient(to right, var(--bg), transparent 12%)`）。
- **判据（骨架盒高按档各测一次）**：并排后文字列变窄（768 档 367px）⇒ 简介折行变多，就绪面板中位数 224.5 → **249.2**，骨架盒高同步改 250；视觉/面板的 x / y / w / h 逐项同框（媒体 312.8×391 完全一致，面板差 ≤1.4px）。
- **坑位（不要把级联推断当事实：tokens.css 的 ≥768 横排是 ≥1024 的）**：本轮开工时据「`tokens.css` 里 `.nk-skeleton__hero { flex-direction: row }` 在 ≥768」推断「平板档骨架横排、就绪竖排 = 既有 CLS 缺陷」，**探针实测把这个推断直接推翻**——那条规则在 `@media (min-width: 1024px)` 内，768 档骨架与就绪**都是竖排且几何一致**。**教训：跨文件的媒体查询归属只能靠读包围块或探针确认，靠「我记得某文件有这条」推断会导向一个不存在的缺陷**（若据此改代码，就是为一个不存在的 bug 重排版面）。
- **判据（骨架/就绪恒有 ~1.4px 横向差的既有偏移）**：三个断点一致复现（骨架比就绪右移 1.4px），来源不在本轮范围内，加载期不可见；因此并排契约的 x / y 用 2px 容差、w / h 仍用 1px——**不把「已知的亚像素偏移」写成「版式不同」**（探针里 `面板 x 同列：否` 就是这么误报的）。
- **降级/未做（第四轮）**：T1b —— 平板档新构图属视觉表现，**待用户 RunPreview 确认**（媒体竖幅 46% 的体量是否够、并排后首屏密度是否过密）；未跑像素基线（4 张基线不含本档）、未跑全量 e2e；仅 Chromium 单引擎；未逐档取 pixel 证据（本轮改动为几何，用 DOM 盒子取证足够）。

## 同轮第五轮：补「缺失的中档字阶」，以及一条被字阶升档当场证伪的判据

- **判据（字阶要有可数的档位，不能只有主字 + 注记）**：hero 此前只有 **64 / 14 / 11** 三级——主字与注记之间是断崖，中档缺席。唯一带检索语义的中档内容是**卷宗编号**（上游 id），故把它从 10px 标签升为 **1.25rem / 600 / `--text2`**（`ARCHIVE ·` 词标仍是 0.625rem/0.28em 的标签档），字阶成 **64 / 20 / 14 / 11** 四级。**判据：档案编号是内容（可被引用），不是装饰——把内容升档 ≠ 加装饰。**
- **契约（档位关系用相对断言，不写绝对值）**：`编号 > 词标`、`编号 > 阵营`、**`编号 < 主字`**（主字仍是唯一主角，禁止越档）。三条都是相对关系，改字号不会假绿。
- **坑位（「同一 flex 行」不能用 top 相等判定）**：第四轮写的断点形态契约用「两项 top 差 ≤ 2px」判「同行」——本轮编号从 10px 升到 20px 后，`align-items: center` 让同行两项的 top 差变成半个行高（≈5.5px），**同行为真、判据为假**，契约当场变红。正解 = **纵向区间相交**（`min(bottom) - max(top) > 0`），拆行则用「阵营顶边 ≥ 编号底边」。**教训：混排字号的 flex 行里，任何「同一行 / 同一基线」类判据都不能用 top 相等表达。**
- **判据（升档必须复测骨架盒高）**：编号 10→20px 使抬头行由 12px 升到 25px，三档就绪面板中位数整体上移——桌面 218.3→**231.3**、平板 249.2→**260.2**、手机 212.5→**223.5**（骨架盒高同步改 232 / 261 / 224）。**改任何一处字号都要跑一次「14 只等距样本 × 3 断点」的盒高中位数探针**，这是本页第三次因字号改动而重测。
- **降级/未做（第五轮）**：T1a —— 未跑像素基线、未跑全量 e2e；仅 Chromium 单引擎；编号 1.25rem 的观感**待用户 RunPreview 确认**（是否抢主字 / 是否显得像「填充」）。

## 同轮第六轮：造出逐字形像素尺子，用它修掉宽档「文字压进立绘着色区」

- **方法（三帧差分，可复用）**：同一 clip 下拍三张——A 全可见 / B 只留媒体（文字 `color: transparent`，**必须作用到后代**）/ C 连媒体也去掉（`background-image: none`）。`painted = |B−C| > 10`（消掉纸感颗粒：颗粒在 B/C 两帧同位同值）、`glyph = |A−B| > 40`（粗覆盖率，避开抗锯齿边缘）。逐元素（按盒子归属）统计「字形像素压绘占比 / 其中 AA 失败占比 / 最坏对比度」。**全程不需要 Node 端 PNG 解码**：把截图 base64 回灌页面、用 canvas `getImageData` 读像素即可（data URI 无 CORS 问题）。
- **实测（本轮发现的真缺陷）**：此前 memory 记的「名称压绘 0%、简介 0~17%」是**旧版媒体右下角铭牌**的口径，与当前的「抬头行拆两行 + 规格行」无关。新尺子实测 **≥1440 档抬头第二行（阵营）与规格行会压进立绘着色区**：1920 档 1204 阵营行 **39%（最坏 2.88:1）**、规格行 **32.7%（3.05:1）**；1308 简介 10.1%（**1.4:1**）。根因：宽档立绘随视口变高而变大（1920 → 820 高），1000 带里的两侧留白只剩 90px，而文字列左对齐固定。
- **修法（宽档立绘整体右移 60px，≥1440 生效）**：实测收益——1920 档阵营行 39%→**11.6%**（最坏 2.88→**4.03**）、1204 规格行 32.7%→**0%**、1503/1001/1308 抬头与规格行全部→**0%**、1308 简介 10.1%→**0%**；1440 档 1204 阵营行 16.2%→**0%**、1005 规格行 5.1%（1.98）→**0%**。**主字全部样本、全部断点压绘恒为 0%** —— 这是它还能加大的依据（下一轮的势能预算）。档位边界也由数据定：1280 档媒体盒右缘距视口只剩 66px、且该档逐字形实测未压绘 ⇒ 不偏移；1920 档偏移 60px 后立绘右缘距带边只剩 30px ⇒ 不再加大。
- **坑位（构图不得住在关键帧里）**：第一版把横向偏移写进视差的 `@keyframes`——探针一跑（它的冻结样式含 `*{animation:none}`）偏移**凭空消失**、前后数字完全一致。**判据：位移若属于构图（任何状态下都该存在），必须落在布局层（`left/right`）或静态 transform；只有「随状态变化的位移」才归关键帧。** 顺带一条：`left/right` 要**同时**外移（只改 left 会让盒宽缩小、把偏移吃掉一半并连带缩放素材）。
- **判据（构图偏移要与 transform 分离）**：`transform` 已被滚动视差占用（同一元素不能叠两个 transform）⇒ 构图偏移走 `left/right`，视差走 `transform`，两者互不覆盖；e2e 断言 `left ≈ 变量值`、`transform.m41 ≈ 0`、reduced-motion 下 `left` 不变（构图不随动效偏好变化）。
- **坑位（媒体整体位移要反向补偿其上的控件）**：`动画` 开关是媒体容器内的绝对定位子元素，媒体右移 60px 它会一起移出内容列 ⇒ `right: calc(20px + var(--nk-hero-media-shift))` 补回原位（与内容列右缘对齐）。**凡「整层位移」都要数一遍层内的绝对定位子元素，别只想着主素材。**
- **降级/未做（第六轮）**：T1b —— 未跑像素基线、未跑全量 e2e；逐字形取证 5 只角色 × 3 视口（1280/1440/1920，非全 98 只），1280 档未压绘故只做对照；宽档右移 60px 的构图观感**待用户 RunPreview 确认**；残留：1920 档 1204 阵营行仍有 11.6% 压绘（最坏 4.03，已高于 3:1 大字档但低于正文 4.5）、1005 简介最坏 2.65（压绘仅 0.1%）。

## 同轮第十轮：胶囊禁令契约（把圆角清除锁死）

- **判据（清理必须配契约，否则只是「这次干净」）**：圆角归一（7 值 → 4 值）清掉了 `10px`（全局 `--nk-radius-card` 与页面声明的 12px 冲突）与 `999px`（手机档「备选队友簇」胶囊），但两者都是「靠人记得」的状态。补 e2e：**页面内任何元素圆角 >20px 且非百分比（圆形）即判红**——只允许页面声明的 `0 / 4px / 12px` 与 `50%`。用「非圆形 + 阈值」而不是「白名单精确相等」是有意的：白名单会在新增一个合法小圆角（如记号条端头）时假红，阈值只拦形态回潮。
- **验证**：该契约在 chromium + mobile-chromium 两个项目上均通过；圆角这条线至此闭合成「归一 + 契约」。
- **未做**：`1.5px`（3px 宽记号条端头）是否归零到直角档；全局 `--nk-radius-card`（10px）要不要按页面声明改成 12px（牵动其余 5 页，需单独裁决）。

## 同轮第十一轮：hero 主字势能（名长度分档 + 高度槽）、区块内索引、以及圆角口径的第三条路（无 ADR，可逆展示迭代）

- **判据一（主字的档位由「宽度天花板」定，不由手感定）**：主字此前恒 `clamp(2.4rem, 5.2vw, 4rem)`（桌面 64px），而 6 字名（开拓者·毁灭、知更鸟•晴歌）的自然宽度约为 2 字名的 **1.9 倍** ⇒ 同一字号下短名永远留着半列空白。逐字形像素尺子已证「主字在全部样本、全部断点压绘恒 0%」= 安全上限未触及。故按名长度（模板写 `data-len` = 码点数）分两档：移动 1 字 2.75rem / ≥2 字 2.125rem，平板 3.2rem / 2.25rem，桌面 1 字 `clamp(4.5rem, 6.1vw, 5.5rem)`（72→88px）/ ≥2 字 `clamp(4.25rem, 5.2vw, 4.5rem)`（68→72px）。
- **档位只切两档，且切在「1 字 vs ≥2 字」上**：三档版（1 / 2~3 / 4+）实测在手机与平板两档下都退化成同一字号（宽度天花板不足以容纳第三档），而多一档只换来 ≤4px、却把字阶切成四段。**判据：档位必须由可实测的宽度天花板推出，不能由「名看起来有长有短」推出。**
- **判据二（同档内名长度不得改变面板高度，否则骨架屏的固定盒高假设当场失效）**：名称族外套 `.nk-hero__name-slot`，`min-height: var(--nk-hero-name-slot)` + `justify-content: center`，槽高 = 本档主字上限 × 行距（如 5.5rem × 1.06 = 93.28 → 5.83rem）。**槽必须落在「名称族」这个容器上，不能落在主字 h1 上**——落在 h1 上会把多出来的空间全部灌进主字与注音之间（族内距被撑开，正好破坏「注音是同一排版单元」那条判据）。
- **判据三（任何字号改动都要重测盒高中位数，且这次要取全量）**：全量 98 只（不是 14 只抽样）× 2 断点复测就绪 hero 面板高度中位数——**桌面 231.3 → 239.8、平板 260.2 → 262.5、手机 223.5（不变）**；骨架盒高同步为 **240 / 263 / 224**（对中位数上取整）。抽样集里 1 字名只有 0 只、2 字名 8 只，抽样偏差会把新档位的占比算错，故这次改成全量。
- **坑位（同权重档位规则混写会让断点规则被非媒体规则反压）**：`character-hero.css` 与 `character-skeleton.css` 的档位规则权重都是 0,3,0，靠跨文件源序判定（后者最后导入）。第一版把「手机档 1 字规则」写成**非媒体查询**规则、把平板规则写进断点块 ⇒ 平板断点内两条并列命中，后写的非媒体规则胜出，平板档 1 字名恒为手机字号（实测 44px 而非 51.2px）。**判据：每个断点、每一档只允许一条声明；跨文件级联时先确认两个文件的导入序，再决定哪一条该带媒体查询。**
- **验收（逐字形像素尺子复测，可用同一把尺）**：`temp/hero-aa.mjs` 在 1280 / 1440 / 1920 × 5 只角色下的 name **压绘恒 0%**（与改档前一致）⇒ 势能加到 88px 仍未触及与立绘的重叠。
- **坑位（真实缺陷：英文名把 `nowrap` 撑出面板）**：横向余量探针（全量 98 只 × 4 视口）发现 `1506` 的注音 `Silver Wolf LV.<unbreak>999</unbreak>` 宽 412.7px > 面板 390px，**在手机档横向出画面**。根因不在 CSS：`name_en` 走 `resolve_text_en` 时没有过 `clean_text` ⇒ 游戏内标签直接进了 JSON。修法 = `resolve_text_en` 命中后仍走 `clean_text`，并**先判占位符再清洗**（顺序反了 `{NICKNAME}` 会被洗成中文「开拓者」，产出假英文名）；`1506.json` 就地补丁（不必重跑 55.9MB 文本表的全量转换）。已补 5 条 pytest 锁住「去标签 / 占位符留空 / 顺序」。**教训：任何「不折行」的次级文本都要参与横向余量探针——它不会自己有溢出信号。**
- **判据四（长区块的「可扫描」要落成可枚举的定位层，不能只靠留白）**：技能 1808px / 星魂 1481px 两个区块此前只有吸顶的**区块级**导航，区块内部无锚点。新增区块内索引条（`.nk-idxstrip`：标签 + 实心发丝引导线 + 可点项，纯 `<nav>` + `scrollIntoView`，不做滚动同步高亮——那需要 IntersectionObserver 常驻，本页 T3 级纪律不允许）。条目由页面数据派生（技能族 = `groupSkillsByFamily` 输出的族序，星魂 = `ranks` 键），锚点 `nk-skill-<id>` / `nk-eidolon-<num>`，落点带 `scroll-margin-top: 64px`（= 吸顶条 44 + 余量，与 `.nk-enh-module` 同档）。实测 11 个条目全部落在吸顶条之下（64.3~130.3）。
- **判据五（组间距必须大于卡内距，否则六张卡读成一片）**：同级卡片之间此前一律 `margin-top: 20px`，而卡片自身 `padding: 24px`（≥1024 是 24/28）——**组间距小于卡内距**是这个长区块读不出分节的直接原因。改成分档：手机 32 / ≥768 40。实测技能 2243.9（手机）· 1980.4（桌面）、星魂 1550.9 / 1691；卡间距 32 / 40。
- **判据六（圆角口径的第三条路：不给全局 token 改值，也不放任字面量）**：`--nk-radius-card`（10px，全站卡片档）与页面声明（12px）同名不同值。上一轮记成「要不要按页面声明改全局 token（牵动 5 页）」，本轮换第三条路——页面**另立一名** `--nk-char-radius-card: 12px` 收口本页容器档，只动本页 4 份 CSS，全站 token 不动。同时把残留的 `1.5px`（3×16 记号条端头，半径 = 宽度一半 = 全圆端头）归零到直角档、`3px`（对比页 badge/tag）并在 4px 内联档。**实测圆角集合收敛到 3 值：`4px`×56 / `12px`×50 / `50%`×18**。判据：本页记号语言（属性行首色条 / 章标索引 / 强化标记）全是直角，同一页不该出现两套端头。残留（有意）：`border-radius: 50%` 用于头像 / 状态点等真圆形。
- **验证**：`e2e/layout-character.spec.ts`（新增 2 条：hero 主字分档契约、区块内索引契约）；`tools/check-colors` / `check-contrast --strict` 全绿；`check-e2e-literals` 未高于基线；converter `pytest tests/test_textmap.py` 17 passed。
- **降级/未做**：像素基线（`visual.spec` 4 张本就不含角色详情页）未跑；仅 Chromium 单引擎；逐字形取证 5 只 × 3 视口（非全 98 只）；索引条只验证「落点在吸顶条下 + 卡片可见」，未做「当前项高亮」（有意不做，见判据四）；本轮观感（88px 主字是否压过卷宗编号、索引条在手机档两行/三行的体量、卡间距 40px 是否过大）**待用户 RunPreview 确认**。

## 同轮第十二轮：把逐字形尺子补到最窄桌面档 —— 量出一处真实可读性缺陷，并因守卫约束放弃该档修法

- **判据（取证视口集必须覆盖「约束最紧」的那一档，不能只覆盖最宽档）**：上一轮的尺子只跑 1280 / 1440 / 1920，而桌面叠压版式是从 **1024** 起生效——1024 档文字列与立绘横向重叠率最高（memory 记 62%）。把尺子扩到 1024 / 1152 后立刻暴露一处从未被量过的缺陷：**1024 档规格行（星级 / 属性 / 命途）压绘 29%~44.2%、AA 失败 21.7%~35.3%（最坏 2.52:1）**；简介压绘 10.5%~17.5%、失败 35.7%~73.6%（最坏 1.25:1）。1280 以上这些数字都是 0~1%。**教训：口径的缺口不在阈值，在采样集——「最紧的一档没量」等于结论不成立。**
- **判据（主字的势能预算这次才真正被验证）**：分档后主字在 1024 档压绘 0~0.7%（1001 的 0.7% 是 88px 单字压到立绘边缘）、未超 3:1 大字档；抬头行 0~19.9% 但 min 4.72~9.34 全部达标。⇒ 主字从 64 加到 88px **没有引进新的可读性回归**，此前「压绘恒 0%」的结论在补上 1024 后依然成立。
- **放弃的修法（记录理由，避免下一轮重新试错）**：把 ≥1440 的 `--nk-hero-media-shift` 下放到 1024~1439 档，实测**确有效**（1024 档规格行压绘 29.7%→6.7%、AA 失败 →0%，min 2.52→10.08；着色区右缘最右 992 仍在视口内，无裁切）。**但该档 hero 带右缘恰好等于视口宽（实测 1024 档 hero [148..1024]、媒体盒 [148..1024]）⇒ 任何正值偏移都让媒体盒右缘越过视口（1024 档左缘 +48 即变成 [196..1072]）**，`findHorizontalOverflow` 判红 3 个元素（`.nk-hero__visual` / `.nk-hero__bg` / `.nk-hero__spine`）——与既有 `<1440 不偏移` 的成因完全一致（上一轮只是没在 1024~1279 量过，而非那里有余量）。
- **两条被排除的替代路（都试过或读透了）**：① `background-position` 单移素材：Spine 画布是 `.nk-hero__visual` 的兄弟节点、由播放器自行定位（`spine/player.ts` 不写画布 CSS）⇒ 素材与 Spine 会错位，正是上一轮明确拒绝的路；② `transform` 位移：容器上的 `transform` 已被滚动视差占用（同元素不能叠两个 transform），把偏移折进视差关键帧会违反「构图不得住在关键帧里」（reduced-motion 下 `animation: none` 会连带丢构图）。⇒ **要修这一档必须先把「立绘 + Spine 画布分别位移并重解对齐」做成一条线，属独立任务。**
- **本轮留下的未决项（用户裁决）**：1024~1439 档的规格行 / 简介压绘是**已知未修**状态（不是本轮引入，量出来才知道）。可选方向：a) 该档也改「文字在左 · 媒体在右」的并排版式（与平板档同形，版面变化最大）；b) 给该档整片媒体加左向软遮罩（上一轮已被用户以「破坏观感」否决过一次）；c) 接受现状（口径同本页既有降级：重叠即记录值，不宣称 AA 达标）。
- **判据（契约要跟着语言收窄，别停在粗阈值）**：圆角契约从「非圆形且 >20px 即红」升级为**四值白名单**——容器档期望值从页面令牌 `--nk-char-radius-card` 派生（元素越档即红），并把残留的 `1px`（记号条端头）/ `3px`（强化徽章）一并归到 0 与 4px；实测全量 `border-radius` 声明里**越档 0 处**。
- **验证（第十二轮）**：`e2e/layout-character.spec.ts` 受影响用例（1024 面板契约 / 宽档偏移契约 / 圆角四值契约）3 passed；`hero-aa.mjs` 5 视口 × 5 角色；两项守卫与 build / test 见交付记录。
- **降级/未做**：仅 Chromium 单引擎；1024 档逐字形取证 5 只角色（非全 98 只）；`noUnknownOverflow` 的判据（被 clip 的越界元素仍算溢出）本轮**未改**——它是全站共用原语，改它属跨模块契约变更，须单独裁决。

## 同轮第十三轮：页面外壳（吸顶区块导航）在窄档的两处真实缺陷，以及一处 Layout Shift 陷阱

- **判据一（「横向可滚」不等于「用户能找到」）**：`.nk-secnav` 是全站共用原语（`tokens.css`，角色 / 货币战争 / 终局 / 吞噬四类详情页共用），本身是 `overflow-x: auto` + 隐藏滚动条的横滑条。角色详情页 10 个区块在 390 档实测 `scrollWidth 647 / clientWidth 358` ⇒ **只有 5 项可见**，而本页没有第二个入口能到「遗器 / 档案 / 配音」。修法 = 在会裁的档（<1024）给容器加 `mask-image` 右缘渐隐（28px）当「还有内容」的几何提示，≥1024 三项全可见故不加。**判据：可滚动容器必须有溢出提示，且提示只在真溢出时出现**——用 `mask-image` 而不是贴一块渐变遮罩，是不引入新颜色（反 AI 味禁令针对装饰性色块，不是可达性提示）。
- **判据二（触控目标要抬真实高度，不能扩不可见热区——在滚动容器里热区会被裁）**：`.nk-secnav__btn` 视觉盒 28px 高，原 `::before { top/bottom: -7px }` 想扩热区，但父级 `overflow-x: auto` 会把竖向扩展**裁掉**：用 elementFromPoint 逐向扫描实测首项命中区 **56×44**（改前 **64×28**）——高度是硬伤（WCAG 2.2 AA 目标 44）。修法 = 本页 `<1024` 档把按钮与导航盒都抬到 44px。**这与 hero「动画」开关的 `::before` 手法相反，区别在于后者不在滚动容器里**——同一个「扩热区」直觉在两个容器里结论相反。
- **坑位（吸顶条一变高就会盖住首屏，且有跨文件常量依赖它）**：`.nk-page--detail { padding-top: 45px }` 是按「吸顶条 47 = 内距 6×2 + 内容 34 + 边框 1」定的。导航抬到 44 后条长到 **59**，390 档实测 hero 顶边 50.5 < 条底 59 ⇒ **首屏被盖 8.5px**（页面级截图上不易察觉）。修法 = 同档把 `.nk-enh-bar__inner` 的竖向内距归零 ⇒ 条高回到 47、避让关系不变。**判据：改一个 fixed 层的高度前，先找谁按它的高度写死了避让值。**
- **判据三（同一几何量在两个文件里各写一遍 = 下一次必漂移）**：媒体右移的反向补偿写 `calc(20px + var(--nk-hero-media-shift))`，20 在 `character-skeleton.css`；就绪面板与骨架面板的 `left/bottom: 24px` 也是两份重复（骨架必须与就绪同框，容差 1px）。本轮收口成 `--nk-hero-panel-edge: 24px` 与 `--nk-hero-toggle-inset: 20px`（声明在 `character-hero.css`），四处消费全部改读令牌，取值不变。判据：**「两处必须同值」的约束只写在注释里就等于没有约束。**
- **验证（第十三轮）**：新增 e2e 契约 1 条（`/character/1204：吸顶区块导航在 <1024 档可横滑到位 + 有溢出提示 + 触控 44 且条高不变`，含「≥1024 不得出现溢隐提示」的反向断言）；数值：按钮命中区 64×28 → **56×44**、可见项 5/10 → **6/10**、末项横滑可达、吸顶条高恒 **47**（三档实测）；受影响 6 条既有用例全绿（动画开关命中区 / 骨架同框 ×2 / 1024 面板在内 / 宽档偏移 / 新契约）。
- **降级/未做**：仅 Chromium 单引擎；`mask-image` 的 `-webkit-` 前缀双写（Firefox 需 `mask-image`，已在同一规则里覆盖）；`<1024` 档按钮横向内距由 11 收到 7（与 voracity / endgame 同口径的局部覆盖），观感待 RunPreview。
- **顺带修掉的既有守卫记账（非本任务引入）**：`node tools/check-adr-index.mjs --strict` 的 1 条单项指针漂移（ADR 0031 声明修订 0037，而 0037 未回指）在 0037 的「状态」段补齐回指行——工具给的就是这个修法，属零歧义的文档记账。

## 同轮第十四轮：可达名取证（队伍备选头像把上游 id 当名字）与「合成 focus 不触发 :focus-visible」这条取证陷阱

- **判据一（图标链接的 `title`/`alt` 就是它唯一对外的话，回退串不得当名字）**：审计「交互件可达名」时发现配队头像链接受 `#id` 形态的可达名（1204 实测 8/13 个是 `#8007` / `#1309` / `#1414`…）。根因不在模板也不在 `itemName` 的回退策略（全仓 12 处都在用 `'#'+id`），而在**数据收集漏了一类字段**：`loadLocalBuildNames` 只把 `member_list` 收进 `needed`，`backup_list1..N`（备选队友，键按位编号、没有数组字段可枚举，得按前缀扫键）从未被收集 ⇒ 它们永远只拿得到最后一跳的回退串。全量核对：47 个 member 与 46 个 backup 的 id **全部存在**于 `characters.json`，即纯属可修的数据路径缺口。修后全量 98 页 / 1588 个队伍头像链接**残留 0 个** `#id` 可达名。
- **判据二（回退串的两条出路分开走）**：`itemName` 的 `'#'+id` 回退在**有可见文字的位点**是有用的降级（至少能看出是哪个 id），但在**无可见文字的图标链接**上是纯噪声。故本轮只把该串拦在可达名之外：命中回退形态时 `title` 归空、`alt` 降为装饰性（`alt=""`）——`title` 留回退串会被读屏念出 `#8007`，`alt=""` 则让链接退化为「无名字的链接」同样不达标，最终按 `角色 <id>` 兜底。**判据：同一个回退值在不同位点有不同代价，不能一刀切。**
- **坑位（取证手法本身会给出假结论：合成 `el.focus()` 不触发 `:focus-visible`）**：用 `el.focus()` 逐元素量「焦点后样式是否变化」，得出「5 个 `input[type=range]` 无焦点环」；改用**真实 `keyboard.press('Tab')` 遍历**后，滑条实测 `outline: solid 2px`，全页 54 个焦点停靠点**零个缺焦点态**。同一批元素、两种聚焦方式、相反结论。**根因**：`:focus-visible` 的启发式只在「键盘交互」下命中，程序化 `focus()` 在多类控件上不置位。**判据：凡断言 `:focus-visible`，必须用真实键盘输入驱动；`element.focus()` 只能用于量「非 focus-visible 的焦点态」。**
- **判据三（全局焦点环选择器没覆盖 `input`）**：`tokens.css` 的 `:where(#app) button/a/[tabindex]:focus-visible` 不含 `input`，而技能等级滑条是本页唯一表单控件 ⇒ 页面作用域内补 `input:focus-visible`（令牌与偏移沿用全局那套）。**这是「全局原语覆盖面」类缺陷：只看按钮/链接会漏掉表单控件。**
- **坑位（新用例等到了 Spine 就绪，就会撞上既有的画布越界缺陷）**：焦点用例用 Tab 遍历耗时较长，等到 1204 的 Spine 画布挂载 ⇒ `noUnknownOverflow` 报 `canvas.spine-player-canvas right=1289 left=139`。复测（1024/1440/1920）：画布恒带 `matrix(1.15,…)` 且左右各越出容器 75px，`--nk-hero-media-shift` 为 0 时也越界 ⇒ **纯既有缺陷**（2026-09 定性：scale 1.15 越界、被祖先裁掉、用户看不到），与本轮改动无关。处理同既有口径：本用例**不调** `noUnknownOverflow`，只断言 JS 无异常。
- **判据四（语义结构先量后改）**：标题层级实测 `h1×1 + h2×10`（hero 主字唯一 h1，10 个区块各一 h2），无跳级 ⇒ 本轮**不改**结构，只把它记成已验证基线。**判据：语义结构类改动必须先证明现状有问题，不能凭「应该有层级」就动模板。**
- **验证（第十四轮）**：新增 e2e 契约 2 条（配队可达名来自随站数据 / 滑条键盘焦点环）+ 单测 1 条（`loadLocalBuildNames` 必须收 `backup_listN`，含「名录没有的 id 仍走 `#id` 回退」的反向断言）；全量 98 页队伍可达名普查 0 残留。
- **降级/未做**：仅 Chromium 单引擎（Tab 遍历取证）；可达名审计只覆盖「有可见文字 / 图标链接」两类的命名来源，未做完整 WCAG-EM 式人工评审；`input:focus-visible` 的轮廓在**手机触屏**下不出现（`:focus-visible` 语义如此），触屏走 `:focus` 之外的既有反馈，未额外加。

## 同轮第十五轮：区块导航「点哪节亮哪节」——一个零点几像素的边界判定，以及一次被平滑滚动打穿的修法

- **判据一（两个数字各自都对、但取同一个值就会互相打架）**：`jumpTo` 把区块顶边送到**正好等于**吸顶条下沿（偏移线），`computeActive` 用「顶边 ≤ 偏移线」判定命中 ⇒ 落点带 **0.2~0.4px** 抖动（实测 58.625 / 59.156 / 59.391）时判定翻转，表现为「点附件、亮技能」。修法 = 落点比偏移线多让出 **8px**（`LANDING_SLACK`）：滚动少走几像素用户看不见，命中判定不动。**判据：当「执行」与「判定」用同一个边界值时，必须有一侧留余量——零点几像素的抖动足以让人以为是逻辑错误。**
- **判据二（语义无解时要显式建状态，而不是继续调阈值）**：页尾的短区块（实测「09 配音」仅 200px）永远排在几个长区块之后，而 `.nk-page--detail` 已到滚动上限 ⇒ 它的顶边只能停在偏移线**下方 640px**，任何「顶边越线」类规则都判不出它。这类「锚点规则本身无解」的场景，正确做法是把「用户点到的就是当前的」建成显式状态（跳转钉住 `pinnedId`），而不是给规则加更多特例。
- **坑位（钉住窗口被平滑滚动打穿——两种「精度」不是一回事）**：第一版把钉住实现成「落点 ±24px 窗口」，**实测恒偏 40px**（钉住 8101 / 实际 8063）：`jumpTo` 用点击瞬间的布局算目标，而页面在滚动过程中继续 reflow（懒加载图片、字体、Spine 就绪），动画末段还可能有整数吸附。改用**「滚动停止」作为释放信号**（滚动静默 160ms 后复算一次再释放），并覆盖 `prefers-reduced-motion` 分支（该分支没有滚动动画、不会有 scroll 事件，钉住必须自己释放）。**判据：凡是「A 时刻算目标、B 时刻到达」的机制，都不能用静态窗口去校验，要用「到达信号」。**
- **坑位（取证本身要等稳定态，且不能把动画中态当结论）**：用固定 `waitForTimeout(700)` 采样，同一动作的可达 `scrollTop` 在多次运行间差 **20~40px**（390 档点「01 技能」实测 1374 / 1452 / 1514），一度让我以为「改动没生效」。契约改用 `expect.poll`（只在稳定态比较）、探针改为「等 scrollTop 连续两次相同再读」。**判据：任何依赖平滑滚动的断言，都必须轮询到稳定态；固定 sleep 得到的是动画快照，不是页面状态。**
- **验证（第十五轮）**：新增 e2e 契约 1 条（`/character/1205：点区块导航后高亮落在被点的那一节`，逐项点 10 个区块、用 `expect.poll` 等稳定态；单跑连绿 3 次）；`layout-character` + `layout-currency`（共享 `useScrollSpy` 的另一个消费方）合计 **65 passed**。
- **推翻/偏离记录（依用户 2026-10 授权）**：`use-scroll-spy.ts` 是**跨页共享 composable**（角色详情 / 货币战争角色详情消费），按仓库纪律改它属跨模块改动、应先确认；本轮依授权直接改并在此记录——理由：该缺陷在字符页表现最重（10 个区块、页高 8000+），且修法是纯行为修正（不改签名、不改对外语义），并以 `layout-currency` 全套回归作为替代判据。
- **降级/未做**：仅 Chromium 单引擎；`pinnedId` 期间进度条仍按实时 `scrollTop` 计算（这是有意的：进度条表示真实位置，不该被钉住）；未对 `topThreshold`（返回顶部按钮出现阈值）做任何调整。

## 同轮第十六轮：把「获奖级」落成验收标准（外部判据 + 首次 WCAG 2.2 AA 扫描）

- **判据来源（外部公开页，非转述）**：Webby 的 [Judging Criteria](https://www.webbyawards.com/judging-criteria/) 给出 Websites & Mobile Sites 的 7 个评审维度，其中 **Visual Design 明写「improving inclusion for people with disabilities…low-vision」、Functionality 明写「cross-platform and browser independent」「special access needs, disabilities, and bandwidth limitations」** ⇒ 无障碍与跨引擎不是附加项，是评审维度本身；awwwards 的 [Evaluation System](https://www.awwwards.com/about-evaluation/) 是评审团四轴（Design / Usability / Creativity / Content），**页面不公开逐项百分比，故验收标准只引其维度、不引未证实的数字**；触控目标取 W3C [SC 2.5.8 Target Size (Minimum), Level AA](https://w3c.github.io/wcag/understanding/target-size-minimum)（24×24 CSS px，本仓按 44 执行更严）。验收标准落到 `docs/audit/角色详情页验收标准.md`（A 类可自动判定 / B 类待补 / C 类明确排除），并已写进目标。

- **坑位（现有 a11y 扫描用的是 axe 默认标签，WCAG 2.2 规则从未被覆盖）**：`e2e/accessibility.spec.ts` 一直写 `new AxeBuilder({ page }).analyze()`——axe-core 4.x 的默认标签只覆盖 WCAG 2.0/2.1 的 A+AA，**2.2 新增规则（target-size 等）默认不跑**，而本仓口径一直宣称「WCAG 2.2 AA 目标尺寸 44」。以 `withTags(['wcag2a','wcag2aa','wcag21a','wcag21aa','wcag22a','wcag22aa','best-practice'])` 重扫角色详情页（390 / 1440 × 1001 / 1204）实测三类命中：**`region`（moderate，69~77 节点）——本页正文没有 landmark 包裹（无 `<main>`，各 section 相互独立）**；`color-contrast`（serious，仅 390 档、命中侧栏标签，属全站侧栏既有项）；`image-redundant-alt`（minor，3 处，队伍头像 `alt` 与相邻可见文字同名——由第十四轮的可达名修复引入，`alt` 与可见文字二选一即可，留可见文字、头像退化装饰）。**判据：声明「我们跑 WCAG 2.2 AA」之前，先确认扫描器真的按 2.2 规则集在跑。**

## 同轮第十七轮：按验收标准收口 B2（landmark / 冗余 alt / 手机档对比度），并补上「声明 2.2 就得按 2.2 扫」的工具缺口

- **判据（landmark 不是装饰：`region` 命中的是「内容没有归属」这件事）**：首扫最重的一条是 `region`（moderate，**69~77 个节点**）——本页正文没有任何 landmark，读屏用户只能从头听到尾。修法 = 在 `CharacterView.vue` 的三种态（骨架 / 错误 / 就绪）外层包一个 `<main>`（导航本来就是 `<nav aria-label>`）。修后 `region` 归零。**判据：`region` 命中数 ≈ 页面内容块数，它不是「个别元素」问题，是结构问题。**
- **判据（有可见文字的图片必须装饰化——`alt` 与可见文字二选一）**：`image-redundant-alt` 命中 3 处，是第十四轮可达名修复引入的副作用：成员槽**带可见角色名**却同时给了同名 `alt`，读屏会把名字念两遍。修法 = 成员槽 `alt=""`（图片装饰化），**备选队友槽没有可见文字，仍保留 `alt` 作唯一可达名**。**同一个模板文件里两类槽的 `alt` 策略必须分开判：看它旁边有没有可见文字。**
- **坑位（自己的对比度探针给出了**乐观**的假结论）**：手机档 axe 报 7 处 serious 级 `color-contrast`，而我的自建探针算出 **7.3:1**（判为通过）。差异根因：探针把页面底色 `#121214` 当背景，而**真实底色是手机底栏的 `#1e1c1d`**（更亮 ⇒ 对比更低）。axe 的原始数据是 `fgColor #737d8d / bgColor #1e1c1d / 4.07:1`（门槛 4.5:1）。**判据：凡「文字在某个容器里」的对比度，必须取该容器**实际解析出的背景色**——拿 `--bg` 或 `<body>` 当背景会系统性高估。** 这也解释了为什么侧栏英文小字那条旧登记当初被记成「~3.2:1 但 impact moderate 所以豁免没生效」：**背景取错会让结论偏移一个量级。**
- **判据（不透明度不保留文本语义 ⇒ 弱化要用显式取值）**：`.ui-sidebar-link` 非激活态 `opacity: 0.72` 把 10px 标签压到 4.07:1（`--text2` 以 0.72 复合到 `#1e1c1d`）。实算 α 与对比度：0.75→4.30、**0.78→4.54（贴线）**、**0.85→5.16**、0.90→5.64、1.0→6.61。取 **0.85**：仍在「明确弱化」档且远离阈值。**判据：需要留余量时不要在阈值上取值（0.78 的 4.54 只要渲染差一点就回红）。**
- **推翻/偏离记录（依用户 2026-10 授权，第 2 条）**：本轮改了**共享外壳** `tokens.css` 的 `.ui-sidebar-link`（`opacity 0.72 → 0.85`）。按仓库纪律改共享令牌属跨模块改动、应先确认；依授权直接改并记录——理由：该值在 <768 档把底部导航文字标签压到 **WCAG 1.4.3 的 4.5:1 之下（4.07:1）**，是**实打实的不达标**而非风格问题，且手机用户在底栏看到的第一个东西就是它；替代判据 = 全站 a11y 套件（≥768 档天然不可见该路径）在 1280 档仍零违规 + 新增的 390 档用例。
- **判据（扫描器必须显式声明规则集，且排除项会藏整条路径）**：`accessibility.spec.ts` 此前用默认标签（只含 2.0/2.1），已改为显式 `withTags`（含 `wcag22aa`）；同时**该文件被 playwright 的 mobile 项目 `testIgnore` 排除** ⇒ 手机独有的对比度路径（底栏标签只在 <768 显示）从未进过流水线，故补一条 390×844 专用用例。**判据：口径声明（「我们跑 WCAG 2.2 AA」）与执行（实际跑的规则集 / 视口 / 排除项）必须逐项对齐。**
- **验证（第十七轮）**：`e2e/accessibility.spec.ts` 11 passed（含新手机档用例）；`layout-character` + `guards` 合计 **72 passed**；`pnpm test` 364 passed；`pnpm build` 全绿；`check-contrast` / `check-colors --strict` 全绿；角色页 390/1440 在 2.2 AA + best-practice 规则集下**零违规**。

## 同轮第十八轮：A2 缺口闭合 —— 「容器没有余量」不等于「素材没有余量」

- **判据（同一个视觉问题，容器层与资产层是两条独立的手段）**：1024~1439 档媒体盒右缘贴到视口（1024 档 hero 带 `[148..1024]` = 视口宽），**容器层一像素都移不了**（任何 `left/right` 外移都让媒体盒越界 → `noUnknownOverflow` 判红，第十四轮已实测并把 `--nk-hero-media-shift` 限制在 ≥1440）。但**资产本身有余量**：`background-size: contain` 下 2048² 方图在横带里左右各留大片空档。把 `background-position` 由 `center` 改 `right`，等于把立绘整体推到媒体盒右侧、空档留在文字列这一侧，**容器一像素不动**。
- **实测（逐字形尺子，5 只角色 × 4 档）**：抬头 `19.9% → 0%`、规格行 `44.2%（最坏 2.52:1，AA 失败 35.3%）→ 0%（0 失败）`、主字 `0.7% → 0%`、简介 `17.5% → 3.6%`；越界元素 **0**。1280 / 1152 档简介与规格行也归零。**验收标准 A2 的未决缺口就此闭合**，仅剩简介 ≤3.6%（最坏 min 1.15）属既有明示降级。
- **被数据否掉的另一条路（记下来免得重试）**：先试的是「缩小资产」——`background-size: 92%` 反而把文案压绘**大幅推高**（1024 档抬头 19.9%→48%、规格行 44.2%→70.6%）。原因：`contain` 在小容器里高度是限制边，缩小尺寸等于把图往中间缩、更靠近文字列。**判据：先量再选手段——「让素材变小」与「让素材远离」是相反方向的直觉。**
- **代价与口径（必须说清）**：窄档改资产对位后，**立绘与 Spine 画布的对位不再一致**（画布由播放器自行定位、仍居中）。这一档两者本来就是二选一展示（`动画` 开关切换），且画布恒带 `matrix(1.15,…)` 越出容器被裁（2026-09 定性），故接受；≥1440 档仍走容器整体位移（那边有余量，且保持立绘与画布对齐）。**两档手段不同、各有实测支撑**，已在 CSS 注释里写清，别互相「统一」掉。
- **契约（收口必须配断言，否则一次无关改动静默抹掉）**：新增 e2e `/character/1001：hero 素材对位分档`——窄档 `background-position` 不得是居中档、且 `bgPositionX` 必须**严格大于**宽档，≥1440 必须回到居中。用相对关系而非像素值。
- **降级/未做（第十八轮）**：仅 Chromium 单引擎；逐字形取证 5 只角色 × 4 档（非全 98 只）；简介残留 ≤3.6% 压绘（最坏 min 1.15）为既有明示降级口径，未再压；并发下「hero 媒体滚动视差」用例出现过 1 次单跑即绿的红（既有 flake，非本轮引入，全量复跑 55 passed）。

## 同轮第十九轮：B4 视口矩阵（320→2560 + 矮横屏）落地，以及铺量探针里两处必然出假数的地方

## 同轮第二十轮：B5 结构化数据 —— 角色详情页从「一篇文章」改成「一个角色实体」

- **判据（结构化数据的第一个问题是「这个页面是什么」，不是「加了多少字段」）**：角色详情页原先把 JSON-LD 记为 `Article`（全站详情页共用 `ldArticle`）。用 `Article` 描述一个角色数据页，等于告诉机器「这是一篇资讯稿」——角色身份与角色属性都拿不到。改成 `WebPage` + `mainEntity` = `Person`（角色本体，`@id` 用 `#character` 供页面引用）+ `BreadcrumbList`。
- **判据（字段要挑有定义的属性，不自己造）**：角色属性（稀有度 / 命途 / 属性 / 阵营 / 终结技能量）走 `Person.characterAttribute`——schema.org 对它的定义正是「a piece of data that represents a particular aspect of a fictional character (skill, power, character points, advantage, disadvantage)」，语义贴合；拉丁转写名走 `alternateName`。**没有**选 `Person` 之外的方案：`VideoGame` 会把「这个页面」说成「这款游戏」，`Article` 已被否，自定义类型机器不认。
- **判据（空值整键省略，不留空串——与第十四轮同一条纪律的另一个位点）**：开拓者 10 个形态的 `name_en` 是空串（上游 `{NICKNAME}` 占位符），若照搬会产出 `"alternateName": ""`。守卫里加了反向断言：`alternateName` 存在就必须非空，否则整键省略。实测 `8001` 快照无该键、`1204` 为 `Jing Yuan`。
- **坑位（绿守卫什么都证明不了：必须做反向验证）**：「守卫通过」只说明没报错，不说明新加的检查真的在跑（选择器写错、路径判断写错都会静默通过）。做法：手工把 `dist/prerender/character/1204.html` 里的 `"@type":"Person"` 改成 `"@type":"Article"` 再跑守卫 ⇒ 如期判红（`角色详情 JSON-LD 缺 Person（角色实体）节点`），随后还原复绿。**判据：凡新增守卫断言，交付前必须做一次「故意弄坏它」的验证。**
- **契约（形状而非取值）**：新增的守卫断言只查**形状与必填项**（有 `WebPage`/`Person`/`BreadcrumbList`、`mainEntity` 指向同页 `Person`、`characterAttribute` 非空、`alternateName` 不许空串），**不查具体取值**——取值随数据变，锁死必假红。
- **验证（第二十轮）**：`pnpm build`（含 `gen-ai-endpoints` 1200 快照 + 守卫 7/7）全绿；守卫反向验证如期判红并还原；抽查 `1204` / `8001` 快照 JSON-LD 形状正确。

## 同轮第二十一轮：B1 性能实测与「明示降级」，以及一次**被数据否掉的**修法

- **判据（性能门禁的第一件事是量，不是装工具）**：不装 Lighthouse，直接用浏览器 Performance API（`largest-contentful-paint` / `layout-shift` / `paint` 三个 PerformanceObserver，`addInitScript` 在导航前挂上）在 dev server 上量 4 视口 × 3 角色 × 3 次。实测：**LCP 中位 468~788ms**（最大元素恒为 `.nk-hero__bg` hero 立绘）、**CLS 最大 0.0107、14 次里 9 次为 0**。两项都远低于 Core Web Vitals 门槛（2.5s / 0.1）。**INP 未测**：headless 里没有真实交互负载，合成事件给不出有代表性的数字 —— 记「未覆盖」而不是编一个数。
- **判据（环境不可比时必须写明，不能拿 dev 数字当生产结论）**：以上都是 **dev server**（未压缩、按需编译）数字。口径写成「dev 环境下两项均远低于门槛」，而不是「生产达标」——生产只会更快，但那需要一次真实部署采样才算证据。
- **坑位（我自己的修法被数据否掉：`scrollbar-gutter` 无效）**：先用 CLS 的 `sources` 定位到根因——加载中滚动条出现 ⇒ 滚动容器 `clientWidth` 少 1px ⇒ hero 面板重新居中（`prev 296,452 542x253` → `cur 297,449 541x256`，单次 v=0.00592）。据此想用 `scrollbar-gutter: stable` 修，**逐变体实测（baseline / 滚动容器 / `html`，各 2 角色 × 3 次）三者数字完全同量级**（0.0059~0.0086），即**无效**，故**不落这条规则**（不留下一条看着对、实际没用的声明）。噪声地板约 0.002，0.006~0.009 属亚感知量级。
- **判据（CLS 的代理指标要指「最大潜在位移」，不是随便找一条契约）**：本页最大的潜在位移是**骨架→就绪的块替换**，而现有 e2e「骨架态与就绪态 hero 面板同宽同高（±1px）」正好锁死它，且盒高取自**全量 98 只角色**的就绪面板中位数（不是抽样）。故把它**正式接受为 B1 的代理验收项**并写进 `character-skeleton.css` 的注释与验收标准；同时把实测与残留（0.006~0.009）一并记录，不宣称「零位移」。
- **降级记录**：B1 = 实测已做 + 代理指标已选 + 残留已记录；**INP 未覆盖**（无代表性负载）；生产环境 LCP/CLS 未采样（需一次真实部署）。

## 同轮第二十二轮：B3 跨引擎对照 —— 抓到一个「支持性缺陷」：不支持的引擎不是少个动效，而是构图永久偏移

- **判据（跨引擎对照要找的是「同一 CSS 在不同引擎下语义不同」，不是「截图不一样」）**：装 firefox + webkit 后逐引擎跑同一批断言。**七项全部一致**：标题语义（`h1×1 + h2×10`）、hero 面板落位、主字分档（68px / 34px）、素材对位（窄档 `100% 40%` / 宽档 `50% 40%`）、横向溢出（零）、焦点可见（`solid 2px`）、`:has()` 与 `mask-image`。
- **真缺陷（唯一差异，且是构图级的）**：**Firefox 不支持滚动驱动动画**（`CSS.supports('animation-timeline','scroll(nearest)')` = false，WebKit 26.5 与 Chromium 均已支持）。此时 `animation-timeline` 被忽略，`nk-hero-lag` 退回**普通时间轴**跑完并停在末帧（`fill: both`）⇒ 媒体层 `translateY` **恒为 36px**（chromium/webkit 是 0→17.1→36）。**这不是「少个视差效果」，而是立绘被永久下移 36px、与文字列错层**。修法 = 把整条动画关进 `@supports (animation-timeline: scroll())`：不支持 ⇒ 静态构图（实测修后 Firefox 恒 0）。**判据：渐进增强的正确形态是「不支持 = 静态还原」，不是「不支持 = 停在末帧」——凡是 `fill: both` + 时间轴驱动的动画，都必须包特性查询。**
- **坑位（既有契约里藏着一条只在某个引擎显形的竞态）**：把 Firefox 拉进常规回归后，`/character/1212` 的技能图标契约立刻判红（`naturalWidth = 0`）。查证：该用例**没有等图片加载完**就断言 `complete/naturalWidth`，等于把「还没加载」当「加载失败」。实测 firefox 与 chromium **立即都是 6/6 未完成、6s 后都是 6/6 完成且零宽 0、占位 0**——纯**测试竞态**，Chromium 长期不显形是因为请求缓存 + 靠前用例预热。修法 = 先 `expect.poll` 等到 `complete` 再断言。**判据：`complete`/`naturalWidth` 类断言前面必须有等待，否则它的通过与否取决于跑在前面的用例。**
- **入 CI 的取舍（明示未覆盖，不假装全绿）**：新增 playwright 项目 `firefox-layout-contract`，**只跑 `layout-character.spec.ts`**（该文件的用例自钉视口或声明 `@viewport-pinned`，不受项目默认视口影响），实测 **39 passed**。**不扩到三引擎 × 全量**：墙钟与既有 flake 面会成倍放大，收益不匹配；**WebKit 未入 CI**，以一次性人工对照取证代替——这条未覆盖写进验收标准 B3 条目。
- **验证（第二十二轮）**：三引擎对照探针（2 视口）+ 视差计算值探针（3 引擎 × 3 滚动位置）；`layout-character` @ `firefox-layout-contract` **39 passed**。

## CI e2e 全红复盘：新增 playwright project 未同步 CI 浏览器清单（**零覆盖却只在 CI 显形**）

- **现象与指纹**：CI run（`0e4c590`）e2e job 4m57s，**119 passed / 39 failed**，39 条**全部**是 `[firefox-layout-contract]` 且错误同为 `browserType.launch: Executable doesn't exist at /home/runner/.cache/ms-playwright/firefox-1538/firefox/firefox`（3 次重试撞同一错）。**判据：失败集恰好等于某个 project 的全部用例（39 = 该项目用例总数）且错误停在 `launch` ⇒ 直接判「二进制不存在」，不必读 trace / DOM 快照**——项目级 100% 失败而不带任何断言差异，只有环境缺件这一种成因。
- **根因**：第二十二轮在 `playwright.config.ts` 新增了 `firefox-layout-contract` project，但 `.github/workflows/ci.yml` 的安装步骤仍是 `playwright install --with-deps chromium`（该行写于「单 Chromium」时代）。本机早已手工装过 firefox（三引擎对照那次），故**本机全量 e2e 124 passed**，缺口一路带进 push。
- **判据（最重要的一条）**：**CI 的浏览器集合是 `playwright.config.ts` 的投影，不是一条独立事实**。新增 project 时「本机全绿」**零证明力**——本机浏览器是历史手工安装的既成事实，本地跑绿只证明「我这台机器恰好有」。同理推广：凡「运行环境依赖清单」（浏览器 / Node / Python 版本 / 系统库）新增消费方，必须同批同步清单；**本地装了 = 缺口被掩盖**，而「不装浏览器的 project」在报告里仍然占着用例数，看起来有覆盖、实际是零覆盖。
- **修法**：`ci.yml` 安装清单改 `--with-deps chromium firefox`（`mobile-chromium` 复用 chromium 二进制，无需单列）；缓存 key 补 `-v2` 后缀——`actions/cache` 命中旧 key 后**不回存**，不升版则每次 run 都要重下 firefox。契约登记进 [testing.md](../agents/testing.md)（新增 project 必须同步该清单，该文件是 e2e 分层唯一事实源）。
- **同类漏登记（顺手发现）**：`testing.md` 第 14 行仍写「单 Chromium」——第二十二轮新增 project 属**契约变化（新 e2e 分层）**，按 AGENTS.md 文档分级应登记子文件，当时只改了 config 与 memory。**判据：config 里新增 project = 新分层 = 必须登记子文件，memory 的复盘段落不能替代登记项。**
- **降级/未做**：修复只在本机验证到「firefox project 可跑通」（Windows firefox；用例断言全为计算样式与相对关系，无 Linux 专属分支），**Linux CI 上的最终确认必须等 push 后的 run**——本地无法证伪 CI 侧。已排除的替代方向：把 firefox project 用 `process.env.CI` 门掉（等于砍掉第二十二轮刚建立的跨引擎守卫，覆盖率下降，与「CI 覆盖率不得下降」冲突）。

## 同批第二层：骨架盒高收口为「就绪面板高度下限」（**跨引擎字体度量差异不再击穿 ±1px**）

- **坑位（最重要的一条）**：**项目级 100% `launch` 失败会把该项目的真红一起埋掉**。上一段修好「firefox 没装」后重跑，39 failed → **154 passed / 2 failed / 2 flaky**：两条真红（`layout-character` 桌面 Δh **2.8167**、平板 Δh **1.5**，容差 1，3/3 次重试全红）此前从未被任何人看到过。**判据：环境缺件的修复不是收尾——必须重跑一次并确认「该项目真的跑起来了」，否则你只是把「缺件红」换成了「真红被掩盖」。**
- **根因（探针取证：就绪面板内容高是字体度量的函数）**：把就绪面板高度拆开看构成 —— `head 195.313 = rubric 45 +16+ meta-row 18 +16+ title 96.313`，`+ gap 20 + desc 24.5`；其中 `rubric` 里的 archive 是 10px 文本却被内含的 20px 编号行撑到 25px，`camp` / `name-en` / `stars` / `badge` 同样如此——**这些元素的 `line-height` 全是 `normal`**，其行盒比例由**实际解析到的回退字体**决定。Windows 上 Chromium/Firefox 回退同族（实测 239.813 vs 239.817，差 0.004px）⇒ 本机恒绿；Linux 上 fontconfig 给两引擎不同回退 ⇒ Firefox 内容高 **242.82（比 Windows 高 3.0px）**、平板 **264.5（高 2.0px）**⇒ 恒红。**判据：「两态几何相等」这类断言，只要一侧是若干 `line-height: normal` 行盒求和，它就是字体度量的函数、不是环境无关不变量**——跨引擎 CI 之前必须先把这条链路消掉，或把它改成下限式契约。
- **坑位（我把 |Δ| 的符号想当然了，白烧一轮 CI）**：断言比的是**绝对值**，我据「Windows 侧 239.813 略低于常量 240」推断「Linux 一定更矮」，于是第一版修法只做了 `min-height`——PR run 回来红值**与改前一模一样（2.8166656494140625 / 1.5）**。反证定方向：本机探针已证明 `min-height` 生效（就绪面板 262.453 → 精确 263），而 CSS 与平台无关 ⇒ **若内容偏矮必被顶到下限、Δ 应为 0**；红值未变 ⇒ 内容**偏高于**下限。**判据：绝对值断言在定修法之前必须先定方向；「加了兜底但红值一字未变」本身就是方向判据——兜底只对一侧有效。**
- **修法（令牌收口 + 判「环境 vs 契约」后移出 CI）**：① 盒高收口成单一令牌 `--nk-hero-panel-h`，骨架 `height` 与就绪 `.nk-hero__panel` 的 `min-height` **同源消费** ⇒ 就绪高 = `max(内容高, 令牌值)`，值仍是标定的 224 / 240 / 263，**零视觉变更**；下限式契约消掉「内容偏矮」那一侧，两态同框在标定源上由构造成立（不必再依赖「常量恰好等于内容高」这个 0.19px 级的巧合）。② 「内容偏高」那一侧**不由 CSS 硬扛**：判定它是**平台字体差、不是契约破**（3px 级、只影响 Linux Firefox 加载瞬间、CLS≈0），按「环境相关判定不进 CI」（与像素基线移出 CI 同一条理由）给该断言打 `@font-calibrated`，`playwright.config.ts` 按 `process.env.CI` 在三个 project 上收起它 ⇒ CI 层少 2 条、本机全量仍判。③ 被否掉的方案（**记下来免得重试**）：把令牌抬到 243 / 265 就能让 CI 全绿，代价是**所有平台**的面板盒高 +3.2px（面板无底板 ⇒ 整块文字上移），**拿全局视觉位移换一条 3px 级加载瑕疵的消音**——不值。
- **判据（这条最通用）**：断言翻红时先问**「它判的是环境还是契约」**——判环境的（字体度量 / 渲染差异 / 外部服务）按仓库纪律**不进 CI 层**，本机判；判契约的（结构 / 语义 / 不变量）才允许用改设计去满足。**禁止**为了把环境相关断言塞进 CI 而改动全局视觉。下限 / 兜底类修法也有方向盲区：它只对「实际值偏矮」有效，偏高必须换思路（本轮第一版修法就撞在这上面）。
- **本仓既有先例**：`--nk-hero-panel-edge` 的注释写的正是「骨架是就绪态的代理，两处必须同值 ⇒ 收口成令牌」——同一判据的第二次应用；遇到「两处必须同值」的骨架/就绪对，先找令牌而不是再算一遍常量。
- **flaky 记录（非本轮引入）**：同一次 run 里 `[chromium] hero 媒体滚动视差` 与 `[mobile-chromium] 首页三分区` 各首跑红、重试绿（前者是第十八轮已登记的既有 flake）；CI 的 `retries: 2` 吸收，不计失败。
