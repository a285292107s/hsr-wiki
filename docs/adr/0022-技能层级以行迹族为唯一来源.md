# 0022. 技能层级以行迹族为唯一来源

## 状态

`accepted`（**已实现**：族推导 `src/lib/skill-family.ts` + 技能卡图标列与层级线渲染全部落地；层级线几何的**第二轮修订**（竖轨落父图标底边中点 + 缩进一个技能图标空间 + 折角接子图标中线）亦已落地，见文末「相关」与 `docs/memory/2026-09.md`）

## 背景

需求：角色详情页 SKILLS 区要**精确**标明技能之间的父子 / 兄弟层级（以带折角的连接线表达，如真珠 1503 的「行笔，临摹断水」→「行笔，幻造星月 / 行笔，绘制末浪」）。

现状的层级判定是**前端启发式**：`SkillsPanel.vue::groupSkills()` 按 `(type + type_name)` 分组，并以 `AvatarConfig.SkillList` 顺序的**首个**成员为父、其余为子；`SkillCard.vue` 递归渲染子卡。该启发式在两个层面不可靠：

| 问题 | 实测 |
| --- | --- |
| 父节点取错 | 镜流 `Point02` 族序为 `121202`（无罅飞光，基座）→ `121209`（寒川映月，形态），而 SkillList 顺序把 `121209` 排在前面 → **形态被当成父卡** |
| 族被拆成平级卡 | 白厄（`140804/140805`）、远坂凛（`150804/150805`）、吉尔伽美什（`150904/150905`）的「天赋 + 天赋 2」两条同族技能，因一条 `type=Passive`、一条 `type=null` 而落进两个分组键；姬子•启行（`151004` + `151022/151025/151026`）的天赋与三条助战技亦被拆到两个分组键 → 全部渲染成互不相干的平级卡 |

**源数据里有更权威的等价物，且已在 converter 输出中**：`AvatarSkillTreeConfig` 的锚点（一个**行迹升级槽位**，游戏内即"升级该技能"的槽位）通过 `LevelUpSkillID` 串起该槽位下的全部技能形态；converter 的 `_build_skill_trees()` 已把它输出为 `characters/{id}.json` 的 `skill_trees[anchor][level].level_up_skill_id`，**无需改转换器、无需重跑数据**。

全量实测（`public/data/cn/characters/*.json` 98 个角色 JSON；"可见"= `type_name` 非空且 `type` 在 `SKILL_ORDER` 内，含 `ElationDamage` / `Assist`）：

| 指标 | 数量 |
| --- | --- |
| 可见技能族（族内 ≥2 个可见成员） | 39 |
| 现状启发式多成员组（`type + type_name`） | 36 |
| 父节点与族序不一致 | 1（镜流 `Point02`） |
| 族成员被拆到不同卡 / 部分落单 | 4 族（白厄 `Point04`、远坂凛 `Point04`、吉尔伽美什 `Point04`、姬子•启行 `Point04`） |
| 族内首位是基座槽位（`Skill01/02/03/04/P01/Maze`）的族 | **39 / 39** |

族成员中被 converter 过滤的（`HideInUI`、`Skill31-34` 内部子技能）在输出 JSON 里**完全不存在**，故族与可见技能的交集是干净的：如黄泉 `Point03` 族含 `130814-130817` 四个内部子技能、飞霄 `Point03` 含 `122014`，交集后与现状一致。

另实测：**`SkillTriggerKey` 不可作为层级依据**。它的首位数字不恒等于技能槽位——飞霄的 `Skill11` / `Skill21`、姬子•启行的 `Skill11` / `Skill21`、开拓者·毁灭的 `Skill11` / `Skill21` 都是 `AttackType=Ultra` 的**终结技**形态（并非普攻 / 战技槽位），因此它只能证明"是形态"，无法可靠推出"属于哪个槽位"。

## 决策

**技能父子层级以「行迹族」为唯一事实来源**：族 = `charData.skill_trees` 中某锚点的 `level_up_skill_id` 与可见技能的交集；**族内首个（`level_up_skill_id` 原序）为基座技能 = 父卡**，其余为形态技能 = 子卡（互为兄弟）。前端**禁止**再按 `(type + type_name)` 分组，也**禁止**用 `SkillList` 顺序判定父子。

约束：

1. **族来源于数据，前端只读**：不为层级新增数据源、不在前端硬编码族或形态清单；族成员中不存在于 `d.skills` 的（已被 converter 过滤）一律不渲染。
2. **退化路径**：角色无 `skill_trees`、锚点缺失或交集 ≤ 1 条 → 该技能按单卡渲染（无子卡、无线），**禁止**回退到 `(type + type_name)` 分组。
3. **只影响 SKILLS 区的层级归属**：技能卡的其余渲染（等级滑条、强化来源、技能预览、技能数据表、强化角标）与动画按索引分发逻辑不变。
4. **内部子技能维持不展示**：`Skill31-34` 的过滤是既有裁决（描述为空、文案并入父级描述），本决策不重开。
5. **本轮范围**：忆灵技能区（当前平铺）与对比模式（变化技能列表）**不使用**本族关系；忆灵技能的族虽同在 `skill_trees`（`Point19` / `Point20` 等锚点指向 `11xxxxx` / `18xxxxx`），但是否/如何展示属另一决策。

## 后果

**正面**

- **零数据改动**：族已在输出 JSON 里，改的是前端「怎么读」，不引入 converter 改动与全量数据重跑。
- 修好 5 处族关系显示错误（镜流父节点错位 + 4 个族的成员被拆到不同卡），"精确标明层级"这一诉求才有事实基础。
- 族序即官方顺序（基座 → 形态），父子方向不再依赖 `SkillList` 的偶然排序。
- 忆灵技能的族关系在同一字段里已存在，未来扩展不需要新的数据来源。

**负面**

- **显示语义扩张**：天赋族也将开始出现父子 / 兄弟线（如白厄「此身为炬」→「命运•此躯即神」、吉尔伽美什两条天赋从两张平级卡变为一父一子、姬子•启行的三条助战技挂到天赋之下），读者可能认为"天赋怎么会有子技能"。这是**有意的语义修正**，但不是用户本轮点名的场景。
- **父卡换人**：镜流 `战技` 的父卡由「寒川映月」变为「无罅飞光」——既有页面认知、技能预览分发（按子卡索引分配动画）与像素基线都会随之变化。
- **依赖 `skill_trees` 的存在性与锚点语义**：族判定依赖"锚点 = 行迹升级槽位"这一源数据语义；若上游改变 `AvatarSkillTreeConfig` 的写入方式（例如合并锚点、或让不同槽位共用 `LevelUpSkillID`），族需要重新核验。退化路径（无族 → 单卡）是防御，但会**静默降级为没有层级**，需要 e2e 断言兜住。
- **族内形态无条件文案**：数据里没有"什么条件下切换到哪个形态"的权威短文案（条件写在各形态的描述正文里），故层级线只能表达"同族"，**禁止**为形态自造「强化 / 形态 2」类标签。

**中性**

- `SkillsPanel` 的 `SkillGroup` 结构（`main` + `children`）可保留，只把"谁当 main"的来源换掉；`SkillCard` 的子卡渲染与 `childSkills` prop 契约不变（图标列与连接线是另一项展示决策）。
- 忆灵技能区、对比模式、光锥详情页（共用 `skill-card.css`）不受影响。

## 替代方案

| 方案 | 为何未采用 |
| --- | --- |
| 沿用现状启发式（`type + type_name` + `SkillList` 首位为父） | 5 处族关系显示错误（1 处父节点错位 + 4 个族的成员被拆到不同卡），"精确"无从谈起 |
| 前端按 `SkillTriggerKey` 推导（`Skill01/02/03/P01` 为基座、`Skill1x/2x/3x/4x/5x` 为形态） | converter 当前不输出该字段（需改转换器 + 重跑全部角色 JSON）；且编号首位不恒等于槽位（飞霄 / 姬子•启行 / 开拓者·毁灭 的 `Skill11`、`Skill21` 均为终结技形态），推不出族 |
| 按技能**同名**分组 | 同族形态名多不相同（真珠 `150301/150308/150310` 三名各异），同名分组会漏掉全部非同名形态 |
| 由 converter 新增显式族字段（如 `family_id` / `parent_id`） | 族可从既有 `skill_trees` 无损推导，新增字段等于制造第二事实源，且需全量重跑数据 |
| 沿用内部子技能（`Skill31-34`）作为"子技能"语义 | 它们是描述为空的内部行为子技能，文案已并入父级描述，既有字段裁决已排除；与"形态"不是一回事 |

### 几何修订：竖轨落在父图标底边中点 + 缩进一个技能图标空间（2026-09 第二轮，已落地）

用户连续三轮修正缩进、并在落点上二次修正后定稿的层级线几何（术语见 `CONTEXT.md`「技能图标空间」「技能层级线」）：

| 规则 | 取值 |
| --- | --- |
| 竖轨 x | = 父图标**底边水平中点**（= 行体左缘 + `--nk-skill-gutter` + `--nk-skill-rail` / 2），父卡与全部子卡共线 |
| 父卡竖轨上端 | 自**父图标底边**下垂，无短横 / 无圆角 / 无端点装饰（取消原 10px 短横与 6px 圆角） |
| 子技能行缩进 | 恰为一个**技能图标空间** = `--nk-skill-rail`（= 图标边长），**删除**移动端独立缩进值 |
| 折角（├ / └） | y = **子图标中线**（= 卡顶 + `--nk-skill-child-gap` + `--nk-skill-rail` / 2）；横段 = 半个技能图标空间；因缩进 = 一个图标空间，**子图标左缘 = 父图标右缘** |
| ├ / └ 圆角 | 中间子卡 ├ 无圆角；末位子卡 └ 保留 6px 圆角，竖轨止于该折角（跨行不断规则不变） |
| 兄弟纵向间距 | 半个技能图标空间 `calc(var(--nk-skill-rail) / 2)`，取代原 18px 全断点常量 |
| 图标列左侧留白 | `--nk-skill-gutter` 由 20px / 16px 压到 **10px / 8px**：图标列与内容列整体左移，内容列同宽增加（`--nk-skill-rail` 本身不变） |

**包含块原点（实测，禁再搞错）**：子卡上绝对定位伪元素的包含块是子卡 padding box 的**外缘 = 卡片顶**，不是内容 box 顶。实测真珠 1503（桌面）：插入真实 `position: absolute; top: 0` 元素得 top = 1529.23 = 子卡 cardTop（子卡 padding-top = 24px）；同批实测 `top: calc(var(--nk-skill-rail) / 2)` = 1553.23 = 子图标**顶边**、`top: calc(var(--nk-skill-child-gap) + var(--nk-skill-rail) / 2)` = 1577.23 = 子图标**中线**。故「折角接子图标中线」的公式**必须带 child-gap**；上一轮据错误基准把折角改成 `rail/2`，折角整体落到子图标顶边，由用户肉眼发现（原话「折角线应该对齐子图标中心」）。同理 e2e 的 `pseudoBox()` 只能用宿主 border 宽度换算，**不得加 padding**——加了会继续掩盖该错位。

定稿依据（实测真珠 1503，桌面 1440）：原竖轨 x = 356，而父图标左缘 366（差 10px——竖轨落在图标列左侧沟槽里，靠一段 10px 短横接回图标底边）、父图标中点 390；子图标左缘 402、父图标右缘 414（重叠 12px）。「36px」从来不是图标边长的整数倍，故一轮在**数值**上、一轮在**单位**上、一轮在**落点**上先后被打回：**Q14 把「对齐父图标左缘」写作「正下方」，用户随即回问「竖轨不是应该在父级图标正下方吗？」→ Q19 重新定为图标底边中点**。教训：① 方位词（正下方 / 中间）必须当场落到具体参考点（哪条 x）并配对比图；② 伪元素坐标必须用真实哑元元素实测包含块原点，禁止按名词推导（同一处曾因此得出相反结论并回归一次）。代价（实测 375px）：子卡内容列 219px → 191px（−28px），用户已确认接受。
