# 货币战争 · 「按赛季切换数据」可行性分析报告

> 状态：**方案 B 已实现（2026-11-18）**；本文档保留为方案 / 审计记录。转换器隔离审计结论见文末「十」。
> 已落地：设置页「04 赛季」切图鉴列表（偏好存 localStorage）；详情页标题按赛季消歧；五图鉴 fetchData 读 `ctx.cwSeason`。未做：枢纽页随赛季、赛季进路由（见判断）。
> 范围：货币战争（Currency War）数据模块 + 设置页赛季切换。
> 取证口径：以当前仓库产物（`public/data/cn/currency/*.json`，4.7.0 快照，`season.id=2`）与转换器源码为准；官方源表只读通过 `tools/converter`。

---

## 一、结论摘要（先给判断）

- **官方怎么区分赛季：数据里已经很完整**。五个货币战争数据域（角色 / 羁绊 / 投资环境 / 投资策略 / 装备）的**每条记录都带赛季归属字段**（`season_ids` 数组或 `season_id`），每个产物顶层还带 `season = { id, sub_season_ids }`（当前 `id=2`）。也就是说「按赛季区分」**不需要改转换器、不需要新抓数据**，现有产物已足够。（与仓库历史文档里「装备无赛季字段」的过时说法不同——4.7.0 起装备也有 `season_ids`。）
- **前端已经有一半在做**：五个图鉴页（`/currency/{role,trait,item,buff,augment}`）的 `fetchData` **现在就按 `season.id`（当前季）过滤**，只是**写死当前季**、没有让用户选。
- **真正的难点不在「按赛季筛」，而在「本赛季新增」这个口径**：`is_season_new` 只在**当前代**算得出（历史季全为 `false`），所以「让用户切到旧赛季」时，枢纽页「本赛季新增」那套展示会**结构性失效**（旧季全空）。这是决定「值得做到哪一档」的关键。
- **建议**：**值得做，但按「数据查看」而非「赛季新增回顾」定位，并分两档落地**——
  - **推荐档（低成本、高确定性）**：新增赛季切换偏好 → **五个图鉴页 + 详情页**按所选赛季过滤/展示；枢纽页已改为「本季全量 + 数据同步版本」（不再展示「本赛季新增」，`is_season_new` 退役，见第十一节）。
  - **完整档（中高成本）**：再让**枢纽页**也随赛季切换（需要为历史季补一套「新增」判据或换展示口径），工程与维护都上一个台阶，建议二期。
- **不建议**做的：把赛季做成路由（`/currency/s2/...`）——会成倍放大预渲染/快照/SEO/守卫/内部链接的工作量与永久维护负担，与现有站点「本地优先·构建期快照」的成本模型冲突。用**设置页偏好（localStorage）**即可。

## 二、官方是怎么区分赛季的（数据事实）

### 2.1 源表层面的赛季归属

转换器已把赛季归属从官方**赛季 × 实体连接表**取到每条产物记录（不是从基础表反推，这是有意的正确做法，见 `docs/agents` 与 `docs/memory/data-semantics.md`）：

| 数据域 | 赛季来源连接表 | 产物字段 | 说明 |
| --- | --- | --- | --- |
| 角色 | `GridFightRoleBasicInfo.SeasonIDList / SeasonID` | `roles[].season_ids: number[]` | 一个角色可属多季 |
| 羁绊 | `GridFightTraitBasicInfo.SeasonID`（+`GridFightSeasonTraitShow` 校验） | `traits[].season_id: number` | 单季 |
| 投资环境 | `GridFightSeasonPortal` | `portals[].season_id` | 单季，未登记为 `null` |
| 投资策略 | `GridFightSeasonAugment` | `augments[].season_id` | 单季 |
| 装备 | `GridFightSeasonItem` | `items[].season_ids: number[]` | 可多季共有 |

每个产物**顶层**都有 `season: { id, sub_season_ids }`，当前 `id=2`、`sub_season_ids=[1]`（`season_scope.py::season_meta`；当前季取 `GridFightSeasonModule.SeasonID` 的**最大值**，禁止取首行/行序，因为滚动后表内会同时存在多季行）。

### 2.2 当前产物里的实际分布（4.7.0 实测）

| 域 | 赛季 1 | 赛季 2（当前） | 合计 |
| --- | --- | --- | --- |
| 角色 `roles` | 75 | 62 | 137 |
| 羁绊 `traits` | 33 | 34 | 67 |
| 环境 `portals` | 84 | 36 | 120 |
| 策略 `augments` | 334 | 77 | 411 |
| 装备 `items`（按归属计） | 166（含 71 两季共有） | 174（含同 71） | 269（95 仅 S1 / 103 仅 S2 / 71 共有） |

> 因数据只有 2 个赛季桶，切换维度目前是「赛季 1 / 赛季 2」二选一；未来赛季滚动会自动变成三选一，这恰好是「用偏好而非写死」的理由。

### 2.3 关键的语义陷阱：「本赛季新增」（`is_season_new`）

`is_season_new` 的判据是**当前代名册 − 上一代名册**（`season_delta.py::mark_season_new`：`*Old` 表里 `ExistSeason` 最老的一代做参照，再叠「本赛季登记」闸门）。这条链**天然只认「当前代 vs 上一代」**，所以：

- **赛季 2 的角色**：`is_season_new=True` 只有 15 条（其余 47 条是同季但非新增）；羁绊 34 条全 True（本季新增）。
- **赛季 1 的角色/羁绊**：`is_season_new` **全为 `false`**（它们不在「当前代 − 上一代」里）。

**这意味着**：如果让用户切到「赛季 1」并复用现有枢纽页逻辑（按 `is_season_new` 过滤），**枢纽页的「本赛季新增」会整片空**。要展示「赛季 1 的新增」，本质上需要一个**针对赛季 1 的差集判据**（把「上一代」定位到「代 1 之前」），而那是另一套算法与另一批可能已不在当前 vendor dump 里的历史名册——**这是完整档里最贵、最不确定的一块**。

## 三、现状盘点：已经按赛季的 vs 写死当前季的

| 位置 | 现在是否按赛季 | 备注 |
| --- | --- | --- |
| 5 个图鉴页 `fetchData` | ✅ 按赛季过滤，但**写死 `season.id`（当前季）** | 角色 `season_ids.includes`、羁绊/环境/策略 `season_id ===`、装备 `season_ids.includes`；这就是加切换的「接入点」，改动很小 |
| 枢纽页 `/currency`（`useCwSeason`） | ⚠️ 只用**当前季 + `is_season_new`** | 「本赛季新增 / 本赛季全量」口径；换赛季需要重构 `buildCwSeason` 与整套账头 |
| 角色/羁绊等**详情页** | ✅ 数据本身不裁季（S1 详情可直连），只是站内已无 S1 列表入口 | 详情页展示的是「该条目自身」，天然无赛季维度冲突 |
| 设置页 `SettingsView.vue` | ✅ 已有「强调色 / 开拓者性别 / 语言」三块偏好区 | 赛季切换照抄这套（`localStorage` + `ref` + 分段按钮），模式最成熟 |
| 预渲染快照 / sitemap / AI 端点 | ⚠️ 按「当前季可见条目」生成 | 若赛季改为路由会成倍膨胀；若只做偏好，则**快照仍按当前季**（爬虫与无 JS 用户看到当前季），这点要接受 |
| 数据转换器 | ✅ 无需改（产物已全量含两季 + 归属字段） | 唯一可能要动的是「为历史季补新增判据」（完整档才需要） |

## 四、实现方案与难度

### 4.1 三档方案

- **方案 A（不推荐）赛季进路由**：`/currency/role?s=1` 或 `/currency/s1/role`。影响：路由、预渲染快照家族、sitemap、`check-ai-endpoints` 守卫、内部链接本地化前缀、e2e 全谱都要×N 赛季；永久维护负担最重。
- **方案 B（推荐）设置页偏好 + 图鉴/详情按所选赛季**：新增偏好存 `localStorage`（照抄 `lib/theme.ts` 的 `getSavedAccent/setAccent` 模式），当 `CatalogContext` 里带上所选赛季，五个 `fetchData` 用它替代 `season.id`；枢纽页保持当前季（或加「仅当前赛季」提示）。
- **方案 C（完整档）B + 枢纽页也随赛季**：额外重构 `useCwSeason`/`buildCwSeason` 让「账头/名册/羁绊」随所选赛季，并为历史季准备一套「新增」口径（或把历史季的枢纽页改成「该季全量名册」而非「该季新增」）。

### 4.2 分模块改动清单（方案 B）

1. **新增偏好模块** `src/lib/cw-season.ts`：`getSavedCwSeason() / setSavedCwSeason(n|null)`（`null` = 跟随当前季，默认值），沿用 `localStorage` + 类型守卫模式。约 40 行。
2. **设置页新增「赛季」分区**（`SettingsView.vue`）：照抄现有 `nk-seg` 分段按钮（性别那块），选项来自「数据里出现过的赛季集合 ∪ 当前季」，选中即存。需新增 i18n 键（见 4.3）。约 60–80 行 + 少量样式复用。
3. **`CatalogContext` 扩展**：`{ version, cwSeason?: number | null }`，`CatalogPage.vue` 构造 ctx 时注入所选赛季。**注意**：`use-cw-season.ts` 与 `use-release-showcase.ts` 也构造 ctx，需一并处理（前者是枢纽页，方案 B 里它继续用当前季即可）。
4. **五个 `fetchData` 改用 ctx 的赛季**：把 `const currentSeason = season?.id` 改为「`ctx.cwSeason ?? season?.id`」，其余过滤逻辑不变。**这是最小、最安全的核心改动**（5 个文件各 1–2 行）。
5. **详情页赛季印记**：`CurrencyRoleView.vue` 现在显示 `data.season_ids`（如「赛季 1 / 2」），已能表达归属，无需改；若要显示「当前查看的赛季」需再加，属可选。
6. **列表页可能的赛季切换入口**：可选在货币战争图鉴页顶部放一个轻量切换器（复用同一偏好），或只在设置页切。**建议只在设置页**，避免每页都塞控件。

### 4.3 i18n 与术语

- 需新增键（`ui` 词典，13 语言）：`settings.seasonTitle`、`settings.seasonListbox`、`settings.seasonFollowCurrent`（「跟随当前赛季」）、`settings.seasonHint`、以及赛季标签文案。
- **术语红线（重要）**：`CONTEXT.md` 明确「赛季代际 / 本赛季新增」**不显示赛季号**，因为货币战争编号跨代不一致（数据里当前代是 2，而旧代 101/102/103）。ADR 0020 在 2026-11-11 才解禁「第 {n} 赛季」（因 `season.id=2` 已与外部第二大赛季对齐）。**因此「赛季 1」这个桶如何标注需要单独拍板**：是写「第 1 赛季」、还是「第一赛季（4.4 扩充）」、还是「历史赛季」。**不要**默默把数据桶号直接当官方赛季名用。
- 官方**赛季名**（如「货币战争•零和博弈」）当前**不在产物里**（`season.json` 已删）；要把名字显示出来，需从 TextMap 重新抽取一份「赛季 id → 官方名」映射（中等量的小转换器工作），否则只能显示数字/序号。
  - **2026-11-18 更新（已落地）**：官方赛季名/简介已由 `currency_seasons.py` 抽取（`GridFightSeasonModule.ActivityModuleID` → `ActivityConfig` → `ActivityPanel.TitleName`/`PanelDesc`），产出 `currency/seasons.json`；枢纽页据此改为「赛季枢纽」页。详见 [ADR 0067](../adr/0067-货币战争枢纽页改为赛季枢纽页.md)。本条下列展开性叙述作历史背景保留。

### 4.4 完整档（方案 C）额外成本

- `buildCwSeason` 现在按 `is_season_new` 造「新增」集合与头像变体、分布、羁绊四件套；要让枢纽页随赛季，需重构为「给定赛季 → 该季全量名册（或该季新增）」。历史季「新增」缺少干净数据源（见 2.3），**这是最大的不确定项**。
- 枢纽页的「赛季印记/账头/账房」全是「本季新增 / 本季全量」口径（ADR 0020 四幕长卷），换赛季等于换一套展示契约，**e2e 断言要大改**。

## 五、难度评估（汇总）

| 维度 | 方案 B（推荐） | 方案 C（完整） |
| --- | --- | --- |
| 转换器改动 | 无 | 有（历史季「新增」判据，不确定性高） |
| 前端改动量 | 小（1 偏好模块 + 设置页 1 分区 + 5 个 fetchData 各几行） | 中～大（重构枢纽页组合式 + 模板 + 样式） |
| 类型/契约 | `CatalogContext` 加 1 字段 | 同上 + `CwSeason` 结构变化 |
| e2e | 少量新增（设置页切换 + 图鉴按季过滤） | 枢纽页断言大改 + 多赛季用例 |
| 预渲染/快照/SEO | **不变**（仍按当前季） | 若做路由则×N；只做偏好则仍不变 |
| 维护风险 | 低（数据驱动，赛季增减自动适配） | 中高（历史季「新增」口径需长期维护） |
| 预计工作量（相对） | ~0.5–1 人日（不含 e2e 深测） | ~3–5 人日 + 数据侧探索 |

**结论：方案 B 是「低成本、高确定性、可逆」的展示层改动；方案 C 的核心不确定性在于历史季「新增」没有干净数据源。**

## 六、维护难度与长期风险

1. **赛季滚动会持续发生**：每上一个新赛季，数据桶从 {1,2} 变 {1,2,3}…。偏好方案天然自适应（选项从数据里派生），**但「当前季」判据必须始终取 `season.id` 最大值，不能写死**——这条已在转换器里正确实现，前端不要另行硬编码。
2. **「新增」口径的历史债**：只要不动枢纽页，历史季「新增」问题就**被隔离在方案 B 之外**；一旦做方案 C，就要长期维护「每季新增」这条链（而 `*Old` 表是死数、旧 dump 轮转会丢——`docs/memory/data-pipeline.md` 记过「赛季轮转不会报错，只让产物静默混季」的坑）。
3. **术语一致性**：赛季号上屏的口径（见 4.3）是长期正确性风险，容易与外部认知（4.4 是「第三次扩充」）冲突。必须先在 CONTEXT.md/ADR 里定死，再上屏。
4. **S1 详情页仍可直连**：当前站内已无 S1 列表入口，但路由可达；做切换后 S1 列表会重新有入口，需确认 S1 详情数据完整（当前产物确实完整保留两季，详情直连无障碍）。
5. **SEO/快照取舍**：偏好存在浏览器端，**爬虫与无 JS 用户永远看到「当前季」**。这是有意的取舍（与站点「本地优先·构建期快照」模型一致），但要在心里接受：赛季切换是**给交互用户的功能**，不进搜索引擎。

## 七、评估结论：是否值得做

**值得做，且性价比高——但要摆正定位。**

- 用户诉求「让用户查看不同赛季的数据」在**方案 B** 下几乎不需要碰数据管线：转换器已全量给两季、图鉴页已按季过滤，只差「把写死的当前季改成用户可选」。这是**投入产出比最高的那 20% 改动**。
- 唯一会让这件事变「贵」的，是把它理解成「赛季复盘/赛季新增回顾」（方案 C）——那会撞上历史季「新增」无干净数据源 + 枢纽页口径重构两块硬骨头。**除非用户明确要「回看旧赛季新增了什么」，否则建议先用方案 B 满足「查看不同赛季数据」。**
- **不做赛季进路由**：维护成本与站点架构冲突，收益不成比例。

## 八、建议落地路径（分两期）

**一期（方案 B）**
1. `src/lib/cw-season.ts` 偏好模块（默认「跟随当前赛季」）。
2. 设置页「04 赛季」分段区（数据驱动选项、`localStorage` 持久化）。
3. `CatalogContext.cwSeason` + 五个货币战争图鉴 `fetchData` 改读该值（`?? season.id` 兜底）。
4. 新增 i18n 键（13 语言）+ 术语按 4.3 定稿。
5. 验证：`pnpm test`（fetchData 单测加「指定赛季」用例）、`pnpm build`、受影响 e2e（设置页切换 + 图鉴按季过滤 + 无溢出）。快照/SEO 断言不变。

**二期（方案 C，按需）**
6. 先做**数据侧探索**：能否为历史季算出一套可信的「该季新增」（或在枢纽页把历史季改为「该季全量名册」口径），拿到结论再动前端；否则不做枢纽页切换。

## 九、需要你拍板的点

1. **定位**：你要的是「查看不同赛季的图鉴/详情数据」（方案 B），还是也包括「回看某赛季新增了什么」（方案 C）？
2. **控件位置**：只放设置页（推荐），还是货币战争图鉴页顶部也放一个快捷切换？
3. **赛季标注**：数据桶「1 / 2」上屏怎么叫——「第 N 赛季」还是「第一赛季（4.4 扩充）」？是否要额外做「赛季 id → 官方赛季名」的抽取？
4. **旧赛季入口**：切到旧赛季后，旧赛季的列表/详情要不要都开放（数据齐全，可开放），还是只读展示？
5. **枢纽页**：已裁决——枢纽页改为「本季全量 + 数据同步版本」，不再随切换、也不再展示「新增批次」（`is_season_new` 退役）。见第十一节。

## 十、转换器赛季隔离审计（2026-11-18 落地时实检）

### 10.1 数据层隔离：干净可靠（PASS）

逐项核过产物与源码（`public/data/cn/currency/*.json`，4.7.0）：

1. **每条记录都带赛季归属，无 null/髒值**：角色/羁绊/环境/策略/装备的 `season_id(s)` 全 ∈ {1,2}，**null = 0 条**（`season_scope.py::apply_season_ids` / `_season_item_membership` 未登记时置 null 而非兜底当前季——这是正确的，不把未知归属伪装成确定值）。
2. **无跨季引用污染**：遍历 137 条角色的 `trait_list`，**没有一条引用了不同赛季的羁绊**（0 例）。角色与羁绊的赛季归属自洽。
3. **列表/快照/守卫三处同口径按 `season.id` 过滤**：图鉴 `fetchData`、`gen-ai-endpoints` 的列表/详情页、`check-ai-endpoints` 的期望集都取顶层 `season.id`（当前 2）——不会出现「路由层一季、快照层一季」的错位。
4. **S1 详情页仍可直连**：产物完整保留两季（`role.json` 137、`traits.json` 67…），详情页不裁季，`/currency/role/{S1 id}` 可达。即「列表只给当前季/所选季，详情始终给条目本身」。

### 10.2 语义层：`is_season_new` 仅当代可算（已知边界，非 bug）

- `is_season_new` 只在**当前代**算得出（`season_delta.py` 差集），S1 条目全为 false——所以「切到 S1 后枢纽页『本赛季新增』会空」。本方案 **B 把枢纽页排除在切换外**，此边界不影响图鉴/详情。
- `currency_catalog.py::_convert_traits` 的 `season_id = entry.get("SeasonID", 0) → 0` 是**默认值不是 nullable**：若上游缺 `SeasonID` 会得 0（当前 0 条），比 null 难发现。建议转换器加一条「season_id ∉ {已知季} 时告警」，属低优先加固。

### 10.3 AI 误导的真正向量：同名跨季条目的标题未消歧（本轮已修）

**发现（真缺陷）**：49 个角色名同时存在于 S1 与 S2，且是**不同条目**（瓦尔特 `1004`[S1] vs `100402`[S2]，立绘同 `avatar_id` 但 rarity/羁绊/技能全不同）。修缮前详情页 `<title>` 与 `<h1>` 只写角色名，导致 `/currency/role/1004` 与 `/100402` **标题与 h1 完全相同**。AI（或人）搜「第 2 赛季瓦尔特」时，搜索引擎可返回 S1 页 → 读到的是 S1 数据，正是你担心的「查 S2 结果检了 S1」。

**修复**：详情页标题追加赛季（`瓦尔特 · 第 1 赛季 - …` / `瓦尔特 · 第 2 赛季 - …`），且**快照（`tools/gen-ai-endpoints.mjs`）与客户端页（`document.title`）两处同口径**同步改（两源不改会同一 URL 两标题）。验证：构建后 `dist/prerender/currency/role/1004.html` 与 `100402.html` 标题已不同；跨季同名碰撞 **49→0**。

**残留（另类，未在标题层）**：构建后仍有 3 组同名 <title>，均为**同季内同角多费变体**或**跨季同名+季内变体**（阿哈 `151112/151122/151132`、布洛妮娅 `11011/11012`、银狼LV.999 `15061/15062/15063`[S1]+`150602`[S2]）。改标题不能消歧这类（同季同名的条目本就无法靠季号区分），**也不是「S2 误指 S1」那类困惑**（都在同一季或本就是同名变体）。已记入 `docs/memory/data-semantics.md`，若要彻底解需在标题/描述里再区分费用或变体，属单独议题。

### 10.4 AI 侧补充结论

- 枢纽快照已改为**本季全量**（不再用 `pickSeasonNew`）；AI 读图鉴列表页与详情页（标题带季号）都不会混季。
- 赛季切换偏好存在浏览器端，**快照/SEO 仍以当前季为准**（有意取舍）：爬虫/无 JS 永远看当前季，交互用户可切。这是方案 B 的既定边界。

## 十一、版本差异展示口径 —— 退役「赛季新增」（2026-11-18 裁决）

**背景**：赛季 1→2 是玩法大版本，但期间有多个小版本更新，官方**不提供「赛季 1.1」这类精确表述**。核查后的数据事实：
- 常规模式每条目自带 `release_version`（小版本粒度）；**货币战争产物条目无任何版本字段**，最小时间片只能到「代」（`ExistSeason` 101/102/103），且 `*Old` 名册只留这几代快照、4.6/4.7 无快照，**代内小版本被并入该代**（ADR 0020 自认 4.3 的 Archer 并入代103）。
- 因此「`is_season_new` = 当前代 − 上一代」本质是把**多个小版本捆成一个假批次**，却用「本赛季新增」这种像精确追踪了小版本的说法展示 → 误导。

**裁决（落定）**：把「版本差异」拆两概念，**只保留可靠的那条**：
1. **赛季索引**（内容属于哪一季）——可靠（连接表直取）→ 做赛季切换与筛选（方案 B 已做）。
2. **新增批次**（何时/哪版新增）——不可靠（无版本级数据、代内小版本被吞）→ **不展示**。

**落地**：
- 枢纽页由「本季新增 / 全量」改为 **「本季全量 + 数据同步版本」**：账头显示角色 62 / 羁绊 34（本季全量），印记保留「第 N 赛季 / 版本 4.7 / 同步日」；不再出现「新增」措辞与空态。
- **前端与快照全部停用 `is_season_new` / `season_new_count`**：`useCwSeason`/`buildCwSeason` 改为本季全量；跨高亮改为通用的羁绊↔角色双向（不再依赖 isNew）；AI 快照枢纽页改列本季全量。
- **字段保留在产物**（转换器照常计算，`season_new_count` 仍作可观测），只是无消费点——避免连动转换器与产物 JSON。
- 文案：`cwHub.releaseTitle`→「本季全量」、`cwHub.act3Title` 去掉「新」、`cwHub.empty/loadingAria/errorDetail` 与 `snapshot.sum.cwHub` 去「新增」措辞（13 语言已改）。

**未采用**：不编造「赛季 1.1」等官方不存在的表述；不硬切「按小版本」细分（数据不支持）。
